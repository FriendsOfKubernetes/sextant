# ADR-0120: OpenShift views read OpenShift's own types, diagnose Routes like Ingresses, and send only what `oc` sends

## Context

#267 asked for the OpenShift kinds where a cluster serves them: Route (host, TLS termination, the Service and its pods, a diagnosis like an Ingress's), DeploymentConfig (rollout state, triggers, restart and rollback like Deployments where the API allows), Project, BuildConfig and Build (status, the build pod's logs), ImageStream and ImageStreamTag. Read-only except explicit actions with a confirmation.

The kinds are served by openshift-apiserver (aggregated APIs, not CRDs): `route.openshift.io/v1`, `apps.openshift.io/v1`, `build.openshift.io/v1`, `image.openshift.io/v1`, `project.openshift.io/v1`. DeploymentConfigs are deprecated since OpenShift 4.14 but still served. Some facts shape the design:

- A Route carries its TLS material inline (`spec.tls.certificate`, `key`, `caCertificate`, `destinationCACertificate`): the private key is part of the object, not a Secret. OpenShift 4.16+ may name a Secret instead (`spec.tls.externalCertificate`).
- The router matches `spec.port.targetPort` against the endpoints' port name or number (`endpointsForAlias`, `pkg/router/template/template_helper.go` in openshift/router): a name is the Service port's name (EndpointSlice port names are the Service port names), a number the pod port. Without a target port the router uses every endpoint of the Service.
- ImageStreamTags are served without `watch` (`oc api-resources -o wide`), and tables and details in Sextant follow objects by watching them.
- A DeploymentConfig's scale subresource answers `extensions/v1beta1` Scale for `apps.openshift.io/v1` (`GroupVersionKind` of `ScaleREST`, `pkg/apps/apiserver/registry/deployconfig/etcd/etcd.go` in openshift-apiserver), whose `status.selector` is a map; the core's scale (kube-rs `patch_scale`) decodes the answer as `autoscaling/v1` Scale, where it is a string.
- `oc rollout undo` is two steps (a `DeploymentConfigRollback` POST to `deploymentconfigs/<name>/rollback` that returns a generated config, then an update of the DeploymentConfig with it), with `--to-revision` resolved from the ReplicationControllers' encoded configs.

Sources read: github.com/openshift/api `route/v1/types.go`, `apps/v1/types.go`, `apps/v1/consts.go`, `build/v1/types.go`, `build/v1/consts.go`, `image/v1/types.go`, `project/v1/types.go`, `annotations/annotations.go`; github.com/openshift/oc `pkg/cli/rollout/latest.go`, `pkg/cli/startbuild/startbuild.go`; github.com/openshift/library-go `pkg/apps/appsutil/util.go` (`MakeDeployment`, `LatestDeploymentNameForConfigAndVersion`, `IsTerminatedDeployment`), `pkg/build/naming/namer.go` (`GetName`); github.com/openshift/openshift-controller-manager `pkg/build/buildutil/util.go` (`GetBuildPodName`, `LabelValue`, `IsTerminalPhase`); github.com/openshift/router `pkg/router/template/template_helper.go`, `router.go`; github.com/openshift/openshift-apiserver `pkg/apps/apiserver/registry/deployconfig/etcd/etcd.go`.

## Decision

- **A discovered section** `openshift` ("OpenShift", `src/features/openshift/`) with Routes, DeploymentConfigs, BuildConfigs, Builds, ImageStreams and Projects (cluster-scoped), each listed only where discovery serves it, with the generic Edit and Delete. ImageStreamTags are not a table of their own (no `watch`): an ImageStream's details list its tags from `spec.tags` and `status.tags` — the fields an ImageStreamTag is built of — with the current image, import time, history size, scheduled import and the `ImportSuccess=False` message. A trigger's or an output's `ImageStreamTag` reference links to its ImageStream.
- **Route**: state Admitted (some router's `Admitted=True` in `status.ingress[]`), Rejected (a router's `Admitted=False`, in its words), else Not admitted; the address (`spec.host`, else a router's generated host; `https` with TLS), path, wildcard policy, target port, TLS termination and the plain-HTTP policy (`None` when unset). Of the inline TLS fields only **whether each is set** is read and shown — never a value, the private key included; an `externalCertificate` Secret is a link and is not read. A certificate's expiry is not shown: the window has no certificate parser, and TLS parsing stays in the core for Secrets only (ADR-0069). The backends (`spec.to` and `alternateBackends`) show their weights (100 when unset, as the API defaults it) and their share of the requests, and each Service's pods ready from the namespace's Service and pod watches (the same specs the diagnosis watches, shared).
- **Diagnose like an Ingress** (`src/features/diagnose/openshift.ts`, registered through `routeKinds.ts`): the routers' admission first (a rejection breaks the path; no answer is a warning for 2 minutes, then broken: no router runs or no shard selects the Route), the address, the TLS beside the path (a certificate without a key is broken; no certificate means the router's default one; reencrypt without a destination CA trusts the service CA), then each backend: not a Service, every weight 0 (the router answers 503), a weight 0, a missing Service of the Route's own namespace, the Service port the target port selects (by name; by number the ports targeting that pod port; a number only a named target port could lead to is "cannot tell"), and on into the Service's own checks. No list and no Secret of its own is read.
- **DeploymentConfig**: the rollout state from the conditions (`Progressing` reasons of `apps/v1/consts.go`: `ProgressDeadlineExceeded` and `ReplicationControllerCreateError` failed, `RolloutCancelled` cancelled, `NewReplicationControllerAvailable` done, others under way; then `Available`; paused; never deployed), replicas, latest version and its causes, strategy and hooks, triggers (ConfigChange, ImageChange with its ImageStreamTag, automatic, containers, last image), and the rollouts: the ReplicationControllers labelled `openshift.io/deployment-config.name=<name>` (as `MakeDeployment` labels them; owned ones checked by the owner's uid), newest version first, with the deployer's `openshift.io/deployment.phase`, pods ready and the status reason — one label-selected watch of the namespace, ≤ 200.
- **BuildConfig and Build**: strategy and builder image, source (the Git URI through `safeUriText`: no userinfo, query or fragment; an inline Dockerfile only as "set"; the source Secret by name), output, run policy, triggers by type (a webhook trigger's secret is never read), and the builds labelled `openshift.io/build-config.name=<LabelValue(name)>`, newest number first (≤ 500). A Build's phase, reason and message, BuildConfig, number, commit, what started it, times, duration (`status.duration` in nanoseconds, else start to end), output image and digest, the log snippet (`cleanText`), and its pod: `openshift.io/build.pod-name`, else `GetBuildPodName` (`<build>-build`, past 63 characters the name cut to 48, its FNV-1a hash and `-build`), watched by name; "Build logs" opens the existing logs tab of that pod. A gone pod is said so.
- **Project**: display name, description, requester and node selector annotations, phase, and its Namespace.
- **Two actions, window only, after a confirmation that shows the request** (`openshift_rollout_latest`, `openshift_start_build` → `crates/sextant-core/src/resources/openshift.rs`): "Rollout latest" refuses a paused DeploymentConfig and one whose latest version's ReplicationController (`<name>-<version>`) has not ended (`Complete` or `Failed`), as `oc rollout latest` does — the window disables the button from a watch of that ReplicationController and the core checks again right before sending — then POSTs `{"kind":"DeploymentRequest","apiVersion":"apps.openshift.io/v1","name":…,"latest":true,"force":true}` to `deploymentconfigs/<name>/instantiate`. "Start build" POSTs what `oc start-build <name>` sends without flags: `{"kind":"BuildRequest","apiVersion":"build.openshift.io/v1","metadata":{"name":…},"triggeredBy":[{"message":"Manually triggered"}],"sourceStrategyOptions":{},"dockerStrategyOptions":{}}` to `buildconfigs/<name>/instantiate`. The core builds both bodies from the object's name (the window sends only the reference); the window's copy in `requests.ts` is the text shown, and a test on each side pins the same text. Each is sent once (ADR-0055), signed by `sextant`, under `CHANGE_TIMEOUT`. `oc`'s fallback for servers before 1.4 (raising `latestVersion` by an update) is not copied. Neither command is an MCP tool or an extension method (a test in `src-tauri/src/commands/openshift.rs`).
- **Left out**: Scale of a DeploymentConfig (the scale subresource's answer does not decode as the core's Scale, so the generic action would change the replicas and then report an error; Edit changes `spec.replicas`), Restart (`src/features/restart/` restarts by the apps/v1 controllers' own mechanisms, which a DeploymentConfig does not have; "Rollout latest" is how a DeploymentConfig is redeployed), and Rollback (`oc rollout undo` is a generate-then-update pair, not a small exact copy).
- **Problems**, category `openshift`, on by default, in `NEVER_FOR_AGENTS`: a Route no router admitted after 2 minutes (from its rejection, else its creation); a DeploymentConfig whose rollout failed (at once); a Build Failed or Error for a day after it ended — only the latest failed build of its BuildConfig, judged across the Build source's rows (`across.ts`: a later build of the same BuildConfig by `openshift.io/build.number` tells it instead); an ImageStream with a tag whose import fails, after 5 minutes. The sources (Routes, DeploymentConfigs, Builds, ImageStreams) are each capped at `MAX_SOURCE_OBJECTS`; Projects and BuildConfigs have no problems. The section counter counts the category.

## Why

- OpenShift's own types and conditions are what `oc` and the console read; re-deriving them would disagree with the controllers.
- A Route's private key lives in the Route; the details panel is shown on screen and in screenshots, so it says only "set". The YAML section and Edit show the object as stored, as for any kind.
- Showing the exact request before sending, and building it in the core from the name only, keeps the two changes as narrow as `oc`'s.

## Consequences

- The watches of Routes and Builds bring the inline TLS material and build specs into the window's memory for the problems store, as any watch of these kinds does; nothing of them is kept or shown beyond the problems.
- ImageStreamTag details cannot be opened on their own; their content is the ImageStream's tag table.
- A Route whose target port is a number that only a named Service target port resolves to is "cannot tell" in the diagnosis.
- **Inline secret material leaves the window only hidden** (amendment after the 0.25.0 review). A Route's `spec.tls.key` (openshift/api route/v1/types.go `TLSConfig.Key`) and a BuildConfig's `spec.triggers[].github|generic|gitlab|bitbucket.secret` (build/v1/types.go `WebHookTrigger.Secret`) are rows of the core's one table of inline secret paths (`crates/sextant-core/src/resources/inline_secrets.rs`, shared with the window as `src/resources/inline-secrets.json` and kept equal by a test on each side). An agent's `get_resource` gets them only with "Secret values" on the kind, as a Secret's values (ADR-0043); `list_resources`, `patch_resource`'s answer and dry runs never; an extension's `resources.get|list|watch|patch` never (it gets no Secret value from those either, whatever was granted); the change timeline keeps each such value only as a salted hash in memory (so a change of it is still seen) and records, shows, saves (`timeline::save` drops any value under those paths again) and hands to `get_recent_changes` its path alone, as for a Secret's keys. A hidden copy carries `sextant.dev/values-hidden` naming the hidden paths, so replace and apply refuse it and it is never saved over the real object. The window's own YAML section and editor keep the object as it is (the editor must save the field back unchanged); that is the accepted exception, as it is for any kind the user opens. The certificates (`certificate`, `caCertificate`, `destinationCACertificate`) are public and stay.
