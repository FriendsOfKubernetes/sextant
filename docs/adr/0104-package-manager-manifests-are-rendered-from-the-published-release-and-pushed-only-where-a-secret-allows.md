# ADR-0104: Package-manager manifests are rendered from the published release and pushed only where a secret allows

## Context

#217 asked for the install channels people use for their other tools: a Homebrew cask, Scoop and winget on Windows, an `.rpm` next to the `.deb` and AppImage, and arm64 builds for Linux, with the release workflow keeping the manifests current from the release's own checksums. Update behaviour stays as it was: the AppImage, `.dmg` and `.msi` replace themselves from the signed `latest.json` (ADR-0022), package-manager installs are updated by the package manager. The installers are still not code-signed (#20).

## Decision

- **rpm, x86_64 and aarch64.** The Linux jobs bundle `deb,rpm,appimage`. Tauri's rpm writer adds no `Requires` of its own, so `bundle.linux.rpm` names library capabilities rather than package names, which differ between Fedora and openSUSE: `libwebkit2gtk-4.1.so.0()(64bit)`, `libgtk-3.so.0()(64bit)`, and recommends `libayatana-appindicator3.so.1()(64bit)` (the tray is optional, ADR-0059). An rpm-installed copy reports `rpm` as its bundle kind; the window already offers it no in-app install (`canInstall`) and says "update with your package manager" (`updates:manual.rpm`). `latest.json` still carries `linux-<arch>-rpm` (tauri-action writes it from the signed `.rpm`), like `-deb`.
- **Linux arm64** builds natively on GitHub's `ubuntu-22.04-arm` runner (free for public repositories; 22.04 for the same glibc baseline as the x86_64 job) as another row of the existing build matrix: its own rust-cache key, its own dry-run artifact `bundles-linux-arm64`. tauri-action names the entries after the host: `linux-aarch64` (the AppImage), `-appimage`, `-deb`, `-rpm`. The publish job's "every platform is there" check now requires `linux-x86_64`, `linux-aarch64`, both arches' `-deb` and `-rpm`, `darwin-x86_64`, `darwin-aarch64` and `windows-x86_64`; its per-key file check already knew `*-rpm`.
- **Checksums come from the published assets.** `scripts/packaging.mjs render` takes GitHub's JSON of the published release and uses each asset's `digest` (GitHub's SHA-256 of the uploaded file); an asset without one is downloaded from the release and hashed. Nothing is hashed from a build directory except in a dry run, which has no release (`--dir`). The script renders `packaging/**/*.tmpl` with a fixed set of placeholders, refuses a missing value or one with a quote, backslash or line break, and checks that the Scoop JSON parses. Its tests (`scripts/packaging.test.mjs`, in `npm run check` as `check:packaging`) render the fixture release and check each manifest's structure and that every URL is the asset's own download URL (also after Homebrew's `#{version}` and Scoop's `$version` are substituted); `ruby -c` checks the cask where Ruby exists. No `brew style` or schema validator runs offline, so the structure tests stand in for them.
- **Homebrew: a cask in our own tap** (`FriendsOfKubernetes/homebrew-sextant`, `Casks/sextant.rb`), the universal `.dmg`, `auto_updates true` (the `.app` updates itself, so `brew upgrade` leaves it alone unless `--greedy`), `livecheck` on the latest GitHub release, a `zap` of the app's own directories under the bundle identifier (read from `tauri.conf.json`), and a caveat on opening an app without an Apple Developer ID. `homebrew/cask` itself is not attempted: it no longer takes apps that fail Gatekeeper, which waits for #20.
- **Scoop: a portable zip, not the msi.** Scoop extracts an `.msi` instead of running it, and the executable inside carries Tauri's bundle-kind marker `MSI`: that copy would offer "Install and restart" and run the `.msi` into Program Files beside Scoop's. The Windows job therefore also packs `Sextant_<version>_x64_portable.zip` with `target/release/sextant.exe`, the executable the bundler restores unpatched after each bundle (`__TAURI_BUNDLE_TYPE_VAR_UNK`; `check-unbundled` fails the job if that ever changes). Such a copy has no bundle kind: it never checks for updates at start and Settings sends the user to the release page — Scoop updates it (`checkver`/`autoupdate` on the GitHub release). The app is a single executable (no resources or sidecars) and uses the WebView2 runtime Windows 10 and 11 ship; settings and data stay in `%APPDATA%`/`%LOCALAPPDATA%`, so nothing needs `persist`. The bucket is our own (`FriendsOfKubernetes/scoop-sextant`, `bucket/sextant.json`).
- **winget: the msi.** Three manifests (version, installer, defaultLocale; schema 1.6.0; `FriendsOfKubernetes.Sextant`, `InstallerType: wix`, SHA-256 in upper case) under `manifests/f/FriendsOfKubernetes/Sextant/<version>/`. A winget install is the `.msi` install and updates itself as before. winget-pkgs takes pull requests only and reviews a new package by hand, so the first version is submitted by hand; afterwards the `winget` job opens the pull request with `wingetcreate submit`.
- **Outward steps are gated by secrets and never fail the release.** The `packages` job runs after `publish`, renders the manifests and keeps them as the artifact `packages-<tag>` (30 days). It sends a manifest anywhere only for a release that became "latest" with a plain `vX.Y.Z` tag, and each push needs its own secret — `TAP_GITHUB_TOKEN`, `BUCKET_GITHUB_TOKEN`, `WINGET_GITHUB_TOKEN` — and is skipped without it; the pushes are `continue-on-error` (the `winget` job as a whole). `packaging/push-manifest.sh` commits the one file to the tap or bucket (the token in an `http.extraheader` for that process only, never in a URL or `.git/config`; an unchanged file is not committed). The taps are updated by a direct commit, not a pull request: they are our own repositories and the manifest is generated.
- **A dry run** builds the zip and every bundle as before, renders the manifests from its own `bundles-*` artifacts into `packages-<tag>`, and sends nothing. A dry run for a tag that does not exist yet builds the commit the run was started from (its manifests must already carry that version), so a change of the workflow is tried before a tag exists: `gh workflow run release.yml --ref main -f tag=v<next> -f dry_run=true`. With an existing tag it builds the tag as before; a real release still requires the tag.

## Outward steps (the user's, one step each)

1. Create `FriendsOfKubernetes/homebrew-sextant` and `FriendsOfKubernetes/scoop-sextant` (public, initialized with a README).
2. Add the repository secrets `TAP_GITHUB_TOKEN` and `BUCKET_GITHUB_TOKEN`: fine-grained tokens with Contents read and write on that one repository.
3. After the first release with these assets, submit the first winget version from the `packages-<tag>` artifact: on Windows, `wingetcreate submit manifests/f/FriendsOfKubernetes/Sextant/<version>` (it asks for a GitHub login, or reads `WINGET_CREATE_GITHUB_TOKEN`; or `komac new FriendsOfKubernetes.Sextant` with the `.msi` URL); once it is merged, add `WINGET_GITHUB_TOKEN` (a classic token with `public_repo`, whose account may fork microsoft/winget-pkgs).

## Consequences

- Releases carry three more Linux files per arch pair (`.rpm` x86_64, and `.deb`/`.rpm`/`.AppImage` for aarch64) and the Windows portable zip; release notes say which installs update themselves.
- A Scoop copy is told apart by where it runs (see the amendment): About says "Scoop (portable .zip)" and the update hint says `scoop update sextant`.
- The `.deb` update hint names the `.deb` of the running machine's architecture (see the amendment).
- A rebuild of a published release that is still the latest renders and pushes again: the new bundles have new checksums, so the tap and bucket must follow, and the winget pull request for the same version carries the new `.msi` hash. Re-running the job when nothing changed commits nothing to the tap or bucket, but opens another winget pull request, which its reviewers close.
- If tauri-action ever stops writing `-rpm` or `linux-aarch64` entries, the publish check stops the release instead of leaving a platform without updates.

## Amended (v0.19.0): review findings (#217, #229)

- **Rebuilding an older tag.** `gh workflow run release.yml --ref vX.Y.Z -f tag=vX.Y.Z` runs the tag's own workflow and is the documented way (workflow header, AGENTS.md). Run from main, the workflow builds what the checkout knows: the `create-release` job outputs `packaging` (the checkout has `scripts/packaging.mjs`), and without it the build is the pre-ADR-0104 one — the Linux row bundles `deb,appimage` (`legacy-args`), the arm64 row skips every step, no portable zip, no `packages` job — and the publish job requires only `linux-x86_64`, `darwin-x86_64`, `darwin-aarch64`, `windows-x86_64` (`requiredPlatforms("legacy")`). The publish job's script is checked out from the workflow's own commit, so it always matches the workflow file.
- **latest.json is repaired from the assets.** tauri-action's jobs merge `latest.json` one after another and lose entries when they finish together. The publish job runs `node scripts/packaging.mjs latest-json`: every entry is checked (a tagged URL of this release, the right file ending, an existing asset), every signature is taken from the asset's `.sig`, and every key an asset gives but the manifest lacks is rebuilt from that asset and its `.sig` (`updaterKeysOfAsset`: AppImage `amd64`/`aarch64` → `linux-<arch>` and `-appimage`, `.deb` `amd64`/`arm64` → `-deb`, `.rpm` `x86_64`/`aarch64` → `-rpm`, `.app.tar.gz` universal/x64/aarch64 → `darwin-<arch>` and `-app`, `.msi` → `windows-<arch>` and `-msi`; the URL is the tagged download URL tauri-action writes, since a draft's own asset URLs say `untagged-…`). It fails only when a required key has no asset or no `.sig`, and says which. A release with no `latest.json` at all is built from the assets.
- **The portable zip never fails the release.** If `check-unbundled` finds `target/release/sextant.exe` patched, the Windows job warns and makes no zip; the `packages` job then renders every manifest except Scoop's and skips the bucket push. arm64 stays a hard gate.
- **A Scoop copy has its own bundle kind.** Tauri reports no bundle for the unpatched executable; a copy that runs from Scoop's app directory (`…\apps\sextant\<version or current>\`, per-user or global) is `scoop` (`installedBundleKind`, `src/api/updater.ts`): it checks for updates like a `.deb`, never installs one itself, and says "update it with Scoop: scoop update sextant"; About names it "Scoop (portable .zip)". A bare executable elsewhere stays "not installed from a release package". The `.deb` hint names `Sextant_<version>_<amd64|arm64>.deb` from `about_info`'s architecture (a `*` pattern while unknown).
- **winget matches the installed .msi.** The installer manifest carries `AppsAndFeaturesEntries` from `msiIdentity` (`scripts/packaging.mjs`): DisplayName = `productName`; Publisher = the MSI's Manufacturer as Tauri writes it (`bundle.publisher`, else the identifier's second part: `sextant`); UpgradeCode = `{F2B05806-DABF-521C-ADD8-BDA0F7263EB3}`, Tauri's default (UUIDv5 of `Sextant.exe.app.x64` in the DNS namespace, what `tauri inspect wix-upgrade-code` prints), now pinned as `bundle.windows.wix.upgradeCode` so a product rename can never change it. `bundle.publisher` is deliberately not set to "Sextant contributors": it would change the MSI Manufacturer (and the registry key the .msi remembers its install directory under) and the `.deb` Maintainer of existing installs; the package's own `Publisher` in the locale manifest stays "Sextant contributors".
- **Least privilege and a pinned tool.** `packages` runs with `contents: read`, `winget` with `permissions: {}` (their pushes use their own secrets). wingetcreate is the release `v1.12.13.0`, downloaded from its versioned URL and refused unless its SHA-256 is `24042BD3…BD9FFEA` (the checksum Microsoft publishes beside it as `wingetcreate.exe.txt`, equal to GitHub's digest of the asset).
- Tests: `scripts/packaging.test.mjs` (asset → key table, rebuilt and missing entries, legacy set, the CLI, no-zip rendering, `uuidV5` against RFC 4122's example, `msiIdentity`, the winget entries), `src/api/transport.test.ts` (Scoop paths), `src/features/updates/updates.test.tsx` (Scoop hint, arm64 `.deb`), `src/features/about/about.test.tsx`.
