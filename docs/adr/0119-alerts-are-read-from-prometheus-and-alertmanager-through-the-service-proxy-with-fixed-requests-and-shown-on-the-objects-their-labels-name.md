# ADR-0119: Alerts are read from Prometheus and Alertmanager through the service proxy with fixed requests, and shown on the objects their labels name

## Context

#264 asked for the firing and pending alerts of a cluster: from Alertmanager (active, silenced, inhibited) and from Prometheus' own `/api/v1/alerts` (which alone knows pending alerts), shown on the objects they name (namespace, pod, workload, node), on an Alerts page grouped by severity with the silences (read-only), and as an opt-in problems category. URLs and matchers must never come from the window, and only the window has it.

Sources read (2026-10-24): prometheus-community/helm-charts at `0eeacf5` (`charts/kube-prometheus-stack/templates/alertmanager/service.yaml`, `templates/_helpers.tpl` `kube-prometheus-stack.fullname`, `values.yaml` `alertmanager.service.port` 9093 and `routePrefix: /`; `charts/alertmanager/templates/services.yaml`, `_helpers.tpl` `alertmanager.fullname`, `values.yaml` `service.port` 9093), prometheus-operator/kube-prometheus at `f71fb6c` (`manifests/alertmanager-service.yaml`), VictoriaMetrics/operator at `2c0260d` (`api/operator/v1beta1/vmalertmanager_types.go`: `PrefixedName()`, `Port()`), VictoriaMetrics/helm-charts at `5f9a6ac` (`charts/victoria-metrics-k8s-stack/templates/_helpers.tpl`: `vm.single.spec`/`vm.select.spec` set `vmalert.proxyURL` when vmalert is enabled; `values.yaml` alertmanager `port: "9093"`, `routePrefix: /`), VictoriaMetrics/VictoriaMetrics at `3fec2f7` (master) and `cab3d5f` (cluster) (`app/vmselect/main.go`, `lib/vmalertproxy/vmalertproxy.go`, `app/vmalert/web.go`, `app/vmalert/rule/web.go` `ApiAlert`), the Prometheus HTTP API documentation (`/api/v1/alerts`) and Alertmanager's API v2 (`api/v2/openapi.yaml`: `gettableAlert`, `gettableSilence`).

## Decision

- **Core** `crates/sextant-core/src/alerts.rs` (+ `alerts/alertmanager.rs`, `alerts/read.rs`, tests and `alerts/testdata/`), one window command `alerts_list(clusterId)` (`src-tauri/src/commands/alerts.rs`) returning an `AlertsReport`: both sources' states (`off`, `notFound`, `notAvailable`, `ok`, `failed` with the error), the alerts, the silences. The two sources are asked in parallel; a failing source is reported in the answer, only a disconnected cluster is an error. Read-only; MCP agents and extensions get no tool or method (test in the command file), and the `alerts` problem category is in `NEVER_FOR_AGENTS`.
- **The Prometheus-compatible source** is the one of the cluster settings (ADR-0006, ADR-0102: manual, auto-detected or off), through the same client (`metrics::Prometheus`, `get_raw_limited`). Prometheus is asked `api/v1/alerts`. VictoriaMetrics single-node and vmselect answer that path with an empty placeholder unless `-vmalert.proxyURL` is set (`app/vmselect/main.go`), so "no alerts" and "no vmalert" look the same there; for a source known to be VictoriaMetrics (`source_kind`) Sextant asks `vmalert/api/v1/alerts` instead, which they proxy to vmalert (`/vmalert/api/v1/alerts`, the same `ApiAlert` list) and refuse with HTTP 400 without the flag — then the source is `notAvailable` ("VictoriaMetrics gives alerts only through vmalert"). victoria-metrics-k8s-stack sets the flag whenever its vmalert is enabled. A source of unknown kind (a manual address with another path) is asked `api/v1/alerts` and an empty answer is taken as it is.
- **The Alertmanager** is found like Prometheus: in the same 7 namespaces (`metrics::CANDIDATE_NAMESPACES`, one Service list each, in parallel), by name and port, Prometheus' Alertmanagers before VictoriaMetrics', then by namespace, then by rank; the first that answers a probe (`api/v2/alerts` with every filter false, an empty list) through the API server's service proxy wins; the result, "not found" too, is kept a minute per connection.

  | Service | Port | Where it comes from |
  |---|---|---|
  | `alertmanager-operated` | 9093 | prometheus-operator's governing Service of every `Alertmanager` (kube-prometheus, kube-prometheus-stack) |
  | `alertmanager-main` | 9093 | kube-prometheus `manifests/alertmanager-service.yaml` |
  | `…-alertmanager` | 9093, else 80 | kube-prometheus-stack `<fullname>-alertmanager` (fullname = `<release>-kube-prometheus-stack` cut to 26 characters); the `alertmanager` chart's `<release>-alertmanager` (also as the `prometheus` chart's subchart); 80 for the old `prometheus` chart's own Alertmanager |
  | `alertmanager` | 9093 | the `alertmanager` chart when the release name contains the chart's |
  | `vmalertmanager-<name>` | 9093 | VictoriaMetrics operator `VMAlertmanager.PrefixedName()`/`Port()`, as victoria-metrics-k8s-stack creates it |

  A per-cluster setting `clusters[id].alertmanager` (`AlertmanagerMode`: `auto` — the default, also for a value this version cannot read —, `manual` with namespace, Service, port and path prefix, or `off`) overrides it; it is frontend-written, and the core validates a manual address before use (DNS-1123 namespace, DNS-1035 Service, port 1–65535, a path prefix of plain segments, no `..`, query, fragment or escape, ≤ 200 characters). There is no URL form: an Alertmanager is reached only through the service proxy.
- **Fixed requests.** `api/v2/alerts?active=true&silenced=true&inhibited=true&unprocessed=true` and `api/v2/silences`; GET only, under the user's own credentials (`services/proxy` `get`; a 403 says so). Nothing from the window reaches a path, a query or a matcher.
- **Caps and cleaning.** 20 s and 8 MiB per request (a bigger answer is an error, not cut); every element is read on its own (one that does not have the expected shape is skipped); at most 5000 alerts (most severe first, the total is counted, `truncated` said) and 5000 active or pending silences (expired ones only counted); ≤ 64 labels per alert, values ≤ 512 bytes; the summary (`summary`, else `message`), the description, other annotations (≤ 16) and a silence's comment ≤ 2 KB. Every text goes through `clean_text` and every link through `safe_uri`, the Rust twins of `src/resources/uri.ts` (ADR-0115): userinfo, query and fragment are dropped from every URI. An annotation becomes a link (≤ 8) only when its value, cleaned, is `http(s)://host…` and its name ends in `url` (`runbook_url`, `grafana_url`, …) or is `runbook`/`dashboard`/`playbook`, or its value starts with `http`; anything else (`javascript:`) stays plain text. The window shows every text as plain text and opens a link only in the system browser.
- **States and merging.** Alertmanager's `active` and `unprocessed` alerts are firing; a `suppressed` one is silenced when a silence holds it, inhibited when only an inhibition does, and silenced when muted by a time interval. Prometheus' `firing` and `pending` are kept (`inactive` dropped; vmalert's zero `activeAt` reads as none). With an Alertmanager that answered, a firing Prometheus alert is dropped when an Alertmanager alert of the same name carries all its labels (Alertmanager's copy adds the external labels); pending ones always stay. An alert read from Prometheus gets an id hashed from its labels; Alertmanager's keep their fingerprints. Order: severity (critical, error/high, warning/medium, info/low, any other, none or unset), name, state, the oldest first.
- **Objects from labels** (`src/features/alerts/model.ts`), as kube-state-metrics, the kubelet and the kube-prometheus rules label them, in this order — the first set label is the alert's object: `pod`, `deployment`, `statefulset`, `daemonset`, `replicaset`, `job_name` (kube-state-metrics' name for a Job: `job` is Prometheus' scrape job), `cronjob`, `horizontalpodautoscaler`, `persistentvolumeclaim` (each with the alert's `namespace`), `node`, `service` — skipped on kube-state-metrics' alerts (`job` or `service` naming it), where it is the scrape target's Service, not the object's — and otherwise `namespace` alone names the Namespace. A workload's details also list the alerts of its own pods: the pods come from the shared pod watch the right-sizing and cost sections use (`useWorkloadPods`, owners followed through the ReplicaSet), opened only when an alert of the namespace names a pod.
- **Views.** An "Alerts" page in the Cluster section (after Problems): source notes, alerts grouped by severity then name with state, object, age, summary, description, labels and links, filters by severity, namespace, state and text; a read-only "Silences" tab (matchers as Alertmanager writes them, period, author, comment). An "Alerts" details section on Pods, Deployments, StatefulSets, DaemonSets, ReplicaSets, Jobs, CronJobs, HPAs, PVCs, Nodes, Services and Namespaces with the count in its heading; hidden while no source answers. An "Alerts" block in the cluster settings' Metrics tab (the Alertmanager mode and what each source gave). All share one poll per cluster (`store.ts`): every 60 s while a view or the problems source holds it, skipped while the window is hidden and made at once when it shows again, released 5 s after the last user.
- **Problems**: the opt-in category `alerts` (`OPT_IN_CATEGORIES`, a toggle on the Problems page) — every firing `critical` or `warning` alert is a problem of its object, else of its namespace, from its `activeAt`; an alert naming neither is left to the page. Pending, silenced and inhibited alerts never are. Only `critical` ones notify. The source is external (`registerProblemProvider`), held like the other polled categories.

## Why

- Alertmanager alone knows silences and inhibitions; Prometheus alone knows pending alerts. Merging by label subset shows each alert once without needing Prometheus' external labels.
- Probing the documented VictoriaMetrics vmalert path turns an ambiguous empty list into a clear "not available" with what to set.
- A table column of alert counts was rejected: it would poll every cluster whose Pods table is open; the count is in the details section, which polls only while shown.
- Matching objects by fixed label names from the exporters' own conventions keeps the mapping reviewable; guessing workloads from pod names was rejected in favour of the pods' owners where a watch already exists.

## Consequences

- An Alertmanager with another name, namespace or route prefix is set by its Service address; one only reachable by URL (outside the cluster, behind an auth proxy) is not supported.
- Alerts of rules whose labels name objects differently (`kubernetes_pod_name`, `exported_namespace`) appear on the page but on no object.
- A Prometheus that sends to several Alertmanagers shows its firing alerts once from the one Sextant reads; one that sends to none shows them from Prometheus.

## Amendment: scrape-target labels, cleaning everything shown, bounded detection, unique ids (review of #264)

- **The scrape target's labels are not the object.** kube-prometheus-stack scrapes kube-state-metrics with `honorLabels: true` and no relabelling, and prometheus-operator adds the target's `namespace`, `service`, `pod`, `container` and `endpoint`, so `KubeDeploymentReplicasMismatch` carries the kube-state-metrics pod and `KubeNodeNotReady` its namespace too (kube-prometheus drops them, `labeldrop (pod|service|endpoint|namespace)`). On alerts of kube-state-metrics, node-exporter and the kubelet (by `job`, else `service`): `pod` is skipped when it is the scraper's — always for node-exporter; for kube-state-metrics when a workload, HPA, PVC, PV or node label is set, when `container` is the exporter's or when the pod is named after `service`, unless `uid` is set (pod series carry their pod's uid) —; `service` is skipped unless the alert has neither `pod` nor `instance` (TargetDown, aggregated by service, keeps its Service); node-exporter's `namespace` is never the object's, so such an alert names its Node by `node` or by an `instance` without a port (kube-prometheus sets it to the node name) and otherwise nothing. `persistentvolume` names a PersistentVolume (cluster-scoped; PVs get the details section). A workload's "alerts of its own pods" use the same reading (`alertPod`), and so does the problems category. The fixtures `src/features/alerts/fixtures/kube-prometheus-stack.json` are the real label sets of the kube-prometheus mixin rules.
- **Everything shown is cleaned.** Label names and values, alert names, severities, ids, times, annotation names and silence matchers (names and values) go through `clean_text` before clipping, not only the annotations. The URI cleaners of both sides pass one case file, `src/resources/uri-cases.json` (vitest `src/resources/uri.test.ts` and a Rust test in `alerts/tests.rs`): both trim and split at the same explicit set of space characters (Unicode White_Space, U+FEFF and the zero-width spaces — JavaScript's `\s` and Rust's differ on U+0085 and U+FEFF), match schemes in ASCII only, and clean a URI that starts after something else (`‎https://u:p@h`) from its `scheme:/` on.
- **Bounded detection.** The Service lists are capped at 100 per namespace, at most 4 candidates are probed, a found Alertmanager is kept 5 minutes per connection and "not found" 1 minute.
- **Unique ids.** Alerts with the same labels (two rule groups with the same rule) used to share an id; vmalert's `group_id`/`rule_id` now go into the hash, and after merging a repeated id gets `-2`, `-3`, … in the report's order. The window's lists key rows by origin and id, made unique by a counter (`alertKeys`).
