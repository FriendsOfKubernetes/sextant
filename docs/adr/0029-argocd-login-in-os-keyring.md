# ADR-0029: The saved Argo CD login is kept in the OS keyring (`keyring`) in the app

## Context

The Argo CD login can be saved (G04) so as not to enter it again. The data is secret: a password or an API token. The app's settings live in `settings.json` (ADR-0017), and the core does not depend on the OS under ADR-0002.

## Decision

Saving is done by the `keyring` crate (Keychain / Credential Manager / Secret Service) in the `src-tauri` app, not in the core. The entry: service `sextant`, user `argocd:<clusterId>:<namespace>` (the pair of cluster + Argo CD namespace), the value is JSON `{username,password}` or `{token}`. The entry is made by the "Remember" checkbox in the login dialog; "Forget" (`argocd_logout(clusterId, { forget })`) deletes it. Without "Remember" the login lives until the app is closed. The session token is in memory only (`AppState.argocd`). On Linux `keyring` works through libdbus, which `tao` already needs. A saved login is applied automatically (ADR-0028).

## Why

- We write nothing secret into `settings.json` (as the specification says); the option "store it there" was rejected, and a reason other than secrecy is not named in the materials.
- Storage in the core was rejected: the core has no OS dependencies (ADR-0002).
- Other options (an encrypted project file, a password only in memory) are not named in the materials.
- The specification names the key `sextant:argocd:<clusterId>:<namespace>`, whereas the contract and the outcome of task 04 say service `sextant` and user `argocd:<clusterId>:<namespace>`. The second was accepted: it is recorded as built.

## Consequences

- The password itself (`{username,password}`) is stored, not only a session token. A leak from the OS keyring reveals the password, not a short-lived token.
- On Linux a working Secret Service is needed; what happens without it is not described in the materials.
- The storage test runs on a stub backend; the real Keychain, Credential Manager and Secret Service on three OSes were not verified in the materials.
- The entry is tied to `clusterId` and the namespace: another installation or another cluster will require a new login. What happens to the entry of a deleted cluster is not described in the materials.
- A new dependency, `keyring`, in `src-tauri/Cargo.toml`; the build for three OSes must pull it in.

> Amended (v0.6.1): the entry is keyed by the cluster itself — the UID of its `kube-system` Namespace, read once per connection: user `argocd:<namespace>@<kubeSystemUid>`. The same cluster reached through another context or proxy finds the same login, and two clusters behind one API server URL (a Teleport proxy, `kubectl proxy` on 127.0.0.1:8001, a reused local tunnel or kind port) never share one, so a password saved for one is never sent to the other's `argocd-server` (#56). It is never keyed by the URL. When `kube-system` cannot be read (no right to get Namespaces), the user stays `argocd:<clusterId>:<namespace>` — the kubeconfig entry (source path + context), never shared between entries. Old entries are not moved: under a UID key an `argocd:<clusterId>:<namespace>` entry is not read and is deleted the first time the saved login is looked for (the context may have been pointed at another cluster since it was saved; the user signs in once more); under the fallback key it is the same entry and keeps working. Entries `argocd:<namespace>@<apiServerUrl>` written by unreleased builds are deleted the same way. Everything Argo CD has for a cluster — server, port forward, session, typed login, these keys, refusals — belongs to one connection (`ClusterManager::connection`): a reconnect re-reads the kubeconfig and may reach another cluster, so it drops all of it, and a call during which the cluster reconnected sends nothing. The store is read once per entry and app run — the answer (also "none" or an unreadable store) is kept in `ArgoSessions` and updated by "Remember" and "Forget" — so `argocd_status` does not reach the keychain on every call (#60); a change made to the keychain outside Sextant is seen after a restart.

> Amended (v0.7.0): a saved login is bound to the API server it was saved for (#109). The key stays as it is; the value gains `binding: {server, caSha256}` — the server URL of the kubeconfig cluster entry and the SHA-256 of the DER certificates of the certificate authority it trusts (`certificate-authority-data`, else the `certificate-authority` file; `null` when it names none), both taken from the kubeconfig text the current connection was made with (`ClusterManager::server_binding`), not from the file as it is later — e.g. `{"token":"…","binding":{"server":"https://10.0.0.1:6443","caSha256":"9e7d…"}}`. A saved login is offered (tried by itself, reported as saved) only when the current connection's entry gives the same binding; a login bound to another server is kept, not offered (the entry may be pointed back). Without a binding (saved by v0.6.1): under a UID key it is offered and bound when it next signs in successfully; under the fallback key `argocd:<clusterId>:<namespace>` it is deleted unread, because a repointed entry keeps that key while its server changes. When the entry was edited since connecting (its server or CA differs from the connection's), or its server or CA cannot be read, nothing is offered and "Remember" saves nothing and says why, until it reconnects. An entry with no CA (`kubectl proxy`, `insecure-skip-tls-verify`, plain HTTP) binds to the server URL alone: under the fallback key a reused local URL (a tunnel or proxy port now in front of another cluster) is not told apart from the cluster the login was saved for. Older builds read a bound value as the plain login and ignore the binding. This takes back part of the v0.6.1 amendment: the same cluster reached through another context, proxy URL or certificate authority has the same UID key but another binding, so it no longer finds the login saved through the first one and the user signs in again there. Two such contexts of one cluster also share that one UID key with one value: "Remember" in one replaces the other's login and binding, so the other is offered nothing until it signs in with "Remember" again, which in turn replaces the first one's — the last save wins.
