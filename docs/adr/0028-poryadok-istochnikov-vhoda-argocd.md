# ADR-0028: Вход в Argo CD сначала перебирает стандартные источники, окно входа — последнее

## Контекст

Дифф требует входа в API Argo CD (ADR-0027). Пользователь потребовал: перед тем как предлагать ввести логин/пароль или токен, попробовать получить их из стандартных секретов Argo CD (G05). Вход можно сохранить (ADR-0029). SSO через браузер в сборку не входит.

## Решение

Если сессии нет, `argocd_diff` перебирает источники по порядку: (1) сохранённый вход; (2) Secret `argocd-initial-admin-secret`, ключ `password`, пользователь `admin` — если `admin.enabled` в `argocd-cm` не равно `"false"`; (3) Secret с меткой `app.kubernetes.io/part-of=argocd` и ключом `token` — как API-токен. Если ни один не подошёл, команда отвечает ошибкой `unauthorized`, и окно показывает форму входа: логин/пароль или API-токен. В ядре: `standard_credentials(..) -> Vec<Credentials>`, `sign_in(&ArgoClient, Vec<(CredentialSource, Credentials)>)`, `login_options(..) -> LoginOptions { local_users, sso }` (для понятной ошибки у SSO-only сервера). Источник входа — `CredentialSource`: `"secret" | "saved" | "manual"`, виден в `argocd_status`. Пароль и токен из секретов не показываются в окне и не логируются; `SecretString` печатается как `<hidden>`. Отказы запоминаются: `standard_credentials_with_origin(..)` возвращает кандидатов с происхождением `ns/name@resourceVersion`, `is_refusal(&CoreError)` отличает отказ Argo CD от прочих ошибок. Кандидат, отвергнутый Argo CD, не пробуется снова в этой сессии приложения, пока не изменится его источник: `resourceVersion` секрета, новое сохранение или новый ввод. Недоступность сервера не запоминается.

## Почему

- Сразу показывать окно входа отвергнуто требованием пользователя: стандартная установка и так даёт данные.
- `argocd-secret` не годится: в нём только bcrypt-хэш пароля, а не сам пароль.
- Проверка `admin.enabled` нужна, чтобы не пытаться войти в отключённую учётную запись admin; прямо причина в материалах не названа.
- Почему сохранённый вход стоит первым, а не секреты, в материалах не названо.
- SSO через браузер отвергнуто как вне рамок: только логин/пароль и токен.
- Повторять отвергнутого кандидата при каждом запросе отвергнуто: устаревший пароль admin копил неудачные попытки входа и мог заблокировать admin в Argo CD. Запоминание привязано к `resourceVersion`, поэтому исправленный секрет пробуется заново сразу.
- Запоминать и недоступность сервера отвергнуто: это не отказ учётных данных, и после восстановления связи тот же кандидат должен подойти.

## Последствия

- Значение `argocd-initial-admin-secret` читает ядро и не отдаёт окну. Это второй путь чтения значения Secret рядом с `secret_value` (ADR-0014); как именно он читает, в материалах не описано. Назначение ADR-0014 — чтобы значение не попало в окно — сохраняется.
- Если администратор отключил `admin` или удалил секрет, остаются сохранённый вход, токен-секрет и окно.
- Источник (3) — любой Secret с этой меткой и ключом `token`; как выбирается среди нескольких, в материалах не описано (функция отдаёт список).
- На SSO-only сервере без локальных пользователей вход невозможен совсем; ошибка говорит об этом словами (история 13).
- Память об отказах живёт до закрытия приложения и снимается только сменой источника кандидата. Пароль, исправленный в самом Argo CD при неизменном секрете в кластере, не будет пробован до перезапуска Sextant, новой записи или ввода. Для истёкшего токена остаётся сценарий «повторный вход по сохранённому»; флаг `expired` есть в `argocd_status`.
- Пока сессия в памяти есть, источники не перебираются.
