# ADR-0102: VictoriaMetrics is found like Prometheus and answers the same fixed queries, after every Prometheus

## Context

Everything Sextant reads from Prometheus — usage charts and current values (ADR-0006), right-sizing history (ADR-0070), the volume usage fallback (ADR-0086), workload request metrics (ADR-0095) and the traffic graph (ADR-0096) — goes through one client (`metrics/prometheus.rs`) to the Prometheus HTTP API, through the API server's service proxy or a URL. Many clusters keep their metrics in VictoriaMetrics instead, which serves the same HTTP API (single-node at the root, a cluster's vmselect under `/select/<tenant>/prometheus`) with its own query language, MetricsQL. #226 asked for VictoriaMetrics to be found automatically and for every fixed query to be checked against a real one.

## Decision

- **One client, one set of queries.** VictoriaMetrics is a `PrometheusTarget` like any other: a Service with a port and a path prefix, or a URL. No query is written twice; the queries were run against VictoriaMetrics v1.154.0 single-node and cluster in the kind test cluster and none needed a change (below). In the window everything that means "any such source" says "Prometheus-compatible source".
- **Known names** (`known` in `metrics/prometheus.rs`), from the projects' own sources (VictoriaMetrics/helm-charts at `1f2e273`, VictoriaMetrics/operator at `d847128`, 2026-10-20):

  | Name | Port | Path prefix | Where it comes from |
  |---|---|---|---|
  | `vmsingle-<name>` | 8429, else 8428 | — | operator: `VMSingle.PrefixedName()` (`api/operator/v1beta1/vmsingle_types.go`), default port 8429 (`internal/config/config.go`, `VMSingle.Port`) with a second Service port 8428 added when the port is not 8428 (`factory/vmsingle/vmsingle.go`, "http-alias"); victoria-metrics-k8s-stack creates the VMSingle named after its fullname (`vm.cr.fullname`), e.g. `vmsingle-vmks-victoria-metrics-k8s-stack`; victoria-metrics-single with `useLegacyNaming: false` names its Service `vmsingle-<release>` (`vm.plain.fullname` with `kindOverride: vmsingle`) |
  | `…victoria-metrics-single…-server` | 8428 | — | victoria-metrics-single's default naming: `<release>-victoria-metrics-single-server`, or `<release>-server` when the release name contains the chart name (`vm.fullname` + the `server` app key; port from `-httpListenAddr`, default 8428, `templates/service.yaml`) |
  | `vmselect-<name>` | 8481 | `/select/0/prometheus` | operator: `ClusterPrefixedName` (`vmextra_types.go`) for a VMCluster's select, default port 8481 (`VMCluster.AsURL`); victoria-metrics-k8s-stack's VMCluster; victoria-metrics-cluster with `useLegacyNaming: false`. `vmselectinternal-<name>` (the operator's headless Service) does not match |
  | `<name>-vmselect` | 8481 | `/select/0/prometheus` | victoria-metrics-cluster's default naming `<release>-victoria-metrics-cluster-vmselect` (`templates/service.yaml`, `vm.plain.fullname` with the `vmselect` app key; port 8481 from `-httpListenAddr`), the operator's `useLegacyNaming: true` (`ClusterSuffixedName`) |

  The k8s-stack chart itself reads `/select/<tenant>/prometheus` with tenant 0 by default (`vm.prometheus.read` in its `_helpers.tpl`); detection uses tenant 0. vmagent (`vmagent-*`), vminsert, vmalert and vmauth are not matched: the first three have no query API, and vmauth's routing is the user's configuration (a request may go anywhere, under any path), so a vmauth in front of VictoriaMetrics is set as a manual address.
- **Namespaces**: `victoria-metrics` and `vm` are added to the searched list (`-n vm` is the namespace of 57 install commands in the charts' and the operator's READMEs and docs, more than any other), now 7 namespaces, one Service list each, in parallel as before. `victoria-metrics-k8s-stack` was not added: none of the projects' documentation installs into it.
- **Order: every Prometheus first.** Candidates sort by (VictoriaMetrics after Prometheus, namespace order, rank); the first that answers is used. A cluster that has both keeps the Prometheus it had before this change, whatever namespace either lives in, so no existing user sees another source appear. Within VictoriaMetrics single-node ranks before vmselect in one namespace. Choosing "the one with the data" was rejected: it would need queries against every candidate on every detection, and the answer could flip between them.
- **Probe.** `api/v1/status/buildinfo` answers on Prometheus and on VictoriaMetrics from v1.77.0 on (CHANGELOG_2022: "add a handler for `/api/v1/status/buildinfo`"), on single-node at the root and on vmselect under its tenant path — checked on v1.154.0; vmselect without the prefix answers 400, so a wrong prefix is not taken. When buildinfo is refused the way an older VictoriaMetrics refuses it (HTTP 400, or an answer that is not the Prometheus API), the probe asks `api/v1/query?query=vector(1)` once; a missing Service (the API server's 404), a refusal (401/403) or no answer (timeout, 502–504) is not asked again, so a probe of an absent linkerd-viz stays one request.
- **What the window shows.** `MetricsStatus.prometheusKind` (optional, `MetricsSourceKind`: `prometheus`, `victoriaMetricsSingle`, `victoriaMetricsCluster`) says what the source in use is, by the same names, else by a `/select/<tenant>/prometheus` path; absent means "a Prometheus-compatible API". Saved settings are unchanged (`PrometheusTarget` has no new field). The manual address offers presets — Prometheus (9090; a saved port 80, `prometheus-server`, also reads as Prometheus), VictoriaMetrics single-node (8428: the chart's port, and the operator's alias), VictoriaMetrics cluster (8481, `/select/<tenant>/prometheus` with an editable tenant, `accountID` or `accountID:projectID`) — that fill the port and path prefix; the kind is judged again when the address or prefix field is left (not on every keystroke) and on saving; under the cluster kind a prefix that is not `/select/<tenant>/prometheus` with a valid tenant is refused, and "Other" takes any prefix.
- **MetricsQL differences, checked** (`crates/sextant-core/tests/victoria_metrics.rs` against `up --prometheus --victoria-metrics`; vmagent scrapes the Prometheus fixture's targets into both VictoriaMetrics flavours):
  - *`rate` without extrapolation*: VictoriaMetrics divides by the time from the sample before the window to the last one, Prometheus extrapolates to the window's edges. Over the same chart points the CPU series differed by a median of 2–8 % (single points up to 85 % where a window holds the first samples), memory, pods and disk by 0–2 %.
  - *`-search.latencyOffset` (30 s)*: an instant query "now" is answered as of 30 s earlier, and the last 30 s of a range may be incomplete. Current CPU (a 2-minute rate) then covers another window: a median of 9–20 % apart per pod in the measurements, memory 0.3 %. Right-sizing's `time=` queries are moved the same way, which changes nothing at its 5-minute and 10-minute steps. Sextant does not send `latency_offset` (VictoriaMetrics' reason is data not yet complete) and documents the shift instead.
  - *`timestamp()`*: VictoriaMetrics gives the time of the evaluation step, Prometheus the raw sample's. Right-sizing's "first seen" is a 10-minute subquery step either way (measured 5–10 s apart); a container younger than one step plus 30 s has no "first seen" yet on VictoriaMetrics.
  - *Query length*: `-search.maxQueryLen` is 16 KiB by default; Sextant's longest query is ≤ 5 KiB (ADR-0096).
  - *Request and traffic queries* (`or on`, `unless on`, `label_replace`, `histogram_quantile`, `topk`, `and on`): the synthetic series of the request and traffic fixtures, imported into an empty VictoriaMetrics, give exactly the answers the real Prometheus recorded — 42 queries, 68 series, values within 1e-6. Against the cluster's live data every request and traffic query (144 per flavour) is accepted.
  - *Volume stats and history*: the same claims and values (≤ 0.5 % apart, the disk moved between the reads); the history's memory peaks 0–1.3 % apart, CPU p95 a median of 5–9 % (two runs).

## Why

- Prometheus first keeps the answer stable for every cluster that works today; VictoriaMetrics only adds an answer where there was none.
- Names from the charts' and the operator's templates are what a default install creates; anything else is one manual address away, which now has the right port and path at a click.
- One query set kept the checks honest: a separate MetricsQL dialect would have doubled every fixture and every bound.

## Consequences

- A VictoriaMetrics installed with other names (the operator's `useLegacyNaming: true` VMSingle is named exactly as the object), behind vmauth, or in another namespace is set manually; the presets fill the port and path.
- Values from VictoriaMetrics differ from Prometheus' within the bounds above; the views label nothing differently. A recommendation can move by the CPU difference.
- The test cluster's `up --victoria-metrics` adds vmagent, a single-node VictoriaMetrics with its data on a `local` claim (so the kubelet reports its volume stats), a cluster (vmstorage, vminsert, vmselect) and the empty `vm-replay`; `tests/victoria_metrics.rs` compares every family with the Prometheus fixture and auto-detection as a ServiceAccount that sees only the `victoria-metrics` namespace.
