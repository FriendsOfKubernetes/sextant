# ADR-0116: Dynamic Resource Allocation and NVIDIA GPU Operator views read every API shape by its fields, never evaluate CEL, and find components by their manifest names

## Context

#244 asks for Dynamic Resource Allocation (`resource.k8s.io`: DeviceClass, ResourceClaim, ResourceClaimTemplate, ResourceSlice) — which pods use which claims, what was allocated where, and why a pod waits for a claim. #245 asks for the NVIDIA GPU Operator (`nvidia.com` ClusterPolicy and NVIDIADriver): overall state, each component rolled out or not, the MIG strategy and node MIG labels, and GPU capacity per node. Both are read-only CRD projects like ADR-0097, 0100, 0101, 0111 and 0113.

`resource.k8s.io` has had four shapes in two years (kubernetes/kubernetes `staging/src/k8s.io/api/resource/<version>/types.go`): v1alpha3 (1.31) and v1beta1 (1.32) put a request's class, selectors and count on the request and a slice device's fields under `basic`, with a capacity that is a quantity in v1alpha3 and `{value}` in v1beta1; v1beta2 (1.33) and v1 (1.34) put a request under `exactly` (or a `firstAvailable` list) and the device's fields on the device. A cluster serves the version it serves.

## Decision

- **Two discovered sidebar sections**: `dra` ("Dynamic Resource Allocation": Resource Claims, Claim Templates, Device Classes, Resource Slices and the "Devices" page) and `gpuOperator` ("NVIDIA GPU Operator": Cluster Policies, NVIDIA Drivers and the "GPU nodes" page), shown only while the cluster serves their kinds. Kinds are registered at v1 (DRA) and v1/v1alpha1 (NVIDIA); the core resolves to the version discovery serves (`resolve_kind`), and hooks ask discovery for the served version before reading.
- **Every DRA object is read by the fields it has, never by its apiVersion** (`dra/model.ts`): `exactly` or the request itself, `firstAvailable` as ordered choices, `basic` or the device, a capacity as a quantity or `{value}`, the pod's `resourceClaims[].resourceClaimName|resourceClaimTemplateName` (and the 1.26–1.30 `source`), `status.resourceClaimStatuses` for a template's claim (an entry without a name: none was needed).
- **CEL is never evaluated.** Device class and request selectors are shown as written, with a note; Sextant does not say which devices match a selector. Driver configuration (`opaque.parameters`) is shown as JSON text.
- **A claim's state** is `pending` (no `status.allocation`), `allocated`, `inUse` (`status.reservedFor` non-empty), `bindingFailed` (a `bindingFailureConditions` condition True on the device's `status.devices[]` entry, as the API defines it) or `deleting`. The node of an allocation is named only when its node selector is exactly `matchFields metadata.name In [node]`; any other selector is shown as text.
- **Why a pod waits** comes from the scheduler's own words: its PodScheduled condition, parsed with the autoscaling feature's `isUnscheduled`/`schedulingCondition`, and DRA reasons recognised by the dynamicresources plugin's and `resourceclaim` package's messages ("cannot allocate all claims", "ResourceClaim not created yet", "device class … does not exist", "resourceclaim in use", …). Events are not watched.
- **Devices per node from slices, bounded**: a node's details read its slices by `spec.nodeName=<node>` on the API server; the "Devices" page reads every slice, at most 500 (`MAX_SLICES`); which claim holds a device comes from one cluster-wide claim list (≤ 5000), opened only while such a view shows devices. A capped or unreadable claim list makes the "allocated to" column "cannot tell", never "free".
- **Problems `dra`, on by default**: a pod Pending and unscheduled with claims, of which one is not allocated, missing, or not made yet, counted 5 minutes (`LONG_GRACE_MS`) after its PodScheduled change; notified once per owning controller. One provider (`external` source on ResourceClaim, held only where served) watches the cluster's Pending pods (`status.phase=Pending` field selector, ≤ 2000) and the claims of only the namespaces where such a pod waits (≤ 40 namespaces, ≤ 5000). Where the claims are not read in full, a pod counts only when the scheduler names a DRA reason.
- **GPU Operator components by the operator's manifest names** (`assets/state-*/…daemonset.yaml`: `nvidia-driver-daemonset`, `nvidia-container-toolkit-daemonset`, `nvidia-device-plugin-daemonset`, `nvidia-dcgm`, `nvidia-dcgm-exporter`, `gpu-feature-discovery`, `nvidia-mig-manager`, `nvidia-node-status-exporter`, `nvidia-operator-validator`, and the sandbox ones) in the ClusterPolicy's `status.namespace`; the driver's name is matched by prefix because `transformPrecompiledDriverDaemonset` and the OpenShift transform add kernel/OS suffixes. Enabled as each spec's `IsEnabled()` decides (`api/nvidia/v1/clusterpolicy_types.go`: driver, toolkit, device plugin, DCGM, DCGM exporter, GFD, MIG manager on by default; node status exporter and the sandbox components off; the validator always). With `driver.useNvidiaDriverCRD` the driver row points to NVIDIADriver, whose DaemonSets are found by owner reference (their names carry an OS tag and a hash, `internal/state/driver.go`). An unset MIG strategy is shown as "not set" (the device plugin and GFD then decide, default none — `applyMIGConfiguration`).
- **GPU nodes** are the nodes labelled `nvidia.com/gpu.present=true` (≤ 500), with `nvidia.com/gpu.product`, `gpu.count`, `gpu.memory`, `mig.config`, `mig.config.state` and the `nvidia.com/gpu` and `nvidia.com/mig-*` capacity/allocatable from the node status. A node's "GPU" details block reads the node object alone (no watch).
- **Problems `gpuOperator`, on by default**: a ClusterPolicy or NVIDIADriver in state `notReady` 10 minutes after its Ready condition changed; an enabled component's DaemonSet (or one an NVIDIADriver owns) with pods not ready or not updated, 10 minutes after its counts last moved; a node whose `nvidia.com/mig.config.state` is `failed`, after 2 minutes. One provider watches ClusterPolicies and NVIDIADrivers (cluster-scoped, few), the DaemonSets of their operand namespaces (≤ 4 namespaces, ≤ 1000) and the nodes with the failed label (label selector on the API server).
- Both categories are in `NEVER_FOR_AGENTS`; no new command; the kinds offer the generic Edit and Delete only; agents and extensions get nothing new.

## Why

- Reading by fields rather than by version keeps one model for four API versions and survives a cluster upgrading between them while Sextant is open; the API server converts objects to the requested version, so mixed shapes only meet in fixtures and in tests — which is where they are checked.
- Not evaluating CEL: the DRA CEL environment (device attributes, capacity quantities, `compareTo`, semver) is the scheduler's; a second evaluator in the window would disagree with it in exactly the cases a user is debugging. The scheduler's own message is the answer to "why does it not fit".
- On by default for both: the DRA provider's lists are proportional to what waits (Pending pods, their namespaces' claims), and the GPU provider's to the operator's own few objects and one namespace; neither lists every pod, claim or node of the cluster.
- Matching DaemonSets by manifest name (and by owner for NVIDIADriver) rather than by labels: the names are what the operator creates from its assets in every install method (Helm and OLM run the same operator), while the operands' labels are not documented as an interface.

## Consequences

- A claim allocated on several nodes (network-attached devices) shows its node selector as text, not as nodes.
- Device classes' selectors are not matched against slices: the "Devices" page shows what drivers publish and what claims hold, not what a request could get.
- A GPU Operator installed with a custom DaemonSet name prefix is shown as "not deployed yet" for that component.
- Tests: `src/features/dra/dra.test.tsx` and `src/features/gpu-operator/gpuoperator.test.tsx` (models over every shape, providers, sidebar presence and absence, columns, details, pages, axe); fixtures `src/features/dra/fixtures/objects.json` (v1, v1beta1, v1alpha3) and `src/features/gpu-operator/fixtures/objects.json`; `dra_and_gpu_operator_problems_are_never_given_to_agents` in `src-tauri/src/mcp/tools_diagnose/tests.rs`.
