# ADR-0095: Workload request metrics come from the sources found in Prometheus, through fixed queries per source

## Context

#212 asked for request-level health beside a workload's CPU/memory charts: request rate, error rate (HTTP 5xx, gRPC errors) and latency p50/p95/p99, plus CPU throttling per container with a hint when the CPU limit is the cause. It also takes over the Linkerd golden metrics that #155 left out (ADR-0089). Kubernetes itself has no request metrics; they come from whatever sits in the request path and exports Prometheus metrics — a mesh proxy, an ingress controller, an eBPF agent — and every one of them names the workload with different labels. The live traffic graph (#211) needs the same sources.

## Decision

- **Sources are found by metric name, per connection.** `metrics::requests::request_sources` asks the Prometheus of the cluster settings (manual or auto-detected, ADR-0006) one `GET api/v1/label/__name__/values` with `match[]={__name__=~"<the 12 known names>"}` over the last hour, keeps only those names from the answer (an old Prometheus that ignores `match[]` sends everything; the rest is dropped) and derives the sources (`RequestSourceKind::required_metrics`, `latency_metrics`). When that Prometheus has no Linkerd metrics, linkerd-viz's own Prometheus (`linkerd-viz/prometheus:9090`, through the API server's service proxy like every Prometheus) is probed and asked the same way. The result is kept per cluster for 5 minutes (`REQUEST_SOURCES_TTL`) and only for the same connection (`ClusterManager::connection`) and the same Prometheus settings; one entry per cluster. A failed lookup is not kept; Prometheus "off" asks nothing at all.
- **The sources, what names the workload, and what an error is.**

  | Source | Detected by | Workload (Deployment/StatefulSet/DaemonSet) | Pod | Error | Latency |
  |---|---|---|---|---|---|
  | Istio | `istio_requests_total` | `reporter="destination"`, `destination_workload_namespace`, `destination_workload` (set by the receiving proxy) | `reporter="destination"`, `destination_workload_namespace`, `pod` (the scrape target's label) | `response_code=~"5.."`, or a non-OK `grpc_response_status` on a non-5xx response | `istio_request_duration_milliseconds_bucket` |
  | Linkerd | `response_total` **and** `response_latency_ms_bucket` (the pair; `response_total` alone is too common) | `direction="inbound"`, `namespace`, `pod=~` the controller's pod names | `direction="inbound"`, `namespace`, `pod` | `classification="failure"` — Linkerd's own verdict (5xx, non-OK gRPC status, no response) | `response_latency_ms_bucket` |
  | ingress-nginx | `nginx_ingress_controller_requests` | `namespace` + `service=~` the Services selecting the pods, or `exported_namespace` + `exported_service` when the scrape kept its own labels (ServiceMonitor without `honorLabels`) — the first that has series | same | `status=~"5.."` | `nginx_ingress_controller_request_duration_seconds_bucket` |
  | Grafana Beyla | `http_server_request_duration_seconds_count` or `rpc_server_duration_seconds_count` | `k8s_namespace_name`, `k8s_pod_name=~` the controller's pod names | `k8s_namespace_name`, `k8s_pod_name` | `http_response_status_code=~"5.."` (HTTP series), `rpc_grpc_status_code` not `0` (RPC series) | both `_bucket` histograms, summed by `le` |
  | Cilium Hubble | `hubble_http_requests_total` | `reporter!="client"`, `destination_namespace`, `destination_workload` | `reporter!="client"`, `destination_namespace`, `destination_pod` | `status=~"5.."` | `hubble_http_request_duration_seconds_bucket` |

  "The controller's pod names" is the anchored pattern right-sizing uses (`pod_name_pattern`, ADR-0070): `<name>-<hash>-<5>`, `<name>-<ordinal>`, `<name>-<5>` over Kubernetes' safe alphabet, so `web` never counts `web-api`. Hubble needs `labelsContext` with these labels (otherwise it has no series of the workload: "no data", not an error). Anything exporting the OpenTelemetry HTTP/RPC server metrics with Beyla's Kubernetes labels counts as Beyla. Ingress numbers are only the requests that came through the ingress — the section says so.
- **Fixed queries.** Per source, one instant query (evaluated at a fixed time, `timeout=18s`, client 20 s) returns every current value tagged by `label_replace` (`m` = `rate`, `errors`, `p50`, `p95`, `p99`; rates over 5 minutes, quantiles by `histogram_quantile` over `sum by (le)`), and one range query the last hour (`rate`, `errors`; step 60 s, ≤ 61 points per series). Error rate = errors ÷ requests, only when there were requests; a NaN quantile is "unknown", never 0; a source without series of the target over the hour is left out (`golden` lists only sources with data, `sources` lists every source found). CPU throttling is `increase(container_cpu_cfs_throttled_periods_total) ÷ increase(container_cpu_cfs_periods_total)` over the last hour per container, over the right-sizing scope selector (≤ 50 containers). ingress-nginx's Services are read in the core: the pod's labels (a workload's pod template labels) against the namespace's Service selectors, one GET and one list under `STEP_TIMEOUT`, ≤ 20 names, only when ingress-nginx was detected.
- **Nothing from the window becomes PromQL.** `metrics_request_health` takes a `RequestTarget` (`workload` with namespace, kind and name, or `pod`), read strictly (an unknown field — a query, a selector — is an error), validated (`validate_target`: DNS-1123 names, kind among Deployment/StatefulSet/DaemonSet) before anything is asked, and escaped again when written into a query. The window builds the target from the details' own object reference.
- **Read-only, window only.** The command changes nothing and needs only `services/proxy` on the Prometheus Services (and get/list on the workload and Services for ingress-nginx); MCP agents and extensions get no tool or method (test in `src-tauri/src/commands/metrics.rs`). The "Requests" details section (`src/features/request-health/`) polls once a minute through the metrics feature's shared pollers, only while it is shown. The CPU-limit hint appears when a container with a CPU limit is throttled in ≥ 25 % of periods (right-sizing's `THROTTLED_SHARE`) and names right-sizing's recommended CPU limit when its history gives one (sharing its pollers and pod watch). Without Prometheus, or without any source, the section says which sources would provide the data; Sextant installs and enables nothing.

## Why

- Asking for the 12 names by `match[]` is one small request per connection; listing all metric names or counting series would grow with the cluster.
- One label-tagged instant query per source keeps the number of requests per poll at 2 per source + 1, instead of 6.
- Workload labels set by the proxy itself (Istio, Hubble) are independent of how Prometheus scrapes; where a source only has pod labels, the controller-made pod names keep similarly named workloads apart, as right-sizing does.
- Reading Services in the core keeps the command's input to names; passing Service names from the window would be another place where text reaches a query.

## Consequences

- #211 reuses `request_sources`, `RequestSourceKind`, `RequestVia`, `linkerd_viz_target` and the per-source selectors (`metrics::prometheus::requests::request_selectors`, `shape`) and adds edge queries of its own.
- A scrape configuration that renames `pod`/`namespace` (e.g. `kubernetes_pod_name`) gives "no data for these pods" for the sources matched by pod; the label names are fixed by this ADR.
- Older Beyla releases that label `http_status_code` instead of `http_response_status_code` show no errors; Linkerd's newer metrics (if a future proxy drops `response_total`) need a new row here.
