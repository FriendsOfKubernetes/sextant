# ADR-0016: Свои повторы клиента (до 3 раз, до 5 с) и таймаут 30 с на изменения

## Контекст

Клиент kube по умолчанию повторял ответы 429/503/504 до 15 раз с backoff до 1000 с и учётом `Retry-After`; чтение без таймаута. На перегруженном API действие висело до ~5 минут, а внешний предел был только у проверки подключения (20 с).

## Решение

В клиенте подключения `default_retry = false`, вместо него — стек kube с `BufferLayer` и `RetryLayer` с политикой `cluster::RetryPolicy`: не более 3 повторов и не более 5 с суммарного ожидания, повторяются только запросы с клонируемым телом. `tower` и `http` — прямые зависимости `sextant-core` (в `Cargo.lock` они уже были через kube-client). Изменения (scale, restart, cordon, trigger, suspend, `resource_replace`, `resource_delete`) в командах обёрнуты `error::with_timeout` на 30 с (`commands::actions::CHANGE_TIMEOUT`); просрочка даёт новый код `timeout`. Клиент эвикций строится отдельно, без повторов и с тем же `CONNECT_TIMEOUT`. Многошаговые операции (drain, multi-doc apply) ограничены иначе — ADR-0023.

## Почему

- Встроенный `server_retry` оставить нельзя: 15 повторов с backoff и `Retry-After` — это и есть минуты ожидания. Нужен предел по суммарному времени, а то, можно ли задать его настройкой самого `server_retry`, в материалах не проверялось.
- Совсем без повторов отвергнуто: короткие 429/503/504 на живом кластере остаются, и пользователь не должен видеть ошибку на каждую такую секундную перегрузку.
- Таймаут поставлен на уровне команд действий, а не в клиенте, — так записано в решении; причина прямо не названа. Очевидное следствие: общий таймаут клиента оборвал бы и долгоживущие watch, логи и exec.

## Последствия

- `timeout` — ещё один код в закрытом наборе из ADR-0008; интерфейс выбирает для него формулировку из `errors:timeout`.
- Таймаут не отменяет запрос на сервере: к моменту ошибки изменение могло уже примениться.
- Запросы с некопируемым телом идут без повторов вовсе. Обрыв watch по-прежнему обрабатывает его собственное переподключение (ADR-0004).
- Старые подписки при переподключении кластера держат прежний клиент, поэтому политика повторов меняется для них только с новой подпиской.
- Третий построитель клиента — Prometheus по URL (`core/metrics/prometheus.rs`) — со своими таймаутами и этим решением не затронут.
