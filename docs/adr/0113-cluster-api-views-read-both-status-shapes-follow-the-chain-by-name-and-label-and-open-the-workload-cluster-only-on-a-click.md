# ADR-0113: Cluster API views read both status shapes, follow the chain by name and label, and open the workload cluster only on a click

## Context

#243 asked for Cluster API in the style of the other CRD projects (ADR-0097, 0100, 0101): Cluster, ClusterClass, MachineDeployment, MachineSet, Machine, MachineHealthCheck, KubeadmControlPlane and the provider objects they reference; phases and conditions; the chain Cluster → control plane / MachineDeployments → Machines → infrastructure machines → Nodes of the workload cluster when it is also a configured cluster; failed and unhealthy Machines as problems.

Cluster API changed its status in v1beta2 (Cluster API 1.11, proposal `20240916-improve-status-in-CAPI-resources.md`): new conditions (Available, Ready, UpToDate, RollingOut, ScalingUp, Remediating, Paused, …) as `metav1.Condition`s in `status.conditions`, counts by the new meaning (`readyReplicas` — Machines whose Ready condition is True; `upToDateReplicas`; `availableReplicas`), the old conditions and `failureReason`/`failureMessage` moved under `status.deprecated.v1beta1`, and the Failed phases deprecated (never set by the controllers any more). A v1beta1 object keeps the old conditions (with a severity) and failure fields on `status` and, since 1.9, mirrors the new ones under `status.v1beta2`. Discovery hands Sextant one version per kind, the preferred one, so either shape can arrive depending on the installed Cluster API. References are `{apiGroup, kind, name}` in v1beta2 (the version comes from the contract labels of the CRD) and `ObjectReference`s in v1beta1.

## Decision

- **Read-only, frontend only** (`src/features/cluster-api/`): a discovered sidebar section `clusterApi` ("Cluster API") with Clusters, ClusterClasses, KubeadmControlPlanes (`controlplane.cluster.x-k8s.io`), MachineDeployments, MachineSets, Machines, MachineHealthChecks and ClusterResourceSets (`addons.cluster.x-k8s.io`), each listed only where discovery serves it. No Rust command was added, nothing is written; the kinds offer the generic Edit and Delete under their usual confirmations. Strings are the namespace `clusterapi`.
- **Both shapes in one model** (`model.ts`): the new conditions are read from `status.conditions` of a v1beta2 object or `status.v1beta2.conditions` of an older one; when an object has none (Cluster API before 1.9), the old conditions stand in (Cluster's Available ← old Ready). Failure fields are read from `status` (v1beta1) or `status.deprecated.v1beta1`. Counts prefer the new meaning and fall back to the old `readyReplicas`/`updatedReplicas` only when no new count exists. The status column says, from the object's own phase and conditions: a Cluster Available / Provisioned / Provisioning / Not available / Failed / Deleting / Paused (`spec.paused`, the `cluster.x-k8s.io/paused` annotation or the Paused condition); a Machine Running / Not ready / Provisioning (Pending, Provisioning, Provisioned) / Updating / Deleting / Failed; MachineDeployments, MachineSets and KubeadmControlPlanes Available / Rolling out / Scaling / Not available / Provisioning (a control plane not initialized); a MachineHealthCheck Healthy / Remediating / Remediation blocked. The tooltip is the phase and the first failing condition's message.
- **The chain, bounded.** A Cluster's details read its `controlPlaneRef` and `infrastructureRef` by name (`resource_get`), and list its MachineDeployments, MachineSets and Machines by the label `cluster.x-k8s.io/cluster-name=<name>` in its own namespace — three label-selected watches through the shared registry, only of served kinds, closed with the details. The tree (`chain.ts`) groups Machines under the control plane (the `cluster.x-k8s.io/control-plane` label), under their MachineSet by controller owner, and MachineSets under their MachineDeployment; at most 50 Machines are drawn, the rest counted. A Machine's details read its Cluster, bootstrap config and infrastructure machine by name (three reads). MachineDeployments, MachineSets and control planes list their Machines by the selector their controller uses (`status.selector`, else `spec.selector`). Every reader reads at most 50 objects, 4 at a time, again only when the object shown changes, and never asks for a kind discovery does not serve.
- **Provider objects are read generically**: kind, name, and whether they are done by the contract — `status.initialization.provisioned` / `dataSecretCreated` (v1beta2 contract), `status.ready` (v1beta1 contract), else their Ready condition — plus a terminal `failureMessage`. A few fields are shown for DockerMachine/DockerCluster (CAPD), AWSMachine, AzureMachine and VSphereMachine; any other provider is shown by readiness alone.
- **The workload cluster opens only on a click.** A configured Sextant cluster whose kubeconfig server URL has the same host and port as the Cluster's `spec.controlPlaneEndpoint` (443 when the URL names none, IPv6 brackets ignored) gets a button: "Open cluster …" on the Cluster, "Open Node … in …" on a Machine with a `nodeRef`. The cluster list is the clusters store's; a disconnected cluster is connected by that click, never before. An endpoint reached through a rewritten address (a port mapped to 127.0.0.1, a proxy) is not recognised, and the details say no cluster matches.
- **Problems** (category `clusterApi`, on by default, riding the problems store one watch per kind): Clusters, KubeadmControlPlanes and MachineHealthChecks uncapped, Machines capped at `MAX_SOURCE_OBJECTS` (5000). `Failed`: a terminal failure (`failureReason`/`failureMessage`) or the Failed phase, at once. `NotAvailable`: a Cluster or control plane whose Available condition (old Ready) is False, after 5 minutes, or 30 while the Cluster is still Pending/Provisioning or the control plane not initialized. `ProvisioningStuck`: a Machine Pending, Provisioning or Provisioned 30 minutes after `status.lastUpdated` (when its phase last changed), with the message of its first unmet condition (BootstrapConfigReady, InfrastructureReady, NodeReady, …). `RemediationBlocked`: a MachineHealthCheck whose RemediationAllowed condition is False (reason TooManyUnhealthy: more Machines unhealthy than `unhealthyLessThanOrEqualTo` / `maxUnhealthy` allows), after 2 minutes. Deleting and paused objects have none. The section counter counts the same problems.
- **Agents get nothing new**: `clusterApi` is in `NEVER_FOR_AGENTS` (`src-tauri/src/mcp/diagnose_answers.rs`, with a test); no MCP tool or extension method was added.

## Why

- Reading the controllers' own conditions keeps Sextant's verdict equal to `clusterctl describe cluster`'s and survives provider differences; re-deriving health from provider objects would need provider knowledge Sextant does not have.
- Both shapes are in use: Cluster API 1.9–1.10 installations serve v1beta1 with `status.v1beta2`, older ones only v1beta1, newer ones v1beta2.
- The chain needs objects of one namespace only (Cluster API keeps a Cluster's objects in its namespace); label selection on the API server keeps the lists to one Cluster's objects.
- Connecting a cluster opens a connection with the user's credentials; doing it because a details panel was opened would surprise the user and cost a connection for nothing.
- The problems ride per-kind watches with a cap, the way CloudNativePG's and Strimzi's do: Machines are what a Cluster API user watches, and a failed or stuck one is an incident, so the category is on by default.

## Consequences

- A management cluster with more than 5000 Machines has its Machine problems truncated (the source says so).
- MachinePools are not a sidebar kind; their Machines appear in a Cluster's chain under "Other Machines".
- A provider's own failure (a cloud quota, say) shows through the Machine's conditions and the infrastructure object's readiness and `failureMessage`; Sextant does not explain provider-specific statuses beyond the few fields above.
- A Machine stuck in Provisioned (infrastructure ready, no Node) counts as stuck after 30 minutes, which may be earlier than a MachineHealthCheck's `nodeStartupTimeout` would remediate it.

## Amended after review (#243)

- **A Cluster is "settled" for `NotAvailable` (the 5-minute grace) only past the provisioning phases and once its control plane is initialized**, when the Cluster says: v1beta2 `status.initialization.controlPlaneInitialized` (cluster-api `api/core/v1beta2/cluster_types.go`, `ClusterInitializationStatus`), else the `ControlPlaneInitialized` condition, new or old (`ClusterControlPlaneInitializedCondition`; v1beta1 `ControlPlaneInitializedCondition`, `api/v1beta1/condition_consts.go`), else v1beta1 `status.controlPlaneReady` (`api/v1beta1/cluster_types.go`). Before that the 30-minute provisioning grace applies.
- **Old-only status (no `status.v1beta2`)**: in the fallback to the old conditions a False of severity Info or Warning decides nothing (`decisive`; `api/v1beta1/condition_types.go`: Info is not an error, Warning only might become one) — for a Cluster's or a group's availability (old Available/Ready), a Machine's Ready and the first failing condition. Error, or no severity, still decides. The MachineHealthCheck's `RemediationAllowed` is read as before (its False carries Warning by design).
- **Machines and KubeadmControlPlanes of a paused Cluster** (`spec.paused` or the `cluster.x-k8s.io/paused` annotation on the Cluster; `util/annotations/helpers.go` `IsPaused`) have no problems even where their own status says nothing of it (Cluster API before 1.9 writes no Paused condition on them). Their problems carry the Cluster's name (`Detected.belongsTo`), and their sources are judged across the Cluster source's rows: `AcrossDef.from` names another source of the same cluster, which the problems store holds with a row tap for as long as the dependent source lives and whose row changes re-publish the dependents (`across.ts`, `CAPI_PAUSED_ACROSS`). While the Cluster rows are not read in full (loading, forbidden, an error) every problem stays. In the details a Machine or control plane whose Cluster (read by name) is paused shows as paused with the reason; when that Cluster cannot be read and the object has only old conditions, the details say whether it is paused cannot be told.
- **The chain watches are capped** at `MAX_CHAIN_OBJECTS` (= `MAX_SOURCE_OBJECTS`, 5000) each, and the Cluster's chain and an owner's Machine list say when a list was cut.
- **A v1beta2 MachineSet** (which has no Available condition) with fewer ready Machines than desired is "Not available" (or "Scaling" while its count differs), no longer "unknown".
- Tests: `clusterapi.test.tsx` (the grace in every shape, the severity rule, `belongsTo` and `withoutPausedClusters`, the section counter dropping and restoring a paused Cluster's Machine, the details' paused and cannot-tell notes, the capped watch and its note, the MachineSet states).
