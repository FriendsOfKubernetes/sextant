# ADR-0111: Vertical Pod Autoscaler views compute the admission change from the template and judge HPA conflicts from objects only

## Context

The Vertical Pod Autoscaler (kubernetes/autoscaler, `autoscaling.k8s.io/v1`) recommends requests per container and, by its update mode, sets them when a pod is created (admission controller) and changes running pods (updater). Users read `kubectl describe vpa` and still have to work out what a pod would get, why a VPA gives nothing, whether the three components run, and whether the VPA fights an HPA — the project itself warns not to use it with an HPA on the same resource metric (docs/known-limitations.md). Right-sizing (#137, ADR-0070) already recommends from Prometheus history; #242 asks for VPA beside it, read-only, like the other CRD projects (ADR-0097, 0100, 0101).

## Decision

- **A discovered sidebar section `vpa`** with VerticalPodAutoscalers and VerticalPodAutoscalerCheckpoints, shown only while the cluster serves them. The VPA table shows the target, the mode as the API value, the state from the conditions and the first container's CPU and memory target (the CRD's own printer columns). The checkpoint table shows the VPA, the container, the sample count and the save time; the histograms are not shown.
- **State from the recommender's own conditions, in its order** (pkg/recommender/model/vpa.go, input/cluster_feeder.go): `ConfigUnsupported` (the recommender's message; it then also says `NoPodsMatched`, which is not repeated), `NoPodsMatched`, `RecommendationProvided` (with `LowConfidence` or `FetchingHistory` when true), otherwise no recommendation yet. `ConfigDeprecated` is a note. The mode defaults to `Recreate` as `GetUpdateMode` does; `Auto` is shown as the deprecated name of `Recreate`.
- **What a pod created now would get is computed as the admission controller computes it**, from the target's pod template (`admission.ts`): the target as the request, kept within `minAllowed`/`maxAllowed` (`applyVPAPolicy`), with `RequestsOnly` at most the current limit (`capRecommendationToContainerLimit`) and the limit unchanged; with `RequestsAndLimits` the limit is `getProportionalResourceLimit` — no limit stays none, a limit equal to the request or without one becomes the new request, otherwise limit × new ÷ old, rounded down in millicores and bytes (BigInt, so large memory values stay exact); quantities rounded up as `MilliValue()`/`Value()`. A container whose policy is `Off` gets nothing; mode `Off` changes no pod. A LimitRange, containers other webhooks add and the startup CPU boost are not modelled, and the view says so. The updater's rule (outside [lowerBound, upperBound], or after 12 h a change of 10 % or more, never below 2 replicas by default) is told in words, not evaluated against live pods.
- **A workload's details list the VPAs that target it** (Deployment, StatefulSet, DaemonSet, ReplicaSet, Job, CronJob; kind, name and group, never the version) right after right-sizing, with the same table against that workload's template. Right-sizing's rules are unchanged.
- **HPA conflicts are judged from the two objects.** A VPA in `Recreate`, `Auto`, `InPlaceOrRecreate` or `InPlace` and an HPA in the same namespace with the same scale target, on a `Resource` or `ContainerResource` metric for cpu or memory (no metrics = the API default CPU 80 %), that the VPA controls. In the details the template's container names make it exact; without them (the problems) a conflict is claimed only when certain from the VPA alone — no policies or a wildcard policy, or a named container's policy, controls the resource — so the documented pattern "VPA on memory of `app`, HPA on CPU" is never flagged by a guess about unnamed containers.
- **Components found by the install's own names and labels**: Deployments `vpa-recommender`, `vpa-updater`, `vpa-admission-controller` in kube-system (deploy/*.yaml) and Deployments labelled `app.kubernetes.io/name in (vertical-pod-autoscaler,vpa)` with `app.kubernetes.io/component` (the project's chart and Fairwinds' chart). A missing one is explained for the VPA's mode; a missing recommender is not flagged while the VPA has a recommendation (managed VPA, as on GKE, runs outside the cluster, and the view says so). Watched only while a VPA's details are open.
- **Problems category `vpa`, on by default**: `ConfigUnsupported` (2-minute grace from the transition), `NoPodsMatched` (10 minutes, so a rollout or a scale from zero passes) and `HpaConflict` (2 minutes from the first sighting), from one provider (`external` source) holding one cluster-wide VPA watch (≤ 5000) and an HPA list of only the namespaces whose VPAs change running pods (≤ 40 namespaces, ≤ 5000 objects; beyond either the conflicts are not judged and the source says it is truncated). In `NEVER_FOR_AGENTS`.
- **Read-only.** No new command; the kinds offer the generic Edit and Delete only; agents and extensions get nothing new.

## Why

- On by default unlike Traefik, Reflector and Sealed Secrets (ADR-0108–0110): a cluster holds few VPAs (one per workload at most, small objects), and the only other list, HPAs, is opened only where a VPA changes running pods — a cost proportional to VPA use, not to the cluster's size. A tool that creates a VPA per workload (Goldilocks) creates them in mode `Off`, which opens no HPA list.
- Computing the admission change in the window from the template was chosen over reading live pods: the admission controller works on the pod as the template makes it, so the template answers "what would the next pod get" exactly; live pods already carry earlier VPA values and would need a pod watch per view.
- Claiming a conflict only when certain was chosen over assuming containers the policies do not name: a false fight on the documented memory-only pattern would teach users to ignore the category; the details, which have the template, show the exact answer.
- Reading components by name and label was chosen over looking for the webhook configuration or the leases: Deployments answer "is it running" and are what the install manifests and both charts create.

## Consequences

- A LimitRange's default limit or min/max can make a pod's values differ from the table; the table says so.
- A VPA whose policies name only some containers, with an HPA on a resource only an unnamed container's default would fight over, is shown in the details but not on the problems screen.
- Tests: `src/features/vpa/vpa.test.tsx` (model, admission arithmetic against the upstream functions, conflicts, components, provider, the sidebar, details and the workload block with axe); fixtures `src/features/vpa/fixtures/objects.json`; `vpa_problems_are_never_given_to_agents` in `src-tauri/src/mcp/tools_diagnose/tests.rs`.
