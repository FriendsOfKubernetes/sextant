# ADR-0081: Cleanup offers only what it can prove unused, and checks each object again before deleting it

## Context

Clusters collect leftovers (#147): claims of deleted StatefulSets, Released volumes, Services whose pods are gone, old ReplicaSets, finished Pods and Jobs, ConfigMaps and Secrets of removed applications, empty namespaces. Finding them is easy; being sure is not. A reference to a ConfigMap or Secret can sit anywhere — a pod template, an operator's custom resource, a CSI driver's StorageClass parameters, a controller's command-line argument, an application that reads it through the API. Kubernetes has no reference counting and no undo: a deleted Secret that an operator reads on its next reconcile breaks production hours later, and a deleted claim may take its data with it. A cleanup page is the one place in Sextant that deletes many objects at once, so a wrong "unused" is the most expensive mistake the app can make.

## Decision

The page "Cleanup" (Cluster section, `src/features/hygiene/`) offers an object for deletion only when every rule below holds. **These rules are the safety boundary of the feature: relaxing any of them needs a review and a change of this ADR.**

- **When in doubt, not a candidate.** An object is judged only when every list that could name it is known in full (a ready watch, or a kind the cluster does not serve). A list that failed, is forbidden or is still loading makes the objects that depend on it "not judged", named on the page. Nothing is judged before the settings are read.
- **ConfigMaps and Secrets are off by default.** `AppSettings.cleanup.checkConfigMaps` / `checkSecrets` (frontend-written) are false until the user turns them on in the page's settings, which show a warning that Sextant cannot see every reference. When on, references are scanned in pods and every pod template (volumes including CSI and in-tree volume secrets, projected sources, `envFrom`, `env`, image pull secrets, old ReplicaSets and Jobs), container arguments and environment values naming `ns/name` or the name in its own namespace, ServiceAccounts, Ingress TLS and ingress-nginx auth annotations, Gateway listeners and ReferenceGrants, StorageClass secret parameters (a templated name keeps every Secret of the namespaces whose claims use the class) and PersistentVolume secret references, and the objects of known tools by field shape (`scan.ts`: cert-manager, Flux, KEDA, External Secrets, Prometheus operator, Velero, Istio, Traefik, Gateway ListenerSet).
- **Unknown custom kinds gate a namespace.** ConfigMaps, Secrets and claims of a namespace are judged only when its sample (`cleanup_sample` → `resources::sample_namespace`: every served namespaced kind except Events, a metadata-only list of at most 5 names each, 8 requests at a time, once per page open and on "Check again") shows no object of a custom kind the page does not read, since an operator's resource may name them. The page says which kinds blocked which namespace. A failed sample offers nothing in that namespace.
- **An empty namespace is empty of every served kind.** A namespace is a candidate only if it is in view, not `default` or `kube-*`, not terminating, and every served namespaced kind — the watched lists and the sample alike — holds nothing but what Kubernetes creates in every namespace (the root CA ConfigMap, the `default` ServiceAccount and its token). A sampled kind that could not be read, or has more than the sample shows, counts as holding something.
- **Retain volumes are never offered.** A Released PersistentVolume with reclaim policy Retain is shown as "Kept on purpose" and never selectable; a claim's row says its volume's reclaim policy (Delete: the data will be deleted).
- **Never candidates:** objects with an owner, objects being deleted, service account token / Helm release / Argo CD Secrets, `kube-root-ca.crt` and similar distributed ConfigMaps, leader-election ConfigMaps, the Service `default/kubernetes`, ExternalName Services, Pods of a Job or of an unknown controller, a CronJob's Jobs and Jobs with `ttlSecondsAfterFinished`, the system namespaces (`kube-system`, `kube-public`, `kube-node-lease`) and the namespaces excluded in the settings (by default `cert-manager`, `flux-system`, `argocd`, `ingress-nginx`, `istio-system`, `monitoring`, `local-path-storage`). Objects Helm, Flux, Argo CD or another `app.kubernetes.io/managed-by` manages are listed with their manager and never offered: the tool would recreate them or lose track of them.
- **Ages.** An object must be unused (or finished, or in its phase) for a number of days per rule (`AppSettings.cleanup.minAgeDays`: 7 for configs, Services, Pods and Jobs, 30 for claims, volumes and namespaces).
- **The deletion names the object that was checked.** The confirmation lists every object grouped by kind, warns that deleting a namespace deletes everything in it, and above 20 objects requires typing the count. The run waits 1 s after the confirmation (a watch delivers within about 350 ms, so a referrer created before the click is seen), then deletes one object at a time, namespaces last, through the ordinary `resource_delete` with `preconditions` (uid and resourceVersion, `resources::delete_with`). Right before each deletion the object is looked up in the live result again: it must still be a candidate with the confirmed uid and resourceVersion, otherwise it is kept ("no longer looks unused", "changed since it was checked"). A refusal (409 `conflict`, `forbidden`, a timeout) is that object's outcome and does not stop the run; a change is never repeated (ADR-0055). "Stop" finishes the current object and tries no more.
- **Agents and extensions get nothing new.** `cleanup_sample` is a window command (a test in `src-tauri/src/commands/cleanup.rs`); there is no bulk-delete tool or method. An agent still deletes one object at a time under its own rules and confirmations.

## Why

- Offering ConfigMaps and Secrets by default was rejected: the references Sextant cannot see (operators, CSI drivers, controller flags, applications reading the API) are common, and a missing Secret fails late and far from the cleanup. The user turns the rule on knowing that.
- Judging a namespace that holds unknown custom resources was rejected: any operator's resource can name a Secret in a field shape the scanner does not know.
- Checking "empty" against the watched kinds only was rejected: a namespace with only a custom resource would look empty, and deleting it deletes that resource.
- Offering Released volumes with Retain was rejected: Retain is a deliberate choice to keep the data.
- Deleting without preconditions was rejected: between the confirmation and the request an object can be replaced under the same name (a new Secret from a deployment) and the delete would hit the new one. The uid and resourceVersion make the API server refuse instead.
- One-at-a-time with a re-check was preferred over a batch: a referrer that appears during the run keeps the objects after it, and each outcome is reported.

## Consequences

- The page offers less than a script would, and says why for the rest ("not judged", "blocked", "managed", "kept").
- A race with a referrer created during the run cannot be closed by any check before a DELETE; the settle time and the per-object re-check narrow it, and ConfigMaps and Secrets stay opt-in for that reason too.
- At most 5 namespaces of the filter are checked at once; the watches are the resource map's shared ones and close with the page.
- Tests: `rules.test.ts` (each rule and each exclusion), `hygiene.test.tsx` (page, settings, dialog, deletion run), `crates/sextant-core/tests/mutate.rs` (delete preconditions), the sample in `crates/sextant-core/src/resources/sample.rs`.
