# ADR-0125: Charts from metrics-server are sampled in the window into bounded rings while shown; a node's pods get full tables

## Context

Charts of the details (pod, Deployment/StatefulSet/DaemonSet, node) came only from a Prometheus-compatible source (ADR-0102); a cluster with metrics-server alone showed "Charts of the last hour need a Prometheus-compatible source". metrics-server (the Metrics API, `metrics.k8s.io`) keeps no history: it answers the latest window of each pod and node and nothing else. #280 asks for charts from metrics-server and for a resources table on a node's page; #279 asks for the table search to match every column and for a node's pods as a full table instead of the "Show more" list of the "Related" tab.

## Decision

- **History is built in the window, only while a chart is shown** (`src/features/metrics/history.ts`). Without a Prometheus-compatible source and with metrics-server as the source of current values (`MetricsStatus.effectiveUsageSource === "metricsServer"`), `ChartGrid` draws `HistoryCharts`: the values the window already polls every 30 s (`usePodUsageIn` for a pod or a workload — the selected namespaces' poll when it covers the namespace, else a poll of that namespace; `useNodeUsage` for a node) are sampled into a ring per (cluster, chart target). One poll answer is one sample however many charts show it (the answer's identity), and two samples closer than `MIN_SAMPLE_GAP_MS` (5 s) are one. No request is added for the history.
- **Bounds**: a ring keeps the last `HISTORY_MS` (one hour, as the Prometheus charts) and at most `MAX_SAMPLES` (150) samples; at most `MAX_TARGETS_PER_CLUSTER` (30) rings per cluster and `MAX_TARGETS` (100) overall — a new target pushes out the ring nobody has shown for the longest, and never a shown one (then the chart says it cannot sample now); a ring nobody shows is kept `KEEP_MS` (10 minutes), so reopening the details shows the recent past, then dropped; every ring of a cluster is dropped when its connection comes or goes, and its epoch (`useHistoryEpoch`) moves on so a chart still shown (a Reconnect keeps the details mounted) holds a new ring. A new ring never pushes out another cluster's idle ring when its own cluster's cap would refuse it anyway. Nothing is persisted.
- **What is sampled**: a pod's usage; a workload's as the sum of its pods picked by the names its controller gives them (`podNamePattern`, the same matching as the Prometheus workload charts and right-sizing); a node's. CPU and memory only — metrics-server reports no pod counts or disk. The charts say "Since opened · metrics-server, no history". The cluster overview's charts were Prometheus-only at first; see the amendment below.
- **Prometheus stays the first choice**: when a Prometheus-compatible source is found or set, the charts are its last hour as before.
- **The table search matches every shown column** (`src/components/Table/search.ts`): a plain word matches the name, namespace, labels and the text of every visible column — `ColumnDef.searchText` where the shown text is not `value` (an age, "5m", marked `searchTextTimed`), else `value` as text, except a number, a boolean or an RFC 3339 time under a `render` (container squares, Yes/No in the UI language, a time drawn as an age): a cell that shows a translated or reformatted text (a state in words, "All namespaces", a share in percent, an age) gives `searchText`, built with the table's translation, so a word matches what the user reads in the UI language and never a raw identifier the cell does not show. The texts are built once per object (`createRowText`, a `WeakMap` by object, valid until the columns or the language change), lowered and joined one column per line, so a word never spans two columns; only timed texts are rebuilt when the table's clock moves, from translations cached by key and count. Selector terms and their server-side part (`serverSelectors`, ADR-0091) are unchanged. Measured: 20 000 pods, ~180 ms for the first search (building the texts), ~25 ms for the next ones (`search.test.ts` guards it).
- **A node's pods are two details tabs** (`src/features/node-pods/`): "Pods" — the resource table of every pod on the node (one watch by `spec.nodeName`, a field the API server selects by, all namespaces; the Pods page's columns without "Node"; sortable, searched, virtualized, with the row actions) — and "Resources" — "Allocated resources" as in `kubectl describe node` (requests and limits of the non-terminated pods summed against allocatable, with the share in percent, and the node's usage) above a table of those pods with each one's CPU/memory request, limit and usage. Usage comes from whatever source of current values the cluster uses, asked for the namespaces of the node's pods by name — never a cluster-wide poll of its own: the poll of every namespace is read only while another view holds it (the Pods table under "All namespaces"); otherwise at most the first 40 namespaces by name are asked, and the tabs say that usage is shown for those only (`usePodUsageOfMany`).
- **Pod amounts follow ADR-0037**: only `spec.containers`; a pod's limit counts only when every container sets one. So the node's limit sum covers the pods with a whole limit and the tab says how many have none ("the limits above are at least these sums"), where `kubectl` adds partial limits.

## Why

- Sampling the existing polls was chosen over a backend recorder: a backend history would poll every pod and node of every connected cluster all the time; in the window the cost is what the open views already pay. The price is that history starts when the view opens, which the note says.
- Rings per shown target with hard caps were chosen over one ring per pod of the poll answer: the answers hold every pod of the selected namespaces, and keeping them all would grow with the cluster.
- Building row texts once per object was chosen over rendering cells to text or formatting per keystroke: a 20 000-row table must stay responsive while typing.
- Separate "Pods" and "Resources" tabs were chosen over one table with every column: the details panel is narrow, and the two answer different questions (state vs. allocation).

## Consequences

- A chart from metrics-server can have gaps (the view was closed for a while) drawn as a straight line between samples.
- The time is the window's clock at the answer, not metrics-server's own window timestamp.
- Searching for a text a cell draws but no column value carries (a container square's name) finds nothing.
- Tests: `src/components/Table/search.test.ts`, `src/features/metrics/history.test.ts`, `src/features/metrics/historyCharts.test.tsx` (with axe), `src/features/node-pods/model.test.ts`, `src/features/node-pods/nodePods.test.tsx` (with axe).

## Amendment (0.25.1): the cluster overview samples too

The user asked for the overview's charts without Prometheus as well, with the warning kept but shorter. Without a Prometheus-compatible source and with metrics-server as the source of current values, the overview's "Last hour" draws CPU and memory as every node's usage summed (`targetUsage` of `{type: "cluster"}`), sampled from the node poll its usage card already holds — no new request. Every metrics-server chart says only "Since opened · metrics-server, no history" with a link to the cluster settings, in place of the long "Charts of the last hour need a Prometheus-compatible source" (still shown when metrics-server is not there either). A node metrics-server has no value for counts as nothing in the sum. Tests: `src/features/overview/overview.test.tsx` (with axe), `src/features/metrics/history.test.ts`.
