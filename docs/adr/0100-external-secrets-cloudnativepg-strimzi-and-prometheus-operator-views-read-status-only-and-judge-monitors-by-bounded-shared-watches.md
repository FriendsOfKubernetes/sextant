# ADR-0100: External Secrets, CloudNativePG, Strimzi and Prometheus Operator views read status only and judge monitors by bounded shared watches

## Context

#213 asked for readable status of the CRD projects people run most, in the style of the Flux, Argo CD and cert-manager sections. This ADR covers four of them: External Secrets Operator (sync status and last error, never the secret data), CloudNativePG (primary, replicas, failover, backups), Strimzi (Kafka clusters, topics, users: readiness and conditions) and Prometheus Operator (which targets ServiceMonitors and PodMonitors select, and whether they select anything). Argo Rollouts and Argo Workflows are ADR-0097; Knative, Crossplane and Kyverno have their own.

## Decision

- **Read-only, frontend only, one feature per project** (`src/features/external-secrets/`, `cnpg/`, `strimzi/`, `prometheus-operator/`), each a discovered sidebar section (`externalSecrets`, `cnpg`, `strimzi`, `prometheusOperator` in `DISCOVERED_SECTIONS`) that shows only the kinds the cluster serves, at the version discovery serves. No Rust command was added and nothing is written to the cluster; the kinds offer the generic Edit and Delete under their usual confirmations. Each project has its own locale namespace and can be removed on its own.
- **What each one reads** — the operator's own status, never a guess:
  - External Secrets: the `Ready` condition (ready / pending / failed with its reason and message), `spec.refreshInterval` and `status.refreshTime`, the store (`secretStoreRef`, watched by name while the details are open, to show whether it is ready), the target Secret as a link, the remote keys by name (`spec.data[].remoteRef`, `spec.dataFrom`), stores' provider, validation and capabilities, a ClusterExternalSecret's provisioned and failed namespaces, a PushSecret's source Secret and remote keys.
  - CloudNativePG: a Cluster's phase in words (healthy, switchover when `targetPrimary` differs from `currentPrimary`, failing over when the phase says so or the target is `pending`, unhealthy for the phases that need someone), ready instances of desired, each instance's role (`currentPrimary` / `instancesReportedState.isPrimary`) and health (`instancesStatus`), last successful and failed backup, the recoverability point, and the `ContinuousArchiving` and `LastBackupSucceeded` conditions; Backups, ScheduledBackups and Poolers by their fields.
  - Strimzi: `Ready` True is ready; `NotReady` True (or `Ready` False) is not ready with its reason; neither is pending. `Warning` conditions are listed in the details and never count as a problem. A KafkaNodePool carries no Ready condition, so it shows none (its state is the Kafka's). A Kafka's declared listeners are joined with the addresses in `status.listeners`; node pools, topics' partitions and replicas, users' authentication and their Secret's name (a link; its data is never read).
  - Prometheus Operator: Prometheus and Alertmanager readiness from `Available` (True, Degraded, False) and `Reconciled`; a PrometheusRule's groups with their alerting and recording rules; a Probe's prober and targets; and for a monitor, the targets below.
- **What a monitor selects.** Selectors are the resource map's (`resource-map/selectors.ts`), so a label selector means the same everywhere. The namespaces a monitor looks in are `namespaceSelector.matchNames`, every namespace for `any: true`, else its own — unless every Prometheus that picks it up has `spec.ignoreNamespaceSelectors: true`, which makes monitors find targets in their own namespace only (`getNamespacesFromNamespaceSelector`, `pkg/prometheus/promcfg.go`; it does not change which monitors a Prometheus picks up); when only some do, the own namespace is added (amended after the 0.18 review). The details send the selector to the API server as a label selector, so only matching Services (Pods) are listed, in at most 20 namespaces (`MAX_DETAIL_NAMESPACES`); a monitor of every namespace is listed cluster-wide by its selector, and an empty selector over every namespace is not listed at all. The endpoints' port names are checked on what was listed ("on 2 of 3"). Whether a Prometheus (or PrometheusAgent) picks an object up follows the operator's API: a null selector selects nothing, an empty one everything; a null namespace selector means the Prometheus's own namespace, an empty one every namespace, and only a namespace selector with terms makes Sextant read the Namespaces' labels (metadata only); when they cannot be read the answer is "not known".
- **Problems.** Four categories (`externalSecrets`, `cnpg`, `strimzi`, `prometheusOperator`) feed the problems screen, the notifications and each section's counter through the shared problem sources (`problems/store.ts`), watched only where the kinds are served: a failed ExternalSecret, ClusterExternalSecret or PushSecret sync and a store that does not validate; a Cluster not healthy (after 5 minutes), failing archiving or last backup, a failed Backup (for a day after it stopped; the Cluster's `LastBackupSucceeded` keeps the lasting state). "Stopped" is the first of `stoppedAt`, `reconciliationTerminatedAt`, `startedAt`, `reconciliationStartedAt`, the creation time: the operator's `SetAsFailed` (`api/v1/backup_funcs.go`) writes only the phase, the error and `reconciliationTerminatedAt`, and `stoppedAt` comes only from a backup tool that reached the end, so most failed Backups have none and would otherwise never expire. A hibernated Cluster (declarative hibernation, `pkg/reconciler/hibernation`: the annotation `cnpg.io/hibernation: "on"`, exactly "on"; the condition `cnpg.io/hibernation` True/`Hibernated` once the pods are gone, False/`DeletingPods` or `WaitingPodsDeletion` on the way) is a steady state shown as Hibernated / Hibernating, never a problem — the operator leaves the phase as it was and `readyInstances` at 0, so it looked unready by every other field; while the condition says `WaitingForHealthy` hibernation has not started and the Cluster is judged as any other (both amended after the 0.18 review); a Strimzi object not ready (after 5 minutes); a Prometheus or Alertmanager not available, degraded or not reconciled (after 5 minutes). Monitors are judged across objects by a provider (`prometheus-operator/provider.ts` + `store.ts`, held only where ServiceMonitors are served): it holds ServiceMonitors, PodMonitors, Prometheuses and PrometheusAgents in all namespaces and metadata-only Services and Pods of the namespaces the monitors look in, at most 40 namespaces per kind (`MAX_TARGET_NAMESPACES`), through the shared watches of the resource map. A monitor that selects nothing is a problem; one that no Prometheus picks up is a warning (shown, never notified, not counted), and only when the cluster has a Prometheus object at all. **The `prometheusOperator` category is opt-in** (`OPT_IN_CATEGORIES`, mirrored in `diagnose_answers.rs`; a toggle on the Problems page like `policies`): the provider lists every monitor and metadata of the Services and Pods they look at, a cost a cluster pays only when asked; its details still compute what a monitor selects while open. The store looks at changes of the shared watches at most every 500 ms (`REBUILD_DELAY_MS`) and rebuilds a cluster's findings only when one of its own watches, the connection or discovery changed (by the identity of their states); the provider compares the store's state object instead of serialising every finding. Strimzi KafkaTopic and KafkaUser sources are capped at 5000 objects (`MAX_SOURCE_OBJECTS`, `SourceDef.maxObjects`), and a capped source says it is truncated (amended after the 0.18 review).
- **Agents get nothing new.** The four categories are in `NEVER_FOR_AGENTS` (`src-tauri/src/mcp/diagnose_answers.rs`): `get_problems` does not return them; no MCP tool or extension method was added.

## Why

- Judging from the operators' conditions keeps Sextant honest: each operator already decides when its object is ready, and re-deriving it would disagree with the operator during upgrades of either.
- External Secrets touches Secrets by nature. Reading the target Secret to show "what was synced" was rejected: the details link it, and the window gets Secrets stripped by the core anyway (ADR-0014). The remote keys' names come from the ExternalSecret's spec, which is not secret.
- Listing every Service and Pod of the cluster to find monitors that select nothing was rejected for memory: the provider lists only the namespaces monitors name, metadata only, and gives up (no verdict) on a monitor of every namespace or beyond the cap, rather than answering "selects nothing" without knowing.
- "Not picked up by any Prometheus" stays a warning: ServiceMonitors are also read by other collectors (a PrometheusAgent in another cluster, VictoriaMetrics' operator, Grafana Alloy), so it may be intended.
- Keeping the categories from agents follows the rule of this build that agents get nothing new unless an issue asks for it; opening them later is one line plus a review of what the problems reveal.

## Consequences

- A monitor of every namespace, or of more than 40 namespaces, never shows "selects nothing" on the problems screen; its details still list what it selects (by the server-side selector).
- The resource map and the "Related" tab colour a kind green only when the problems rules judge it alone (`judgedByRules` in `problems/sources.ts`): a ServiceMonitor, whose problems the provider finds across objects, is neutral there, never "fine" while the Problems page may list it.
- A cluster that serves PodMonitors but not ServiceMonitors gets no monitor problems (the provider's source is the ServiceMonitor kind); its details still work.
- ServiceMonitors' `status.bindings` (newer operator versions) are not read; the pick-up is computed from the Prometheus selectors, so a Prometheus that rejected a monitor still counts as picking it up.
- The CloudNativePG phase names are the operator's English sentences; "unhealthy" is decided by their words (unrecoverable, cannot, unable, waiting for user, error), so a new phase reads as "progressing" until it is recognised.

**Amended (v0.20.0, #235):** the Strimzi section also lists KafkaConnectors (`strimzi/connectors.ts`, `connectorDetails.tsx`). A connector's and its tasks' states come from the Kafka Connect REST status Strimzi copies as is into a KafkaConnector's `status.connectorStatus` and a KafkaMirrorMaker2's `status.connectors[]` (`{name, type, connector: {state, worker_id, trace}, tasks: [{id, state, worker_id, trace}]}`), and the automatic restarts from `status.autoRestart` / `status.autoRestartStatuses[]` (`{count, connectorName, lastRestartTimestamp}`) with `spec.autoRestart` (`enabled`, `maxRestarts`) — read from strimzi-kafka-operator (`KafkaConnectorStatus`, `AutoRestartStatus`, `AbstractConnectOperator`, `KafkaConnectAssemblyOperator`, `KafkaMirrorMaker2AssemblyOperator`). A FAILED connector (`ConnectorFailed`) or task (`TaskFailed`) is a `strimzi` problem at once, its message the first line of the first failure's trace (prefixed by the connector's name on a MirrorMaker 2), and it replaces the object's generic NotReady problem: Strimzi's NotReady for it only says "see connectorStatus", and a MirrorMaker 2 with a failed task stays Ready, so the REST status is the one source. The details show each failure with the trace folded (at most 20 000 characters rendered) and say when Strimzi stopped restarting because `maxRestarts` is reached. Nothing is asked of Kafka Connect; still read-only, and the category stays out of agents' answers (`NEVER_FOR_AGENTS`).
