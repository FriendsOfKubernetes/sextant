# ADR-0121: OLM views read OLM's own status, never count a copied CSV, and never approve an InstallPlan

## Context

#268 asked for Operator Lifecycle Manager views (`operators.coreos.com`): Subscription (channel, installed and current CSV, upgrade pending, approval), ClusterServiceVersion (phase, requirements, owned CRDs), InstallPlan (approval state), CatalogSource (connection state), OperatorGroup; problems for failed CSVs and stuck install plans; read-only. OLM is installed on every OpenShift cluster and on many plain ones (OperatorHub.io's `olm` namespace). Sources read: operator-framework/api `pkg/operators/v1alpha1/{subscription,clusterserviceversion,installplan,catalogsource}_types.go`, `pkg/operators/v1alpha1/clusterserviceversion.go` (`CopiedLabelKey`, `IsCopied`), `pkg/operators/v1/{operatorgroup,operator}_types.go`; operator-lifecycle-manager `pkg/controller/operators/olm/operatorgroup.go` (`copyToNamespace`, `csvCopyPrototype`), `pkg/controller/operators/catalog/subscription/state.go` (`CheckInstallPlanStatus`), `pkg/controller/install/deployment.go` and `pkg/lib/ownerutil/util.go` (the owner labels); operator-controller `api/v1/{clusterextension,clustercatalog,common}_types.go` for OLM v1.

## Decision

- **Read-only, frontend only.** `src/features/olm/` is the discovered sidebar section `olm` ("Operators (OLM)") with Subscription, ClusterServiceVersion, InstallPlan, CatalogSource (v1alpha1), OperatorGroup and the cluster-scoped Operator (v1), and OLM v1's cluster-scoped ClusterExtension and ClusterCatalog (`olm.operatorframework.io/v1`) where served. No Rust command was added, nothing is written; the kinds offer the generic Edit and Delete only. Strings are the namespace `olm`.
- **No "Approve" for an InstallPlan in this version.** A Manual Subscription's InstallPlan in `RequiresApproval` is shown as waiting (the Subscription's state "Waiting for approval", a note on the plan saying Sextant does not approve install plans). Approving is a change to the cluster that installs or upgrades an operator with cluster-wide permissions; it needs its own decision (what the confirmation shows — the plan's steps, the CSV's permissions — and whether agents may ever do it) and is left for a later version.
- **A Subscription's state** from its conditions and `status.state`: `ResolutionFailed`, `InstallPlanFailed`, `UpgradeFailed`, waiting for approval (`InstallPlanPending` with reason `RequiresApproval` — the catalog operator writes the plan's phase into that condition's reason), upgrade pending (`UpgradePending`, or `installedCSV` ≠ `currentCSV`), upgrade available, at the latest known. `installPlanApproval` unset is Automatic, as OLM treats it. The current plan is `status.installPlanRef`, else the older `status.installplan`. While its details are open, the plan and the installed CSV are read by name (`metadata.name=`) in their namespace to show their phases.
- **Copied CSVs.** OLM copies every CSV, with its whole spec and the original's status, into each target namespace of its OperatorGroup, labelled `olm.copiedFrom=<the original's namespace>` and with `status.reason: Copied`. A CSV is a copy exactly when OLM's `IsCopied` says so: that reason, that label, or an `olm.operatorNamespace` annotation naming another namespace. A copy's details say it is one and link the original; its requirements and Deployments are the original's and are not repeated. The CSV table shows a "Copy of" column.
- **A CSV's details**: phase with reason and message, version, `replaces`, `skips`, provider, `minKubeVersion`, the Subscription in its namespace that installed it, install modes (supported and not), `status.requirementStatus` (with a note when any is not `Present`), owned and required CRDs (`spec.customresourcedefinitions`), and the Deployments of the `deployment` install strategy (`spec.install.spec.deployments[].name`) with ready/desired and the Available condition of the real Deployments, listed in the CSV's namespace by the labels OLM puts on them (`olm.owner=<csv>,olm.owner.kind=ClusterServiceVersion`, ≤ 50). A CSV name over 63 characters cannot be a label value: its Deployments are "cannot tell".
- **An InstallPlan's details**: phase, approval, approved, its CSVs, the `Installed` condition when False (why it failed), bundle lookups with a failing or pending condition, and `status.plan` steps (for which CSV, kind, name, status), at most `MAX_STEPS` = 200. A step's `resource.manifest` — the whole object to create, which can be a bundle's Secret — is never read or shown by the view (the YAML section still shows the object as the API server returns it).
- **CatalogSource**: type, image or address or ConfigMap, poll interval (`spec.updateStrategy.registryPoll.interval`), `status.connectionState.lastObservedState` (a gRPC connectivity state), the connected address, last connect and poll times, and the registry Service. **OperatorGroup**: `status.namespaces` (OLM's `[""]` is "All namespaces"), the requested `targetNamespaces` or selector, the upgrade strategy (a warning for `TechPreviewUnsafeFailForward`), ServiceAccount, provided APIs. **Operator**: `status.components.refs` with their conditions, at most 200. **ClusterExtension**: package, version range, channels, upgrade constraint policy, install namespace and ServiceAccount, installed bundle, and the `Installed` and `Progressing` conditions (Progressing True with reason `Retrying`, `Blocked`, `InvalidConfiguration` or `ProgressDeadlineExceeded` is a warning); **ClusterCatalog**: image, resolved image, poll interval, priority, availability mode, base URL (text, never requested), last unpacked, `Serving` and `Progressing`. OLM v1 has no problems in this version.
- **Problems: category `olm`, on by default**, in `NEVER_FOR_AGENTS`:
  - a CSV in phase `Failed`, originals only, `CSV_FAILED_GRACE_MS` = 5 min after `status.lastTransitionTime` (OLM retries `InstallCheckFailed` and `ComponentUnhealthy`);
  - a Subscription whose `ResolutionFailed` is True, 10 min after the condition changed;
  - a Subscription whose `InstallPlanFailed` is True, at once, about the InstallPlan it names (the problem opens the plan);
  - a Subscription whose `InstallPlanPending` is True with reason `Planning`, `Installing` or `InstallPlanNotYetReconciled` for `PLAN_STUCK_MS` = 30 min ("stuck");
  - a CatalogSource whose connection state is not `READY` (nor `IDLE`, a healthy channel without a call) for 10 min after the state was first seen (the status has no time of the state; a new state starts the grace again).
  - Waiting for an approval is deliberate and never a problem.
- **Sources.** Subscriptions (≤ `MAX_SOURCE_OBJECTS`) and CatalogSources are ordinary sources. CSVs come from a provider (`provider.ts`, an `external` source): one watch of the originals only, the copies dropped by the API server with the label selector `!olm.copiedFrom`, ≤ `MAX_SOURCE_OBJECTS`, each judged by the shared rules (which skip a copy recognised by its reason or annotation too). **InstallPlans are not watched for problems**: each holds the whole manifests of its steps (CRDs included), and the Subscription already reports the state of the plan it uses now — an older failed plan OLM keeps around is no current problem. The InstallPlan table's "Only problems" filter shows the failed plans.
- **Agents get nothing new**: no MCP tool, no extension method; `olm` is in `NEVER_FOR_AGENTS` (a test in `tools_diagnose/tests.rs`).

## Why

- OLM's statuses are its own verdicts (resolution, requirement checks, install checks); recomputing them would need the resolver and the catalogs.
- A copy is not a second failure: an AllNamespaces operator has one copy per namespace of the cluster, so counting copies would turn one failed operator into hundreds of problems, and watching them would hold a full CSV (icons, descriptions) per namespace and operator.
- The Subscription mirrors its current plan (`CheckInstallPlanStatus` removes and re-sets the plan conditions on every sync), so judging the Subscription follows the plan that matters and costs a small object per operator instead of every plan's manifests.

## Consequences

- An InstallPlan created by hand, without a Subscription, never shows on the problems screen; its table and details still show its phase.
- A cluster whose OLM marks copies only by reason or annotation (no label) still lists the copies in the provider's watch (bounded by the cap); they are not counted.
- A CatalogSource stuck in a bad state is counted 10 minutes after Sextant first saw it, not after it entered the state.
- Approving an InstallPlan stays a `kubectl patch`/console action until a later ADR decides otherwise.
