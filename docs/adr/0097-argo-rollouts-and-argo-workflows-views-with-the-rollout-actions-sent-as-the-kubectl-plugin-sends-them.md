# ADR-0097: Argo Rollouts and Argo Workflows views, with the rollout actions sent as the kubectl plugin sends them

## Context

#213 asked for readable status of the CRD projects people run most, in the style of the Flux, Argo CD and cert-manager sections. For Argo Rollouts: Rollouts with their steps, current weight, canary/stable ReplicaSets and analysis runs, and the actions promote, promote-full, abort and retry through `resource_patch` with a confirmation. For Argo Workflows: Workflows and CronWorkflows with their phase, the failed step and its message, and a link to the step's pod logs. Both projects use the API group `argoproj.io`, which Argo CD's section already uses for Application, ApplicationSet and AppProject. Before this change Sextant's patch reached only the object itself, never its `status` subresource (ADR-0069 noted this for cert-manager's renew), while the plugin's promote, abort and retry write status fields.

## Decision

- **Two discovered sections, kinds kept apart from Argo CD.** "Argo Rollouts" (Rollout, AnalysisRun, AnalysisTemplate, ClusterAnalysisTemplate, Experiment) and "Argo Workflows" (Workflow, CronWorkflow, WorkflowTemplate, ClusterWorkflowTemplate) are registry kinds in `argoRollouts` / `argoWorkflows` (`DISCOVERED_SECTIONS`): a section shows only the kinds discovery serves. Each feature registers exactly its own kinds by group *and* kind (`src/features/argo-rollouts`, `src/features/argo-workflows`); Argo CD's registrations and `argoOpenUi` (offered only to the kinds that list it) are untouched.
- **A Rollout's status reads as the plugin reads it** (`GetRolloutPhase`, `utils/rollout/rolloututil.go`): Progressing while `status.observedGeneration` (a string; a hash from v0.9 counts as observed) is behind `metadata.generation`, while `controllerPause` is set without pause conditions (unpausing), or while a referenced workload's generation is not observed; otherwise the controller's `status.phase`/`status.message` (Healthy, Progressing, Paused, Degraded); for a controller older than v1.0 without `status.phase`, `CalculateRolloutPhase` is ported. The step is `currentStepIndex/len(steps)`; the set weight is `GetCurrentSetWeight` (0 after an abort, the maximum once every step is done, else the last `setWeight` at or before the current step); the actual weight is the plugin's (`info/rollout_info.go`): the router's `status.canary.weights.canary.weight` with traffic routing, else the canary ReplicaSet's share of the available pods. ReplicaSets are the Rollout's by owner uid and are marked stable / canary / active / preview by their `rollouts-pod-template-hash` against `status.stableRS`, `status.currentPodHash` and the blue-green selectors. AnalysisRuns are the Rollout's by owner uid (newest 20); each metric shows its counts and its newest failed, errored or inconclusive measurement's value and message.
- **The actions send exactly the plugin's patches** (`pkg/kubectl-argo-rollouts/cmd/promote/promote.go` `getPatches` and constants, `abort/abort.go`, `retry/retry.go`; all JSON merge patches):

  | Action | Spec (the object) | Status (the subresource) |
  |---|---|---|
  | Promote | `{"spec":{"paused":false}}` when `spec.paused` | the first that applies: an inconclusive canary step analysis with pause conditions and `controllerPause` → `{"status":{"pauseConditions":null,"controllerPause":false,"currentStepIndex":i+1}}`; pause conditions → `{"status":{"pauseConditions":null}}`; a canary with steps → `{"status":{"pauseConditions":null,"currentStepIndex":i+1}}` (`i` stays at the end of the steps) |
  | Promote fully | `{"spec":{"paused":false}}` when `spec.paused` | `{"status":{"promoteFull":true}}` when `currentPodHash` ≠ `stableRS` |
  | Abort | — | `{"status":{"abort":true}}` |
  | Retry | — | `{"status":{"abort":false}}` |

  As the plugin, the status patch goes first; when the API server answers `notFound` for the status subresource (Argo Rollouts v0.9 had none), the plugin's "unified" patch (spec and status together, as in its constants) goes to the object instead. Each request is sent once (ADR-0055) within `CHANGE_TIMEOUT`.
- **The status subresource is reached through one new window command**, `resource_patch_status` (`sextant_core::resources::patch_status`, `src-tauri/src/commands/actions.rs`), allowed only for the kinds of `STATUS_PATCH_KINDS` (`argoproj.io/Rollout`); any other kind is `invalid` before a request, and a patch naming the hidden-values marker is refused as by `resource_patch`. MCP agents and extensions get nothing new (a test asserts neither a tool nor a method patches a status; agents keep `patch_resource` on the object under their rules).
- **Confirmation shows the patches, the dialog re-checks before sending.** Every action opens a confirmation that reads the Rollout again and lists each patch with where it goes (the status, the object, and the v0.9 fallback); Promote fully that changes nothing says so and cannot be confirmed. On confirm the Rollout is read once more and the patches are built again; if they differ from the ones shown, nothing is sent and the dialog shows the new ones to confirm. The safe-apply dry run (ADR-0074) is not used: it previews YAML replace/apply, and these patches touch only controller fields whose whole change is the listed patch.
- **A Workflow reads as the Argo UI reads it.** Phase, `status.progress` (counted from pod nodes for an old controller), duration (start to finish or now), and the failed step: the first failed or errored pod/container node to finish, else the first failed non-root node, with its message (else `status.message`). The node tree starts at the root (the node named as the Workflow), shows a DAG task with two parents once, is collapsed below the root, offers "Show the failed step" (opens the path to it) and draws at most `MAX_TREE_NODES` = 500 rows. Nodes offloaded to the controller's database or compressed (`offloadNodeStatusVersion`, `compressedNodes`) are not fetched; the view says so.
- **Pod names follow `workflows.argoproj.io/pod-name-format`** (`workflow/util/pod_name.go` `GeneratePodName`, `ui/src/shared/pod-name.ts`): `v1` is the node id; `v2` (the default, also without the annotation) is `<workflow>-<template>-<hash>`, the hash taken from the node id (the workflow name followed by the 32-bit FNV-1a of the node name) or, when the id does not start with the workflow name, computed from the node name; the prefix is cut to fit 253 characters. A container-set container (`Container` node) runs in its boundary node's pod: the controller creates each container node with the template's `Pod` node as `boundaryID` and names the pod after that node (`workflow/controller/container_set_template.go`, `initializeNode(…, NodeTypeContainer, …, node.ID, …)`), so the id, the name the hash falls back to and the template are the boundary node's (amended after the 0.18 review: the container node's own name was hashed before). A pod node links to its pod and opens its logs in the logs dock tab after one GET of the pod (the pod may be gone: Argo's pod GC deletes it; the error is shown).
- **Problems.** Category `rollouts`: the problems store watches Rollouts (discovered kinds only); a Degraded or aborted Rollout is a problem, and so is an analysis run the Rollout reports in its status (`currentStepAnalysisRunStatus`, `currentBackgroundAnalysisRunStatus`, blue-green pre/post-promotion) as Failed or Error — AnalysisRuns themselves are never watched in the background. All share one notification group per Rollout. Category `workflows`: a provider opens one watch of Workflows by the controller's phase label (`workflows.argoproj.io/phase in (Failed,Error)`), **metadata only** (a Workflow's status holds every node and a failed one can be megabytes), capped at 5000 (`MAX_FAILED_WORKFLOWS`, about 1 KB each; the API server lists in namespace/name order, so a capped list is reported truncated). A failure counts from the latest time known: when the provider saw the Workflow enter the failed list while watching (the controller sets the phase label as it fails), else its creation; it is a problem until 24 hours after that (`until`), at most 500 problems (`MAX_WORKFLOW_PROBLEMS`), the most recent failures first; a CronWorkflow's runs notify as one. `status.finishedAt` is not in a metadata-only list, and the `managedFields` time of the controller's last update (`workflow-controller`, an `Update` without a field manager) was rejected: Sextant's watches drop `managedFields` in the core for every list, and keeping them for one view would change what every watch carries. (Amended after the 0.18 review: before, the cap was 500 in listing order and recency came from the creation time only, so a long-running Workflow failing now was never a problem.) Both sections get a counter on their header.

## Why

- Re-implementing the plugin's patch choice in the window keeps the action one click and one confirmation; running the plugin (a binary the user may not have) or adding a generic status patch to agents would widen what can change a cluster. Limiting the status patch to the one kind that needs it keeps the new surface small; a later kind adds itself to `STATUS_PATCH_KINDS` with its own review.
- Reading the Rollout again before sending (as the plugin does) and refusing when the patches would differ means the user always confirms what is sent, even when the controller moved the Rollout while the dialog was open.
- Watching failed Workflows by label and metadata only keeps the background cost of the problems category bounded whatever the size and number of Workflows; the details read the whole object only when the user opens it.

## Consequences

- Argo Rollouts v0.9 (no status subresource) gets the unified patch on the object, as from the plugin; this path is tested with a mocked `notFound`, not against a v0.9 controller.
- Workflow problems carry no message (metadata only); the failed step and its message are in the details. A Workflow that was already failed when the provider first looked counts from its creation, so a long-running one that failed shortly before Sextant connected is missed until it is opened. A Workflow whose labels were removed or a controller that does not keep the phase label is not counted.
- The fixtures are the projects' examples (`examples/rollout-canary.yaml`, `rollout-bluegreen.yaml`, an analysis with a Prometheus metric; Argo Workflows' `dag-diamond.yaml` and a CronWorkflow) with statuses written in the controllers' formats. The status subresource patch, the null that clears `pauseConditions` and the phase label selector were checked against the official CRDs on the kind test cluster (CRDs only, no controllers, removed afterwards).

## Amended (v0.21.0): Rollout pause and resume, Workflow suspend, resume, stop and terminate (#237, #238)

- **Rollout Pause** sends what `kubectl argo rollouts pause` sends (`cmd/pause/pause.go`): `{"spec":{"paused":true}}`, a JSON merge patch to the object; offered while `spec.paused` is not set (the plugin pauses any Rollout).
- **Rollout Resume.** The plugin has no `resume` any more: its `resume` command was replaced by `promote` in v0.6 (argo-rollouts#277), and it sent `{"spec":{"paused":false},"status":{"pauseConditions":null}}`; Argo CD's Rollout `resume` action sets the same two fields, each only where it is set. Sextant sends that patch split as `promote` splits it: `{"spec":{"paused":false}}` to the object when `spec.paused`, `{"status":{"pauseConditions":null}}` to the status subresource when pause conditions exist, and the old command's whole patch to the object when the status subresource is `notFound` (v0.9). It is offered while the Rollout is paused by hand or by the controller. On a canary pause step, clearing the conditions completes that step, as the controller reads it; unlike Promote, Resume never writes `currentStepIndex` and never lifts `controllerPause`. Both use the existing dialog: the patches listed, the Rollout re-read on confirm, nothing sent when they differ; `STATUS_PATCH_KINDS` is unchanged.
- **Workflow actions** follow `workflow/util/util.go`. A Workflow has no status subresource (`subresources: {}` in the CRD; the controller and `argo resume` write its nodes through the object), so each action is one JSON merge patch of the object through `resource_patch`, sent once within `CHANGE_TIMEOUT`; the Rust status-patch allow-list is not extended.

  | Action | Patch | Refused / nothing |
  |---|---|---|
  | Suspend (`SuspendWorkflow`) | `{"metadata":{"resourceVersion":rv,"labels":{actor labels: null}},"spec":{"suspend":true}}` | refused with `workflows.argoproj.io/completed=true`; nothing when already suspended |
  | Resume (`ResumeWorkflow`, no node selector) | `spec.suspend: null` when set; every running Suspend node `{"phase":"Succeeded","finishedAt":<time of sending>}`, its message followed by `"; "` when it had one, an output parameter with `valueFrom.supplied` given `valueFrom.default` as its `value`, `valueFrom` kept (`OverrideOutputParametersWithDefault` reads `param.ValueFrom.Default`, not the parameter's own `default`; refused without it) and exported by `globalName` to `status.outputs.parameters` (`AddParamToGlobalScope`); with `resourceVersion` and the actor labels removed | refused when the nodes are compressed or offloaded (`compressedNodes`, `offloadNodeStatusVersion`): they cannot be read without the controller's hydrator; nothing when neither applies |
  | Stop / Terminate (`patchShutdownStrategy`) | `{"spec":{"shutdown":"Stop"}}` / `"Terminate"`, no resourceVersion, no labels | refused for a finished Workflow (`Succeeded`, `Failed`, `Error`); nothing when that strategy is set |

  Suspend and resume are an `Update` in util.go, so their patch carries the resourceVersion of the read right before sending: a change in between is a conflict from the API server, shown in the dialog and not retried (util.go retries a conflict; ADR-0055 does not). Sextant has no Argo identity (no claims), so it does what `creator.LabelActor` does without claims — removes `workflows.argoproj.io/actor`, `actor-email`, `actor-preferred-username` and `action` (only those present are named) — and the resume message names no user. The dialog lists the patch with the resourceVersion and time as of opening and says both are taken again when sending; on confirm the plan is rebuilt from a fresh read and compared without them, and a different plan is shown instead of sent. The node selector variants (`argo resume/stop --node-field-selector`, `argo node set`) are not offered. Checked on the kind test cluster against the official Workflow CRD (no controller): the stale resourceVersion is a conflict, the node status and the label removal persist.
- **Retry is left out.** `FormulateRetryWorkflow` rebuilds the node tree (`planReset`/`applyResetPlan`: deletes and resets nodes, scrubs references, drops the onExit subtree), rewrites labels and phase in `createNewRetryWorkflow`, decompresses nodes and deletes the pods of reset nodes — several requests that are not atomic and a reset plan that changes between Argo releases. Reproducing it in the window could leave a Workflow half reset. A failed Workflow's details say to run `argo retry <name> -n <namespace>` instead.
- MCP agents and extensions get nothing new: the actions are window actions in the action registry and use the existing `resource_get`, `resource_patch` and `resource_patch_status` (still limited to Rollouts); agents keep `patch_resource` under their rules as before.

Amended (v0.21.0 review): three corrections. (1) A Workflow resume read the parameter's own `default`; `workflow/util/util.go` `OverrideOutputParametersWithDefault` checks and uses `param.ValueFrom.Default` and only sets `Value`, so Sextant now does the same (the table above). (2) The Rollout Resume dialog said Resume does not advance the rollout; pause.go `CompletedCanaryPauseStep` counts a canary pause step completed when the controller paused it and no pause condition is left, so clearing the conditions on such a step moves the rollout on as Promote does — the dialog says so in every language (Resume still writes no `currentStepIndex`). (3) The Workflow dialog now says that the resourceVersion and `finishedAt` it shows are refreshed when the change is sent.

## Amended (v0.22.0): Rollout Restart (#255)

Restart sends exactly `kubectl argo rollouts restart`'s patch (pkg/kubectl-argo-rollouts/cmd/restart/restart.go, `restartPatch` and `RestartRollout`): the merge patch `{"spec":{"restartAt":"<now>"}}` to the Rollout itself (never the status subresource), the time `timeutil.Now().UTC()` formatted with Go's `time.RFC3339` (whole seconds, `Z`; `restartPatch`/`rfc3339Seconds` in `argo-rollouts/patches.ts`). The plugin's `--in` delay is not offered. Restart is not one of the Rollout dialogs of this ADR: it is the generic Restart action (ADR-0112), so that several Rollouts — and the ReplicaSets a Rollout owns — restart from one selection; its confirmation lists the patch with the time as of opening and says the time of sending is used, and it reads the Rollout again (same uid, not being deleted) right before sending. The patch is sent once, through `resource_patch`, within CHANGE_TIMEOUT.
