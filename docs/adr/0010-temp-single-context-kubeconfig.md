# ADR-0010: Терминал и `helm` получают временный kubeconfig с одним контекстом

## Контекст

Кластеры приходят из нескольких источников: несколько файлов в `KUBECONFIG`, добавленные файлы и вставленный текст в каталоге данных приложения. Несколько кластеров подключены одновременно (R06i.5).

## Решение

Для локального терминала и для вызовов `helm` Sextant пишет временный kubeconfig с единственным выбранным контекстом (он же текущий), с правами 0600, и направляет на него `KUBECONFIG` или `--kubeconfig`. Пользовательские файлы не меняются.

## Почему

- Переключение current-context в пользовательском kubeconfig отвергнуто: в материалах это прямо не обсуждается, но оно ломается при двух одновременных терминалах на разные кластеры и меняет файл, который принадлежит пользователю. Вставленные источники вообще лежат у приложения.
- Передача `--kube-context` с исходным набором файлов отвергнута: контекст может быть собран из нескольких файлов, и единая копия проще для терминала и `helm` одновременно.
- `kubectl config current-context` в терминале должен показывать выбранный кластер: это критерий приёмки R11i.2.

## Последствия

- Учётные данные кластера (сертификаты, токены) копируются во временный файл на диске. Защита держится на правах 0600, а на Windows они не действуют так же, и как это закрыто, в материалах не описано.
- Файл должен жить столько же, сколько сессия, и исчезнуть после неё. При аварийном завершении приложения он может остаться.
- `kubectl config use-context` в терминале меняет только временную копию, поэтому после перезапуска терминала выбор вернётся к кластеру из рейла.
- На Unix оболочка запускается как login-shell. Если её профиль сам переопределяет `KUBECONFIG`, терминал будет смотреть не на тот кластер. В материалах это не проверялось.
- Любая новая фича, запускающая внешний процесс против кластера, берёт ту же функцию, а не строит свой kubeconfig.
