# ADR-0096: The traffic graph reads edges from the request sources' Prometheus metrics, through fixed, bounded queries

## Context

#211 asked for a live graph of requests between services — who calls whom, how much, how many fail and how slow — for clusters that already collect it (Cilium Hubble, Istio, Linkerd, Grafana Beyla), as a "Traffic" mode of the resource map (#139) sharing its layout and bounds, with filters by namespace, protocol and status class, a window of 5 minutes or an hour, at most N namespaces, fixed queries built in the core, polling only while the page is open, and no MCP tool. #212 (ADR-0095) already finds the request-metric sources in Prometheus and owns their per-source queries.

## Decision

- **Prometheus only, also for Hubble.** Every source is read through the Prometheus that #212 finds (`request_sources`, the same cache per connection); for Linkerd also linkerd-viz's own. There is no Hubble Relay client: Relay is a gRPC stream of raw flows that Sextant would have to reach (a port-forward or a service proxy that does not carry HTTP/2 gRPC), aggregate itself and hold in memory for the whole window, with its own TLS and a new protocol dependency; Hubble's metrics already are that aggregation, bounded by Prometheus. A cluster with Hubble but without `hubble_http_*` metrics in Prometheus has "no source", and the page says which metrics would give one.
- **Detection extends ADR-0095's known names**: an edge source needs metrics that name both ends. `RequestSourceKind::edge_metrics` adds `istio_tcp_connections_opened_total` and Beyla's `traces_service_graph_request_{server,client}_seconds_{count,bucket}` to the names asked by `match[]` (17 in all); `RequestSources.edges` lists the edge sources with whether their histogram exists. ingress-nginx names no caller and has no edges; it, and Beyla without its service graph, are listed as `requestOnly` in the "no source" state.
- **What an edge is, per source** (caller → callee; every row is summed by the source's own labels, and a table per part tells which of them name which end — renaming them all into one label set by `label_replace` was the first version, and made every URL kilobytes longer):

  | Source | Series | Caller | Callee | Protocol | Error | Latency |
  |---|---|---|---|---|---|---|
  | Istio | `istio_requests_total{reporter="destination"}`; and `{reporter="source",destination_workload="unknown"}` (a callee without a proxy, which has no callee report) | `source_workload(_namespace)` (`unknown` → unknown) | `destination_workload(_namespace)`; for the second, the Service `destination_service_name/_namespace` | `request_protocol` (http, grpc) | ADR-0095's: 5xx, or a non-OK `grpc_response_status` | `istio_request_duration_milliseconds_bucket` |
  | Istio TCP | `istio_tcp_connections_opened_total`, the same two ways | same | same | tcp (new connections per second) | — | — |
  | Linkerd | `response_total{direction="outbound"}` (the caller's proxy) | `namespace` + `deployment`/`statefulset`/`daemonset` | `dst_namespace` + `dst_deployment`/`dst_statefulset`/`dst_daemonset`, else the Service `dst_service` | grpc when `grpc_status` is set, else http | `classification="failure"` | `response_latency_ms_bucket` |
  | Linkerd, callers without identity | `response_total{direction="inbound",tls!="true"}` (no outbound report of theirs exists) | unknown | the receiving workload | same | same | same |
  | Linkerd TCP | `tcp_open_total{direction="outbound",peer="dst"}` | as outbound | as outbound | tcp | — | — |
  | Beyla | its service graph (`application_service_graph`): `traces_service_graph_request_server_seconds_count`, and `…_client_seconds_count` for the pairs without a server report | `client`, `client_service_namespace` | `server`, `server_service_namespace` | not told | the share `traces_service_graph_request_failed_total` ÷ the spans of both sides | `…_server_seconds_bucket`, the client's where no server reports |
  | Hubble | `hubble_http_requests_total{reporter!="client"}` (the callee's report), and `{reporter="client"}` for the pairs without one (egress-only visibility, a callee outside the cluster) | `source_namespace`, `source_workload` | `destination_namespace`, `destination_workload` | http | the `5xx` class (`status=~"5.."`) | `hubble_http_request_duration_seconds_bucket`, the same two ways |

  Each call is counted once: the parts of a source pick disjoint series (the callee's report; the caller's only where no callee report exists). Where both ends report into the same metric family (Hubble, Beyla), one part takes the callee's series and adds the caller's with `or on(<the pair's labels>)` — by PromQL's definition `callee or (caller unless on(<pair>) callee)`, without repeating the callee's expression; at the workload-pair granularity of an edge. Beyla's span metrics (`http_server_*`, `http_client_*`) name only the instrumented side and the peer as an address, so they make no edge; its service graph does. `traces_service_graph_request_total` is not read: Beyla 2.0–2.2 add every client and every server span to it (`grafana/beyla` `pkg/export/prom/prom.go`, v2.0.0 and v2.1.0: `serviceGraphTotal…Add(1)` after either histogram), so a call between two instrumented services counts twice, while OBI, which Beyla now builds on (`open-telemetry/opentelemetry-ebpf-instrumentation` `pkg/export/prom/prom.go`, main), adds a client span only when `ClientSpanToUninstrumentedService`. The server histogram's count plus the client's for pairs without a server report is the same number under both. The failed counter counts failed spans of both sides under both, so the error share is failed ÷ (server + client spans). Hubble needs `labelsContext` with the workload labels (as in ADR-0095); its L4 flow metrics are counted at both ends of a flow, so Hubble has HTTP edges only. A TCP edge is dropped where the same source has an HTTP or gRPC edge between the same ends (the same traffic seen as connections).
- **Unknown ends are nodes, never dropped.** An end without a name (Istio's `unknown`, an empty label, a caller without a mesh identity, a callee outside the cluster) is an "Outside the mesh or unlabelled" node — one per namespace when the source tells the namespace, else one. A Service end (a host, for Istio) is a Service node. Status classes `2xx`…`5xx` come from the HTTP status label where the source has one (Istio `response_code`, Linkerd `status_code`, Hubble `status`).
- **Fixed, bounded queries.** The window is `minutes5` (`rate(...[5m])`) or `hour1` (`[1h]`). The caller names 1–`MAX_TRAFFIC_NAMESPACES` = 5 distinct DNS-1123 namespaces (`validate_namespaces`; escaped again as a literal regex); an edge is in scope when either end's namespace is one of them (one selector per namespace label, the same series from two of them counted once by `or`). The series keep the source's own labels (`sum by` them; only Linkerd's gRPC marker and the status class are added by `label_replace`); each part's `End` table says which label names which end. Each part is asked on its own (`timeout=18s`, client 20 s, ADR-0095's times): first `topk(MAX_TRAFFIC_EDGES = 200, rate > 0)` — the only query whose failure fails the source; only when it has edges, one query per detail — errors (a matcher of failures; for Istio the one-selector complement "not 5xx and no gRPC error", errors = requests − those; Hubble's are its 5xx class; Beyla's a share), status classes, p50, p95 — each filtered to non-zero values, so none returns more than the part's edges. Only a part whose busiest fill the cap gets its `count` asked and its details restricted to those edges (`and on(...) topk(...)`). A detail query that fails (a timeout, Prometheus' sample limit, the 8 MiB cap) leaves that detail unknown on the part's edges (`TrafficEdge.missing`: errors, classes, latency), which the view says. No URL repeats a part's expression more than twice: the longest query of any source with five 63-character namespaces is 5012 bytes percent-encoded, pinned at ≤ 5 KiB by a test, so the whole URL stays under 6 KiB through a service proxy path of the longest names — under nginx's default 8 KiB buffer (the first version measured 7–15 KiB). A Prometheus reached by its URL gets the same query again as a form `POST api/v1/query` after a 414 or 431; through the API server's service proxy a POST would need the `create` verb on `services/proxy`, so there the error says "the query was too long for a proxy in front of Prometheus" and the source is listed in `queryTooLong` as well as `failed`. Every answer is read up to `MAX_TRAFFIC_BODY` = 8 MiB (a bigger one is an error, never cut) and at most `MAX_TRAFFIC_SERIES` = 4000 series of it; the sources' edges are merged, busiest first, and cut to 200 again with `totalEdges` telling how many there are ("Showing the 200 busiest of N"). A source whose edge query fails is in `failed` (its edges unknown, not absent).
- **Window only, read-only.** `metrics_traffic_graph(clusterId, namespaces, window)` changes nothing and needs only `services/proxy` on the Prometheus Services; MCP agents and extensions get no tool or method (test in `src-tauri/src/commands/metrics.rs`).
- **The view.** A "Traffic" tab beside "Objects" on the map page (`src/features/resource-map/traffic/`): the map's namespace filter (the first 5; the object map keeps 3, since the traffic graph draws only the workloads that talk), its column layout (`placeColumns` in `layout.ts`, callers left, one column per hop from the nearest node nobody calls) and node boxes. A line is as thick as its request rate (log scale) — per pair of ends the busiest source's requests per second (each source's HTTP, gRPC and unreported-protocol edges added up), never the sum of two sources (Istio and Hubble on Cilium see the same calls); TCP connections per second are another unit, kept apart (`tcpRate`, named beside the rate; a pair seen only as connections is drawn thinnest) — and coloured by its error share through theme tokens (`--color-success` under 1 %, `--color-warning` to 5 %, `--color-danger` above, dashed `--color-control-border` when unknown); edges between the same two ends are one line. Filters (namespace, protocol, status: failed / 5xx / 4xx / 2xx) only change the drawing. A node is a button showing its calls; a line opens the call with both ends: "Open" looks the name up as a Deployment, StatefulSet, then DaemonSet (or the Service) with at most three GETs on the click — never a watch, and only for a name the kind can have (a DNS-1123 subdomain, a Service's DNS-1035 label, a DNS-1123 namespace: a label value can be anything); "not found" is kept for a minute, since the object may be created; an end named without a namespace (an Istio host) says so instead of offering to open it — and "Requests of" opens the details at the #212 section. A "List" tab is the same calls as a table, the way for the keyboard and screen readers (the drawn lines are hidden from them). Polling through the metrics feature's shared pollers every 30 s (5 minutes) or 60 s (an hour), a tick skipped while the previous load is in flight (no overlapping rounds against a slow Prometheus), only while the mode is shown and the window is visible (`visibilitychange`). Without Prometheus or a source, the page says what would provide the graph; Sextant installs and enables nothing.

## Why

- Prometheus is where all four sources already aggregate; reading it keeps one access path, one set of bounds and no new protocol.
- One table per part (labels of each end, protocol, what an error is) makes one parser, one `topk` and one `and on(...)` restriction work for all, and lets a fixture of each source be checked by the same code, without renaming labels in the query (which a proxy's URL limit cannot afford).
- Looking an end up on a click costs nothing while the user only looks; watching the workload lists of every namespace a peer lives in would be unbounded.

## Consequences

- The fixtures in `crates/sextant-core/src/metrics/traffic/testdata/` (and `metrics/requests/testdata/hubble-*.json`) are what a real Prometheus 3.15 answered to these queries over the synthetic series each file lists (loaded by `promtool tsdb create-blocks-from openmetrics`; Hubble with L7 visibility at the callee only, the caller only and both; Beyla with a pair instrumented at both ends); a test fails when a query no longer matches its fixture's, and the ignored `write_fixture_queries` writes the queries to regenerate them; `tests/traffic_metrics.rs` checks every query is accepted by the kind cluster's Prometheus.
- Label names are fixed here; a scrape that renames them (or a Linkerd without `response_total`) gives no edges of that source.
- Workload names are what the source says (Istio's `destination_workload`, Linkerd's owner labels, Beyla's service name, Hubble's workload label); one that names no Deployment, StatefulSet or DaemonSet opens nothing, and the panel says so.

Amended (review of v0.17.0): only the edge query fails a source, the details are best-effort (`missing`); queries per part keep the source's labels and stay under 6 KiB of URL, with a form POST after 414/431 for a Prometheus reached by URL and `queryTooLong` otherwise; Hubble and Beyla count the callee's report and the caller's only for pairs without one; Beyla no longer reads `traces_service_graph_request_total` (counted twice by Beyla 2.0–2.2, see above); a line's thickness is the busiest source's request rate with TCP apart; ends are looked up only by valid names, "not found" for a minute; the poller never overlaps its rounds.
