# ADR-0096: The traffic graph reads edges from the request sources' Prometheus metrics, through fixed, bounded queries

## Context

#211 asked for a live graph of requests between services — who calls whom, how much, how many fail and how slow — for clusters that already collect it (Cilium Hubble, Istio, Linkerd, Grafana Beyla), as a "Traffic" mode of the resource map (#139) sharing its layout and bounds, with filters by namespace, protocol and status class, a window of 5 minutes or an hour, at most N namespaces, fixed queries built in the core, polling only while the page is open, and no MCP tool. #212 (ADR-0095) already finds the request-metric sources in Prometheus and owns their per-source queries.

## Decision

- **Prometheus only, also for Hubble.** Every source is read through the Prometheus that #212 finds (`request_sources`, the same cache per connection); for Linkerd also linkerd-viz's own. There is no Hubble Relay client: Relay is a gRPC stream of raw flows that Sextant would have to reach (a port-forward or a service proxy that does not carry HTTP/2 gRPC), aggregate itself and hold in memory for the whole window, with its own TLS and a new protocol dependency; Hubble's metrics already are that aggregation, bounded by Prometheus. A cluster with Hubble but without `hubble_http_*` metrics in Prometheus has "no source", and the page says which metrics would give one.
- **Detection extends ADR-0095's known names**: an edge source needs metrics that name both ends. `RequestSourceKind::edge_metrics` adds `istio_tcp_connections_opened_total`, `traces_service_graph_request_total` and `traces_service_graph_request_server_seconds_bucket` to the names asked by `match[]` (15 in all); `RequestSources.edges` lists the edge sources with whether their histogram exists. ingress-nginx names no caller and has no edges; it, and Beyla without its service graph, are listed as `requestOnly` in the "no source" state.
- **What an edge is, per source** (caller → callee; every row is summed by the source's own labels, then renamed by `label_replace` into one set — `sx_sn`, `sx_s`, `sx_dn`, `sx_d`, `sx_dk`, `sx_p` — so all sources answer in one shape):

  | Source | Series | Caller | Callee | Protocol | Error | Latency |
  |---|---|---|---|---|---|---|
  | Istio | `istio_requests_total{reporter="destination"}`; and `{reporter="source",destination_workload="unknown"}` (a callee without a proxy, which has no callee report) | `source_workload(_namespace)` (`unknown` → unknown) | `destination_workload(_namespace)`; for the second, the Service `destination_service_name/_namespace` | `request_protocol` (http, grpc) | ADR-0095's: 5xx, or a non-OK `grpc_response_status` | `istio_request_duration_milliseconds_bucket` |
  | Istio TCP | `istio_tcp_connections_opened_total`, the same two ways | same | same | tcp (new connections per second) | — | — |
  | Linkerd | `response_total{direction="outbound"}` (the caller's proxy) | `namespace` + `deployment`/`statefulset`/`daemonset` | `dst_namespace` + `dst_deployment`/`dst_statefulset`/`dst_daemonset`, else the Service `dst_service` | grpc when `grpc_status` is set, else http | `classification="failure"` | `response_latency_ms_bucket` |
  | Linkerd, callers without identity | `response_total{direction="inbound",tls!="true"}` (no outbound report of theirs exists) | unknown | the receiving workload | same | same | same |
  | Linkerd TCP | `tcp_open_total{direction="outbound",peer="dst"}` | as outbound | as outbound | tcp | — | — |
  | Beyla | its service graph: `traces_service_graph_request_total` (`application_service_graph`) | `client`, `client_service_namespace` | `server`, `server_service_namespace` | not told | `traces_service_graph_request_failed_total` | `traces_service_graph_request_server_seconds_bucket` |
  | Hubble | `hubble_http_requests_total{reporter!="client"}`; and `{reporter="client",destination_workload=""}` (a callee outside the cluster) | `source_namespace`, `source_workload` | `destination_namespace`, `destination_workload` | http | `status=~"5.."` | `hubble_http_request_duration_seconds_bucket` |

  Each call is counted once: the alternatives of a source pick disjoint series (the callee's report; the caller's only where no callee report exists). Beyla's span metrics (`http_server_*`, `http_client_*`) name only the instrumented side and the peer as an address, so they make no edge; its service graph does. Hubble needs `labelsContext` with the workload labels (as in ADR-0095); its L4 flow metrics are counted at both ends of a flow, so Hubble has HTTP edges only. A TCP edge is dropped where the same source has an HTTP or gRPC edge between the same ends (the same traffic seen as connections).
- **Unknown ends are nodes, never dropped.** An end without a name (Istio's `unknown`, an empty label, a caller without a mesh identity, a callee outside the cluster) is an "Outside the mesh or unlabelled" node — one per namespace when the source tells the namespace, else one. A Service end (a host, for Istio) is a Service node. Status classes `2xx`…`5xx` come from the HTTP status label where the source has one (Istio `response_code`, Linkerd `status_code`, Hubble `status`).
- **Fixed, bounded queries.** The window is `minutes5` (`rate(...[5m])`) or `hour1` (`[1h]`). The caller names 1–`MAX_TRAFFIC_NAMESPACES` = 5 distinct DNS-1123 namespaces (`validate_namespaces`; escaped again as a literal regex); an edge is in scope when either end's namespace is one of them (one selector per namespace label, the same series from two of them counted once by `or`). Per source, at most five instant queries (`timeout=18s`, client 20 s, ADR-0095's times): first `topk(MAX_TRAFFIC_EDGES = 200, rate > 0)` with `count`; only when it has edges, `errors`, `class`, `p50`, `p95`, each restricted to those edges by `and on(...) topk(...)`. Separate queries keep each URL to a few KiB (≤ 16 KiB with five 63-character names, a test) where one query would repeat the edge expression six times (~30 KiB). Every answer is read up to `MAX_TRAFFIC_BODY` = 8 MiB (a bigger one is an error, never cut) and at most `MAX_TRAFFIC_SERIES` = 4000 series of it; the sources' edges are merged, busiest first, and cut to 200 again with `totalEdges` telling how many there are ("Showing the 200 busiest of N"). A source whose query fails is in `failed` (its edges unknown, not absent).
- **Window only, read-only.** `metrics_traffic_graph(clusterId, namespaces, window)` changes nothing and needs only `services/proxy` on the Prometheus Services; MCP agents and extensions get no tool or method (test in `src-tauri/src/commands/metrics.rs`).
- **The view.** A "Traffic" tab beside "Objects" on the map page (`src/features/resource-map/traffic/`): the map's namespace filter (the first 5; the object map keeps 3, since the traffic graph draws only the workloads that talk), its column layout (`placeColumns` in `layout.ts`, callers left, one column per hop from the nearest node nobody calls) and node boxes. A line is as thick as its rate (log scale) and coloured by its error share through theme tokens (`--color-success` under 1 %, `--color-warning` to 5 %, `--color-danger` above, dashed `--color-control-border` when unknown); edges between the same two ends are one line. Filters (namespace, protocol, status: failed / 5xx / 4xx / 2xx) only change the drawing. A node is a button showing its calls; a line opens the call with both ends: "Open" looks the name up as a Deployment, StatefulSet, then DaemonSet (or the Service) with at most three GETs on the click — never a watch — and "Requests of" opens the details at the #212 section. A "List" tab is the same calls as a table, the way for the keyboard and screen readers (the drawn lines are hidden from them). Polling through the metrics feature's shared pollers every 30 s (5 minutes) or 60 s (an hour), only while the mode is shown and the window is visible (`visibilitychange`). Without Prometheus or a source, the page says what would provide the graph; Sextant installs and enables nothing.

## Why

- Prometheus is where all four sources already aggregate; reading it keeps one access path, one set of bounds and no new protocol.
- Renaming every source into one label set makes one parser, one `topk` and one `and on(...)` restriction work for all, and lets a fixture of each source be checked by the same code.
- Looking an end up on a click costs nothing while the user only looks; watching the workload lists of every namespace a peer lives in would be unbounded.

## Consequences

- The fixtures in `crates/sextant-core/src/metrics/traffic/testdata/` are what a real Prometheus (promtool, 3.15) answered to these queries over synthetic series of each source; `tests/traffic_metrics.rs` checks every query is accepted by the kind cluster's Prometheus.
- Label names are fixed here; a scrape that renames them (or a Linkerd without `response_total`) gives no edges of that source.
- Workload names are what the source says (Istio's `destination_workload`, Linkerd's owner labels, Beyla's service name, Hubble's workload label); one that names no Deployment, StatefulSet or DaemonSet opens nothing, and the panel says so.
