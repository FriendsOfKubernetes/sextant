# ADR-0122: vcluster is connected as `vcluster connect` does, through a port forward whose kubeconfig entry lives only as long as the forward

## Context

#269: teams run virtual clusters (loft-sh/vcluster) inside a host cluster, one per namespace. Using one in Sextant meant running `vcluster connect` in a terminal, which writes a context into `~/.kube/config` and keeps a port forward open while the terminal stays. Sextant already connects to the host; it can find the instances there and connect to one on a click, as long as the virtual cluster's admin credentials never reach the window and nothing happens without the user.

What vcluster puts on the host (github.com/loft-sh/vcluster, `main`):

- The control plane is a StatefulSet or a Deployment named `<release>` with the labels `app: vcluster`, `release: <release>` (`chart/templates/statefulset.yaml`; `vcluster.kind` chooses the kind); its pods carry `app: vcluster`, `release: <release>`. The CLI lists instances by the label selector `app=vcluster` on both kinds and takes the name from `release` (`pkg/cli/find/find.go`: `VirtualClusterSelector`, `findInContext`). The external etcd is a separate StatefulSet labelled `app: vcluster-etcd` (`chart/templates/etcd-statefulset.yaml`), so the selector does not catch it.
- A paused instance has the annotation `loft.sh/paused: "true"` or the label `loft.sh/sleep-mode: "true"`; a scaled-down one has `spec.replicas: 0`; the version is the tag of the `syncer` container's image (`find.go` `getVCluster`, `isScaledDown`; `pkg/constants/annotation.go` `PausedAnnotation`).
- The Service is `<release>` with port `https` 443 → `targetPort` 8443 and the same selector (`chart/templates/service.yaml`).
- The syncer writes the virtual cluster's kubeconfig into the Secret `vc-<release>` in the host namespace under the key `config` (also `certificate-authority`, `client-certificate`, `client-key`, `token`; labels `app: vcluster`, `vcluster-name`) — `pkg/setup/controllers.go` `WriteKubeConfigToSecret` → `pkg/util/kubeconfig/kubeconfig.go` (`DefaultSecretPrefix` `vc-`, `KubeconfigSecretKey` `config`, `WriteKubeConfig`, `ReadKubeConfig`). Its server is `https://localhost:8443` unless `exportKubeConfig.server` says otherwise. `vc-config-<release>` is a different Secret (the vcluster.yaml) and is never read here.
- `vcluster connect` (`pkg/cli/connect_helm.go`): finds the newest pod `app=vcluster,release=<name>` that is not being deleted, reads `vc-<name>`, requires exactly one cluster in it, renames the context, cluster and user to `vcluster_<name>_<namespace>_<host context>` (`exchangeContextName`, `find.go` `VClusterContextName`), forwards a random local port to the pod's port (the server's explicit port, else 8443: `portForwardServer`, `serverPort`) and rewrites the server to `https://localhost:<local port>`.
- The API server's serving certificate names `localhost` and `127.0.0.1` among its SANs (`pkg/server/cert/cert.go`).
- Objects the syncer copies to the host carry the label `vcluster.loft.sh/managed-by: <release>` (`MarkerLabel`), the virtual namespace in `vcluster.loft.sh/namespace` and the annotations `vcluster.loft.sh/object-name`, `vcluster.loft.sh/object-namespace`, `vcluster.loft.sh/object-kind` (`pkg/util/translate/types.go`, `translate.go`, `labels.go`).

## Decision

- **Found in the window, read-only.** The page "Virtual clusters" (Cluster section, `src/features/vcluster/`) lists StatefulSets and Deployments by the API server's own selector `app=vcluster` (≤ 500 each) in the namespaces of the filter, or cluster-wide with "All namespaces" (a list the user may not read says so and asks for a namespace choice). An object with the `managed-by` label is never a control plane. For the first 40 namespaces holding an instance it watches the control-plane pods (`app=vcluster`, ≤ 2000), the Services (same selector, metadata only) and the Secrets (metadata only, ≤ 5000; no value crosses into the window) to show ready pods, whether `<name>` and `vc-<name>` exist, or "cannot tell" when a list is unreadable, capped or beyond the 40. The details of a control-plane StatefulSet or Deployment add the "vcluster" section: the same state (Service and Secret looked up by `metadata.name`, metadata only) and the synced objects of seven kinds (Pod, Service, ConfigMap, Secret, PersistentVolumeClaim, ServiceAccount, Ingress) by `vcluster.loft.sh/managed-by=<name>` in its namespace, metadata only, ≤ 500 per kind, 50 shown, each with the virtual name and namespace it stands for.
- **Connect only on a click, after a confirmation** that names the Secret it reads, the host the forward goes through, the context it adds and how long the entry lasts. Window-only command `vcluster_connect(hostClusterId, namespace, name)`:
  1. checks the names (DNS-1123 labels) and that the host is connected;
  2. `sextant_core::vcluster::read_kubeconfig` reads `vc-<name>` with the user's own credentials (`get` on that Secret; forbidden and missing are errors that name the Secret), overwrites every other value of the Secret as soon as it is read, and parses `config` (≤ 256 KiB): exactly one cluster; the current context's user. It keeps only the cluster's `certificate-authority-data`, `insecure-skip-tls-verify` and `tls-server-name`, the user's `client-certificate-data`, `client-key-data` and `token`, and the context's namespace. **A kubeconfig that names a file (CA, client certificate, key, token file), an exec plugin or an auth provider is refused**: it is cluster content that anyone able to write the Secret controls, and Sextant never runs a program or reads a local file because of it. `proxy-url` and every other field are dropped. Errors never quote the text;
  3. `forward_target` picks the Service `<name>` and its port whose `targetPort` is the pod's port (or the one named `https`) — a Service forward moves to another ready pod by itself — and without one the newest live control-plane pod at that port, as the CLI does;
  4. the forward is an ordinary entry of `AppState.forwarder` (`PodFilter::Any`, the user's own action), so it shows in Port forwarding, and the forwarder already closes it when the host disconnects and on exit;
  5. the entry `vcluster_<name>_<namespace>_<host context>` with server `https://127.0.0.1:<local port>` and `tls-server-name: localhost` (unless the Secret named one) goes into this process's own `kubeconfigs/vcluster-<pid>.yaml` (0600, written atomically, an entry of the same name replaced), listed once as a new source kind `SourceKind::Vcluster` — one of Sextant's own files (`is_own`, `remove_source` deletes it), listed like the cloud files but **never stored in the settings** (`KubeconfigRegistry::added_sources` leaves it out) and never edited through the kubeconfig dialogs (`ensure_writable` refuses it). Whatever fails after the forward started (the file write, the forward ending at once) stops the forward and removes the entry, so no forward runs and no entry stays without a link. A second Connect of the same virtual cluster while one runs is a `conflict` (`VclusterLinks::begin`); a link that is replaced anyway has its forward stopped. `127.0.0.1` because the forward listens only there (`localhost` may resolve to `::1` first) and `localhost` as the TLS name because every vcluster certificate has it.
  The window then reads the cluster list again; "Open" connects the virtual cluster like any other. Credentials exist only in the core and that file; the window gets `VclusterLink` (ids, names, local port, forward id).
- **The entry lives exactly as long as its forward.** `AppState.vcluster` (`VclusterLinks`, `src-tauri/src/commands/vcluster.rs`) maps each entry to its forward; a task follows the forwarder's list and, when a link's forward is gone (stopped by the user in Port forwarding or by "Disconnect", the host disconnected, the app exiting; a forward in error stays listed and recovers as port forwards do), disconnects the virtual cluster, removes its entry (the source and file go with the last one) and emits `vcluster-links`, on which the window reads the cluster list again. The task reads the forwarder's list when a change is announced, under the links' lock, never the list the announcement carried: one published before a new forward started would end that forward's fresh link. Connecting again replaces the forward and the entry and disconnects the virtual cluster first (its old address is gone). Closing the window or the app removes this process's file at once (`AppState::close_all` → `commands::vcluster::close_all` → `vcluster::forget_own`, after the forwarder stopped every forward), so the credentials do not wait on disk for the next start. At start, `AppState::new` (`forget_earlier_run` → `vcluster::forget_earlier_runs`) removes only what cannot belong to a live process: `vcluster-<pid>.yaml` files of PIDs that no longer run (a crash; the same test as the terminal's `sextant-kubeconfig-<pid>-*` files, `kubeconfig::process_runs`, which keeps a file when it cannot tell), a file carrying this process's own PID (an earlier process had it), and the single `vcluster.yaml` with its stored source that builds before this amendment wrote. Another running Sextant's file and entries stay — a development or e2e build runs beside an installed Sextant on the same settings directory, since single instance is release-only (ADR-0060). After a restart the user connects again from the host's page. The entry's `ClusterId` is made from `kubeconfigs/vcluster.yaml` (the same name in every run and process, `vcluster::cluster_id`) and the context name, not from the per-process file, so its cluster settings (icon, agent access, …) come back with it; two processes never list each other's file, so the shared id never collides.
- **Nothing automatic.** No host is connected for the user, no vcluster is resumed (the CLI resumes a paused one; Sextant only shows "Paused"), no background proxy container, no `~/.kube/config` write.
- **Agents and extensions get nothing new**: `vcluster_*` are window-only (test in `src-tauri/src/commands/vcluster.rs`). A connected virtual cluster is an ordinary cluster of the list; its agent access is closed by default like any other.

## Why

- Keeping the entry after the forward ends (and re-establishing the forward when the saved entry is clicked) was considered: it would need the connect path of every cluster to know about vcluster, to connect the host or to show "Connect through <host>" from the rail. A dead entry pointing at a closed local port would otherwise fail with "connection refused". Tying the entry to the forward is simpler and never lists a cluster that cannot be reached; one click on the host's page brings it back with the same id.
- Taking the Secret's kubeconfig as it is (as `vcluster connect` does) was rejected for the exec/file fields above: the CLI runs as the user who chose to connect to that Secret's content too, but Sextant's rule is that cluster content never makes it run anything.
- The service proxy cannot carry the virtual cluster's client-certificate authentication (the host API server terminates TLS), so a port forward it is, as the CLI does.

## Consequences

- Without `get` on `vc-<name>` (a namespaced developer role often has it; a read-only one does not) Connect fails with a clear `forbidden`.
- A vcluster exported with a different server (`exportKubeConfig.server`, an ingress) is still reached through the forward; its explicit port is taken as the pod's port, as the CLI does.
- vcluster platform (`VirtualClusterInstance`) and standalone (systemd) vclusters are not handled; multi-namespace sync mode shows only the synced objects of the vcluster's own namespace.
- Removing the "virtual clusters" source in Settings deletes the file but leaves the forwards running until stopped (the confirmation says so).
- Amended after the 0.25.0 review: one file per process (`vcluster-<pid>.yaml`), never stored in the settings, removed on close and, after a crash, at the next start of any Sextant; nothing of an earlier run is ever merged into a new entry. The file name is not part of the id (`id_path` in `kubeconfig.rs` makes a `Vcluster` source's ids from `vcluster.yaml`), which is why the kubeconfig edit dialogs refuse that file: an edit would compute ids from its real path. A new id per run was the alternative and was rejected: per-cluster settings would not come back and would pile up under ids nothing lists.
