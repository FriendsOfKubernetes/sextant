# ADR-0123: k3s and RKE2 views recognise the distribution from node fields, read helm-controller charts with their Jobs, and never show node or chart secrets

## Context

#270 asks to recognise k3s and RKE2, show their bundled components (Traefik, ServiceLB, the local-path provisioner, CoreDNS, metrics-server; RKE2's `rke2-*` charts) with a readable state, and show helm-controller's HelmCharts and HelmChartConfigs with their install Jobs and logs. Both distributions run the same server code (RKE2 embeds k3s with `version.Program` = "rke2"), so every name below is `<program>`-parameterised upstream. Two kinds of text from these objects can hold credentials: a node's arguments (`--token`, `--datastore-endpoint=postgres://user:pass@…`, `--etcd-s3-secret-key`) and a chart's values.

A page "only when the cluster is recognised" has no gate in the sidebar other than discovered sections (a page in a discovered section shows only while the section has a served kind); the cluster overview has no registration slot.

## Decision

- **Two discovered sidebar sections.** `k3s` ("k3s / RKE2": the "Distribution" page, Addons, etcd Snapshots) is shown while the cluster serves `k3s.cattle.io` Addons or ETCDSnapshotFiles, which a k3s or RKE2 server always creates (k3s-io/api `k3s.cattle.io/v1/types.go`); `helmController` ("helm-controller": HelmCharts, HelmChartConfigs) while it serves `helm.cattle.io`. So the page appears on a k3s or RKE2 cluster and nowhere else, without a new sidebar gate. The page lives in the `k3s` section rather than "Cluster" for that reason.
- **Recognition is per node, pure, and ordered by trust** (`nodeDistributionOf`): the kubelet version suffix `+k3s<n>` / `+rke2r<n>`; the annotations `<program>.io/node-args|node-env|node-config-hash` (k3s `pkg/nodeconfig/nodeconfig.go`) and `<program>.io/hostname|internal-ip|external-ip` (`pkg/cloudprovider/instances.go`); `spec.providerID` `<program>://` and the label `node.kubernetes.io/instance-type=<program>` (both from the embedded cloud controller, absent with `--disable-cloud-controller`, the label overridable). The first signal decides; the details name the signals that agree. Roles: `node-role.kubernetes.io/control-plane` (servers, `pkg/server/server.go`), `/etcd` (embedded etcd, `pkg/util/labels.go`), `/master` (older servers); a node whose arguments start with `server` is a server too. `etcd.<program>.cattle.io/node-name` names the etcd member (`pkg/etcd/etcd.go`). "Embedded etcd" is said only when a node has the etcd role; otherwise "SQLite or an external datastore", never which.
- **Node arguments never show a secret value.** k3s already replaces the value after its own secret flags with `********` (`isSecret`: `--token`, `-t`, `--agent-token`, `--datastore-endpoint`, `--etcd-s3-access-key`, `--etcd-s3-secret-key`, `--vpn-auth`), but older releases did not and a setting passed through `--kube-apiserver-arg` is never masked there. Sextant (`k3s/mask.ts`) hides — showing the flag and "hidden" — the value of each of those flags, of every flag whose name looks secret (`looksSecret`, shared with the KubeRay views), of every `*-arg` flag whose `name=value` names a secret-looking setting, and k3s's mask itself; every other value has its URI-looking parts cleaned of credentials (`cleanText`). An annotation that is not a JSON array of strings, or longer than 64 KiB, is "cannot be read", never shown raw. `node-env` is not shown.
- **Bundled components by the names upstream gives them**: k3s's manifests (`manifests/coredns.yaml` → Deployment `coredns`, `local-storage.yaml` → `local-path-provisioner`, `metrics-server/` → `metrics-server`, `traefik.yaml` → HelmCharts `traefik-crd`, `traefik`), each applied as an Addon named after the file's basename (`pkg/deploy` `basename`) that owns what it applied through wrangler's `objectset.rio.cattle.io/owner-gvk|owner-name|owner-namespace` annotations; RKE2's HelmCharts `rke2-*` in kube-system (`rancher/rke2` `charts/chart_versions.yaml`). A chart's workloads are the kube-system Deployments and DaemonSets whose Helm annotation `meta.helm.sh/release-name` is the chart's name (helm-controller installs the release under the HelmChart's name), so `rke2-coredns-rke2-coredns` (the RKE2 chart's fullname, `rke2-charts` `_helpers.tpl` patch) needs no name table. ServiceLB DaemonSets are recognised by `svccontroller.<program>.cattle.io/svcname` and `/svcnamespace` (`pkg/cloudprovider/servicelb.go`), their Service read by name (≤ 50, `resource_get`) for `status.loadBalancer.ingress`. A k3s component that is missing is listed as "not found (disabled with --disable …?)"; an RKE2 chart that is missing is not listed (which ones exist depends on `--cni` and `--ingress-controller`).
- **A HelmChart's state** comes from helm-controller's own conditions (`JobCreated`, `Failed`; `pkg/apis/helm.cattle.io/v1/types.go`, no time on them) and its Job (`helm-install-<name>` / `helm-delete-<name>` in the chart's namespace, labelled `helmcharts.helm.cattle.io/chart=<name>`, `pkg/controllers/chart/chart.go`): failed (the condition, or the Job's Failed condition), retrying (the Job runs again after failed pods), installing, deployed (the Job completed), deleting, "Job created" (all a table row knows without the Job), no status (older helm-controller). "Logs" opens the merged logs tab of the pods selected by that label.
- **Values are shown masked and folded.** `valuesContent`, `values` and `set` are parsed; a value under a secret-looking key is `<hidden>`, other strings are cleaned; text that does not parse as one YAML mapping (or over 256 KiB) is not shown at all. `valuesSecrets`, `authSecret` and `dockerRegistrySecret` are links by name with key names only; no Secret is read. Values never reach a problem, a notification or a log.
- **Problems `k3s`, on by default**: a HelmChart whose install failed, from the Job's failure for a day (with only helm-controller's condition, while it holds); a HelmChart whose Job still runs after 3 failed pods, after 5 minutes (helm-controller's default `backOffLimit` is 1000, so a broken chart may never end Failed); a known component's kube-system Deployment not available, 10 minutes after its Available condition went False. One provider (`external`, held only where HelmCharts are served) watches HelmCharts (≤ 500), the Jobs labelled `helmcharts.helm.cattle.io/chart` (label selector on the API server, ≤ 1000) and, only where Addons are served too, kube-system's Deployments (≤ 1000). In `NEVER_FOR_AGENTS`; the counters split the category: HelmCharts on "helm-controller", components on "k3s / RKE2".
- **etcd snapshots** (cluster-scoped ETCDSnapshotFile) are a table and details: node, S3 or local, size, creation time, ready, error — `location` and the error cleaned of credentials. No snapshot is a problem.
- Read-only: no new command, the kinds offer the generic Edit and Delete only; agents and extensions get nothing new.

## Why

- Ordering the signals keeps recognition stable when one is missing (no cloud controller, an overridden instance type) and makes a mixed cluster visible ("k3s and RKE2 nodes") instead of guessed.
- Masking again in Sextant, more widely than k3s does, because the annotation's masking is release-dependent and covers only k3s's own flags; showing the flag name keeps the arguments useful.
- Matching chart workloads by Helm's release annotation rather than by Deployment names: chart fullnames differ per chart and release, while the annotation is set by Helm on every object it installs.
- The retrying problem exists because a failing chart with the default backoff limit retries for days without ever ending Failed.

## Consequences

- A cluster whose k3s server runs with `--disable-helm-controller` gets no `k3s` problems (the source is held on HelmCharts).
- The component problem overlaps the generic `workloads` problem for the same Deployment; it names the component and comes later (10 minutes).
- The Metadata section of a Node shows `<program>.io/node-args` and `<program>.io/node-env` masked by the rules above (`shownAnnotation` in `src/features/details/secrets.ts`: a secret flag's or a secret-looking variable's value `<hidden>`, other values cleaned, text that does not read hidden whole); the YAML section shows the object as stored.
- ServiceLB DaemonSets of releases that created them in the Service's own namespace (before `--servicelb-namespace`) are not listed: only kube-system is watched.
- Tests: `src/features/k3s/k3s.test.tsx` (recognition table, argument masking table, values masking, chart and component models, problems, sidebar presence and absence, details, the page, axe); fixtures `src/features/k3s/fixtures/objects.json`; `k3s_problems_are_never_given_to_agents` in `src-tauri/src/mcp/tools_diagnose/tests.rs`.
- **Node and chart secrets leave the window only hidden** (amendment after the 0.25.0 review). The annotations `k3s.io/node-args`, `rke2.io/node-args`, `k3s.io/node-env`, `rke2.io/node-env` (pkg/nodeconfig/nodeconfig.go), a HelmChart's `spec.valuesContent` and `spec.set` and a HelmChartConfig's `spec.valuesContent` (helm-controller pkg/apis/helm.cattle.io/v1/types.go) are rows of the core's table of inline secret paths (`crates/sextant-core/src/resources/inline_secrets.rs`, `src/resources/inline-secrets.json`; ADR-0120 has the rules): an agent's `get_resource` gets them only with "Secret values" on the kind, `list_resources`, `patch_resource` and dry runs never, an extension never (a hidden annotation is `""`, a `set` map keeps its keys); the change timeline keeps and shows their paths only.
