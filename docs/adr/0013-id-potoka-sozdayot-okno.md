# ADR-0013: Id потока создаёт окно и слушает его до запуска

## Контекст

Подписку, логи и терминал запускало ядро, а окно подписывалось на события уже после ответа. Начало данных страховали паузами: 300 мс `LISTENER_GRACE` в логах, первый тик 250 мс в watch, копилка вывода терминала до первого resize или input.

## Решение

Окно создаёт id (`crypto.randomUUID()`), вешает `listen("<префикс>:<streamId>")` и только потом вызывает `watch_start`, `logs_start`, `exec_start` или `terminal_start`, передавая `streamId` последним полем. Id принимается из символов `[A-Za-z0-9_-]` длиной до 128, занятый или неверный id даёт `invalid`. Паузы и копилка терминала убраны: первый снапшот уходит сразу, дальнейшие пачки — не чаще раза в 250 мс. Команда `streams_reset` останавливает все подписки, логи и терминалы (подключения и пробросы не трогает), окно вызывает её один раз при загрузке страницы до первого потока. Старт, переживший `streams_reset`, отклоняется кодом `other` и ничего не регистрирует.

Заменяет ADR-0004 в части «первая пачка приходит не раньше чем через 250 мс».

## Почему

- Пауза угадывает скорость окна: короткая теряет начало данных на медленном окне, длинная задерживает каждую первую таблицу и каждые логи. Оставить id у ядра и подобрать паузу отвергнуто: гарантии доставки это не даёт.
- Копилка на стороне ядра (так было у терминала) отвергнута: ей нужен сигнал готовности окна для каждого вида потока, а лимит в 1 МиБ отбрасывает старые данные. Для логов и таблицы такого сигнала не было вовсе.
- Слушатель до запуска — единственный способ доставить всё без пауз: события, отправленные сразу после старта, уже имеют получателя.

## Последствия

- Это смена сигнатур четырёх команд в IPC-контракте (ADR-0007): все вызывающие места и их тесты переписаны, тесты берут id из своего аргумента `streamId`.
- Любая новая разновидность потока обязана принимать `streamId` от окна и подключаться через `openStream`, где `listen` идёт до `start`. Регистрация в `AppState` по-прежнему обязательна (ADR-0011).
- Редкая гонка «старт во время `streams_reset`» превращается в ошибку для пользователя, а не в тихую потерю: поток не запустится.
- `AGENTS.md` и `docs/architecture.md` всё ещё описывают задержки потоков; их обновит финальная память сборки, до этого они расходятся с кодом.
- Окно должно не забыть `streams_reset` при загрузке: перезагрузка WebView событий не даёт, и без вызова старые сессии продолжают жить в `AppState`.
