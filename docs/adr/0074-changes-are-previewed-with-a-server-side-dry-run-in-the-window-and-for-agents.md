# ADR-0074: Changes are previewed with a server-side dry run, in the window and for agents

## Context

Saving in the editor, applying YAML and upgrading a Helm release sent the change at once (#141). What the API server stores is often not what was typed: defaulting fills fields, mutating admission webhooks add sidecars and labels, validation and policies refuse objects, and a Helm chart renders objects nobody looked at. On a production cluster a mistake there is an outage. `kubectl diff` and `helm diff` answer "what would change", but they are separate tools, and an AI agent working through the MCP server had no way to check a change before making it.

## Decision

- **The preview is the API server's own answer.** `resource_dry_run` (`crates/sextant-core/src/resources/dry_run.rs`) sends exactly the request the change would send — the editor's PUT, a server-side apply of each document, a patch — with `dryRun=All` and the same field manager (`sextant`), and returns per object the live object and what the server would store. Both sides go through `to_json` (no `managedFields`; a core Secret has every value `""` and the hidden-values marker); fields that differ on every write (`resourceVersion`, `generation`, and for a new object the dry run's own `uid` and `creationTimestamp`) are left out. What changes in a Secret's values is compared inside the core and told by **key names only** (`SecretKeyChanges`). A refused document keeps its error next to it; a document whose namespace an earlier document creates is reported as not checkable yet rather than as refused.
- **Helm upgrades and installs are previewed by Helm.** `helm_upgrade_preview` / `helm_install_preview` run `helm upgrade|install … --dry-run=server --output json` through `HelmCli` (scrubbed environment, temporary kubeconfig) and compare the rendered manifest with the release's stored one (`helm::diff`): both cut into documents (a `List` item by item), ordered by kind, namespace and name, Secrets masked with key-name changes, unreadable or kind-less documents left out and counted. A Helm older than 3.13 knows no `--dry-run=server`; it is asked again with plain `--dry-run` (a client-side render, flagged `clientSide` in the result) — the fallback never drops the dry-run switch. Hooks are not compared. The render is a task in `AppState.subscriptions` under a frontend-chosen id, limited to 120 s and stopped by `helm_preview_stop`, `close_cluster`, a page reload and exit, which kill its `helm`.
- **Per cluster, "Preview changes before applying".** `clusters[id].previewChanges` (frontend-written) makes the preview a step of every such change ("Preview and save…", "Preview and apply…"); off, it stays a "Preview changes" button. `null` follows the name: on when the display name, the context or the kubeconfig's cluster name has `prod` or `production` as a word of its own (`src/features/safe-apply/policy.ts`). The change itself is still the editor's or the dialog's own call, sent only after the user confirms.
- **Agents get the same dry run without being asked.** `apply_yaml` and `patch_resource` take `dryRun: true`. `Guard::check_dry_run` checks the same requirements as the change (the rules decide, node-shell refusals included) but never asks in the window, since nothing changes; the activity log records `<tool> (dry run)`. A dry run that touches a core Secret also needs the "Secret values" action, and its answer for a Secret is `create`, `write` or `refused` with the keys the agent's own input names — never whether a value differs (ADR-0043). The arguments of the write tools refuse unknown fields (`deny_unknown_fields`; `dry_run` and `dryrun` are accepted spellings), so a misspelt flag fails instead of making the change. Extensions get nothing new.

## Why

- A client-side diff (comparing the edited text with the live object) was rejected: it misses defaulting, webhooks and validation, which are exactly what surprises people.
- Running `kubectl diff` was rejected: another binary to find and trust, a second kubeconfig path, and its output would still have to be parsed and masked for Secrets.
- Showing a Secret's values in the preview was rejected: everything else in Sextant hides them (ADR-0014, `to_json`), and key names are enough to see that a value changes.
- Confirming dry runs in the window was rejected: they change nothing, and asking for every check would teach users to click "Allow" blindly. Gating Secrets behind "Secret values" closes the one way a dry run could leak something — comparing a guessed value.
- Always-on previews were rejected: on a development cluster the extra step is friction; the name rule picks production clusters without configuration, and the user overrides it either way.

## Consequences

- A preview costs one request per document plus a read of the live object; an apply stops at the first refused document after applying the ones before it, so the preview says to fix refused documents first.
- The API server refuses a dry run that would call an admission webhook declaring side effects (`sideEffects` other than `None` or `NoneOnDryRun`); the preview shows that refusal, and the change itself may still go through.
- A Helm before 3.13 renders without `lookup`, so Secrets a chart reuses may show as changed; the preview says so.
- Tests: `dry_run.rs` and `helm/diff.rs` unit tests on the fake API server, `helm/cli.rs` with a fake `helm`, `src-tauri/src/mcp/tools_write.rs` (`dry_runs_follow_the_rules_without_asking_and_change_nothing`, `a_secrets_dry_run_needs_secret_values_and_is_no_oracle`, `write_tools_refuse_unknown_fields_and_take_dry_run_spellings`), `src/features/safe-apply/safeApply.test.tsx`.
