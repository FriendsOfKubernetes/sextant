# ADR-0079: The change timeline is observed from open watches, bounded, and kept on disk only by choice

## Context

"What changed before it broke?" is the first question of an incident (#145). Kubernetes keeps no history of an object: a watch tells the current version, `managedFields` tell the last write of each field manager, rollouts keep a few old ReplicaSets or ControllerRevisions, Helm keeps release Secrets. An audit log would answer, but it lives on the control plane, is often off, and a desktop client cannot assume access to it. Sextant already holds many watches open while it is connected (tables, the problem sources behind the sidebar counter and the notifications, the resource map's shared watches), and every update of them passes through the window.

## Decision

- **Observed, never polled.** The recorder (`src/features/timeline/recorder.ts`) opens no watch of its own. The watch layers report every update they receive to `reportWatchUpdate` (`src/api/watchObservers.ts`): `useWatch`, the problem sources (`features/problems/store.ts`) and the shared watches (`features/resource-map/watches.ts`). The recorder keeps a short text of each object it saw — everything but `status`, `apiVersion`/`kind` and bookkeeping (`resourceVersion`, `generation`, `managedFields`, `uid`, timestamps), without annotations controllers rewrite (`last-applied-configuration`, `deployment.kubernetes.io/revision`; `kubectl.kubernetes.io/restartedAt` stays) — and records a change when a newer version differs, as a diff by field path (list items by `name`), values clipped, at most 30 fields. An older version from a lagging second watch is dropped by `resourceVersion`.
- **Only lists that tell deletions.** A watch narrowed by a label selector or by a field selector other than `metadata.name=` is never recorded from: an object leaves such a list when it stops matching, which is a change of it, not a deletion (`followsDeletions`). Metadata-only watches are ignored (their objects have no spec to compare). A creation or deletion is recorded only for objects without a controller; an object first seen in a fresh list after a while is a "late" change ("Seen later"). Pods, ReplicaSets, ControllerRevisions, Events, Endpoints/EndpointSlices, Leases, CRDs, metrics, a CronJob's Jobs and add-on churn (Cilium endpoints and identities, Calico's `crd.projectcalico.org` objects) are never recorded: their owners tell the story.
- **Who.** Watches and `resource_get` strip `managedFields`, so after a change the recorder asks `timeline_managers` (`crates/sextant-core/src/timeline.rs`: metadata-only GETs, ≤ 50 objects per call, one call per cluster at a time, ≤ 200 waiting, else the change stays without "who") and names the managers whose `time` moved since the last read; when none moved, the most recent manager that did not write `status` is shown as "probably". Sextant's own manager is shown as "Sextant (you or an AI agent)".
- **Bounded.** Per cluster a ring of 5000 changes and about 4 MB of them; object texts share 24 MB over all clusters, an object past it (or past 64 KB alone) is kept as a hash, so a change is noticed without its fields; at most 20 000 objects per cluster, the least recently seen forgotten first.
- **Secrets by key names only.** A Secret reaches the window without values (`resources::get::to_json`), and the recorder's projection keeps only its key names, so a timeline never holds a value; `timeline::save`/`load` strip any value of a Secret's keys again before writing and after reading.
- **Persistence is opt-in.** `AppSettings.timeline.persist` (frontend-written) is off by default: the timeline lives in memory and goes when Sextant quits. When the user ticks "Keep between restarts" on the Timeline page, each cluster's ring is saved a few seconds after it changes through `timeline_save` (one file per cluster under `<app data>/timeline/`, named by a hash of the cluster id, at most 8 MB with the oldest changes left out, written to a temporary file and renamed) and loaded by `timeline_load` when the recorder first sees the cluster; unticking it removes every saved file (`timeline_remove_all`), also of clusters no longer in any kubeconfig.
- **Before Sextant is partial.** `timeline_history` (≤ 10 namespaces of the filter, ≤ 1000 objects per list) and `timeline_object_history` return metadata only: the last change of each field manager of each object (`status` writes left out), rollout revisions (ReplicaSets by revision annotation; ControllerRevisions with `data` dropped at once) and Helm release revisions from the release Secrets' labels. The interface marks them "Partial".
- **Correlation, not causation.** Problems and Warning events of the problem sources that began from 1 min before to 30 min after a change, on the object or on what depends on it (the resource map's graph, three hops), are shown under the change as "Soon after this change".
- **Window only.** No MCP tool and no extension method reads the timeline (tests in `src-tauri/src/commands/timeline.rs`).

## Why

- A watch of its own per kind for the timeline was rejected: it would double the watches of a large cluster to record objects nobody is looking at, and it would make the timeline the biggest consumer of memory and API calls in the app. Recording what is already watched costs one comparison per update.
- Polling `managedFields` of everything was rejected for the same reason; asking only for objects that just changed keeps "who" to a few metadata GETs.
- Reading the API server's audit log was rejected: it is not reachable through the Kubernetes API, and most users of a desktop client have no access to it.
- Recording from label- or field-selected watches was rejected: an object that stops matching leaves the list exactly as a deleted one does, so every relabel would read as a deletion, and the remaining objects of a narrowed list say nothing about the rest of the kind.
- Persistence off by default: a timeline on disk is a record of a cluster's configuration on a laptop; the user decides whether to keep one.

## Consequences

- The timeline only knows what some open view watched; a namespace nobody looked at has no recorded changes, only the partial history. The page says so and watches its own namespaces (≤ 3 of the filter) while it is open.
- Memory is capped, so on a very large cluster old changes and object texts are dropped first; a change of an object kept as a hash says "Changed" without fields.
- "Who" is a field manager name, not a person: `kubectl-client-side-apply`, `helm`, `argocd-controller` or `sextant`.
- Tests: `model.test.ts` (projection, diff, managers), `recorder.test.ts` (selectors, bounds, late changes, persistence), `timeline.test.tsx` (page and tab), `crates/sextant-core/src/timeline/tests.rs` and `crates/sextant-core/tests/timeline.rs` (kind cluster).
