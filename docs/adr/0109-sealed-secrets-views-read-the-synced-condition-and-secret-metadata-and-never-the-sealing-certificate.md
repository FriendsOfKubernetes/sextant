# ADR-0109: Sealed Secrets views read the Synced condition and Secret metadata, and never the sealing certificate

## Context

#240 asked for Bitnami Sealed Secrets in the style of the other CRD projects (ADR-0097, 0100, 0101): the target Secret, the controller's status and its error, the scope a SealedSecret was sealed for, the controller found in the cluster and, if it costs no new rights, the validity of its certificate. Unsealing failures are problems. Sealed Secrets is about Secrets by nature, so what the window may see had to be decided first.

## Decision

- **Read-only, frontend only** (`src/features/sealed-secrets/`): a discovered sidebar section `sealedSecrets` with the one kind `bitnami.com/v1alpha1` SealedSecret, shown only where discovery serves it. No Rust command was added; nothing is written; the kind offers the generic Edit and Delete under their usual confirmations. Strings are the namespace `sealedsecrets`.
- **Status from the controller's own condition.** The controller (`pkg/controller/controller.go`, `updateSealedSecretsStatusConditions`) writes one condition, `Synced`, with no reason: True with an empty message, False with the unseal or update error as the message, and `status.observedGeneration`. Sextant shows Synced (True and current), Failed (False and current) and Pending (no condition, or `observedGeneration` behind `metadata.generation`: the status is of an older spec). No condition at all is explained as "not running, or `--update-status=false`" (the flag is on by default since v0.17.0). Known error texts are explained in words: "no key could decrypt secret" (another controller's certificate, or another name, namespace or scope), "already exists and is not managed by SealedSecret" (the `sealedsecrets.bitnami.com/managed: "true"` annotation), an immutable Secret, and the deprecated `spec.data`. The controller's events (`Unsealed`, `ErrUnsealFailed`, `ErrUpdateFailed`) are in the panel's own Events section.
- **Scope from the SealedSecret's own annotations**, as the controller reads them when it decrypts (`labelFor(smeta)` in `unseal`, `SecretScope`): `sealedsecrets.bitnami.com/cluster-wide: "true"` wins over `namespace-wide: "true"`, anything else is strict. The template's annotations are what the Secret gets, not what decides the decryption.
- **The target Secret is the SealedSecret's own name in its namespace** (the controller sets both whatever the template says). The details link it and read its metadata only (a `metadata.name=` watch with `metadataOnly`), to tell how it stands by the controller's own test before it writes: owned by this SealedSecret (a controller owner reference with its uid), taken over (`managed`) or patched (`patch`) by annotation, controlled by another object, or not managed. The template shows its type, `immutable`, whether owner references are skipped (`skip-set-owner-references`) and the names of `spec.template.data` keys (a null one is "left out"); its texts are not shown.
- **Keys by name and sealed size.** Of `spec.encryptedData` only the key names and the size of each ciphertext (from the base64 length, never decoded) are shown; the ciphertext itself is not, although it is not secret, so that no value of any kind sits in the section. The YAML section still shows the object as the cluster has it.
- **The controller** is looked for while the details are open, by kubeseal's default (the Deployment `sealed-secrets-controller` in `kube-system`, by name) and by the Helm chart's label `app.kubernetes.io/name=sealed-secrets` (cluster-wide, by the API server's label selector), merged by uid: readiness and images. Its sealing keys are listed from the Secrets labelled `sealedsecrets.bitnami.com/sealed-secrets-key` in the controllers' namespaces (at most 5), metadata only: name, `active`/`compromised`, creation time — the creation time shows when the key was last renewed (every 30 days by default).
- **The certificate's validity is not shown.** The public certificate sits in the same key Secret as the private key (`tls.crt` beside `tls.key`), so reading it means reading the private key into Sextant — refused, whatever the core strips afterwards. The other source, the controller's `/v1/cert.pem`, is an HTTP request to the controller through the service proxy, which #240 excludes (and which needs `services/proxy`). The details say "not shown" and why.
- **Problems** (category `sealedSecrets`, opt-in since the amendment below) come from a provider (`provider.ts`, `external`: the target Secret is another object), held only where SealedSecrets are served: one shared SealedSecret watch of all namespaces (at most 5000) and one metadata-only Secret list of the namespaces whose SealedSecrets say Synced (at most 20 namespaces and 5000 objects; beyond either, a missing Secret is not judged and the source says it is truncated). `SyncFailed`: Synced=False for the current generation, counted 5 minutes after `lastTransitionTime` (the controller retries with a back-off), with the controller's message. `TargetMissing`: Synced=True and current but no Secret of that name in a namespace read in full, counted 2 minutes after first seen (the controller recreates an owned Secret when it is deleted; one with skipped owner references it does not). A list that is forbidden, capped or not read is "not known", never "missing". Since the problems come only from the provider, the map and the Related tab colour SealedSecrets neutrally (`judgedByRules`).
- **Agents get nothing new**: `sealedSecrets` is in `NEVER_FOR_AGENTS` (`src-tauri/src/mcp/diagnose_answers.rs`); no MCP tool or extension method was added.

## Why

- The condition is the controller's own verdict; re-deriving whether a SealedSecret can be decrypted is impossible without the private key, and wrong anyway during a key rotation.
- Secret metadata is enough to tell "missing" and "not managed"; whole Secrets were never needed. A background metadata list is bounded by namespace and object caps so a cluster with thousands of Helm release Secrets pays a known cost; it is made only for namespaces with synced SealedSecrets.
- The category was first on by default, because a failed unseal is an incident, not a lasting state; the amendment below made it opt-in.

## Consequences

- A SealedSecret in a namespace beyond the 20 checked, or whose Secrets list is capped or forbidden, never shows "Secret missing" on the problems screen; its details still look the Secret up by name.
- A controller deployed under another name, without the chart's label, is reported as not found in the details (with that caveat in the text); nothing else depends on finding it.
- A SealedSecret whose status is of an older generation is Pending, not Failed, even if the controller is down; the controller block of its details tells that case.

## Amended (v0.21.0 review): the category is opt-in

The review found the default inconsistent with ADR-0108 and ADR-0110: the source holds a cluster-wide list of every SealedSecret (≤ 5000) and metadata lists of Secrets (≤ 20 namespaces, ≤ 5000 objects) in the background as soon as any view of a cluster that serves SealedSecrets asks for problems — the same kind of cost for which `traefik` and `reflector` are opt-in. So `sealedSecrets` is in `OPT_IN_CATEGORIES` (`src/features/problems/model.ts` and its Rust mirror in `src-tauri/src/mcp/diagnose_answers.rs`, kept equal by a test), with a toggle "Sealed Secrets unsealing" on the Problems page (`notifications.enabledCategories`, one setting for the screen, the section counter and the notifications). Off, the Sealed Secrets section's counter holds no source and nothing is watched for it (`badge.ts`, as Traefik's); the views and the details are unchanged. Agents still get none of it (`NEVER_FOR_AGENTS`).
