# Sextant architecture

Three layers, dependencies only point downward: `src/` (React) → `src-tauri/` (the `sextant` crate) → `crates/sextant-core/`.
For why things are the way they are, see `docs/adr/`; for what the words mean, see `CONTEXT.md`.

## Data flow

```
kubeconfig ──► KubeconfigRegistry ──► ClusterManager ──► kube::Client (retries, timeouts)
                                          │                  │
                           ConnectionState (broadcast)       ├─ resources::watch  ─► Stream<WatchUpdate>   (batches, at most 1 per 250 ms)
                                          │                  ├─ logs::stream_logs ─► Stream<LogUpdate>     (100 ms batches)
                                          │                  ├─ exec::exec_shell  ─► ExecSession
                                          │                  ├─ PortForwarder     ─► broadcast<Vec<ForwardInfo>>
                                          ▼                  └─ get / mutate / metrics / helm (request-response)
                        src-tauri: commands (invoke), stream channels (Channel::send) and events (emit)
                                          │
                        src/api: invoke / channel / listen / openStream (transport.ts), mockBackend for tests
                                          │
                        hooks (useWatch, useClusters, …) ─► zustand store + registries ─► components
```

- Request-response: component → `api.<group>.<method>` → `invoke("<command>")` → a thin command in `src-tauri/src/commands/<feature>.rs` → a core function → `Result<T, CoreError>`.
- Live data (watch, logs, terminal, extension watches, GitOps installs, file transfers): the frontend creates the stream id (`newStreamId()`), `openStream` (`src/api/stream.ts`) creates a Tauri `Channel` (`streamChannel` in `transport.ts`) and only then calls `*_start(…, streamId, onEvent: channel)`; the backend forwards the core stream with `channel.send` (`WatchUpdate`, `LogUpdate`, `TermPayload`, `InstallEvent`, `TransferEvent`). Streams are not events: an event is delivered by `eval` of a script with the payload inlined, which WebKit parses as an object literal and keeps the peak memory of, while a channel sends payloads of 8 KB and more through the IPC fetch path, parsed as JSON (ADR-0078). A single `openStream` keeps the order id → channel → start → close → stop. Closing at any point leaves nothing behind: the channel stops delivering at once, a start that has not answered yet is stopped when it does, and the backend drops its end of the channel when the stream stops. In tests `mockBackend` hands a start command's channel the payloads of `backend.emit("<prefix>:<streamId>", …)` (`STREAM_PREFIXES`).
- Terminal output is flow-controlled (#122): `useTerminal` acknowledges the bytes xterm has written (`term_ack`, every 64 KiB or 50 ms); a session with 2 MiB unacknowledged (`OUTPUT_WINDOW` in `src-tauri/src/commands/terminal.rs`) stops taking output from its shell until acknowledgements come, so the bounded output channel fills and the PTY (or, for a container shell, the exec websocket) is not read and the producer blocks. Output that comes quickly is gathered into one channel message per 16 ms; the first chunk after a quiet spell goes at once, and keystrokes are never held back.
- `streams_reset` (`resetStreams()` in `src/api/stream.ts`) is called once when the page loads, before the first stream: it stops the subscriptions and terminals left over from the window's previous page; connections and port forwards are not touched. A start that began before the reset is rejected (`AppState::undo_if_reset`).
- Watch: one set of watchers per subscription (one per namespace); the frontend receives `Snapshot`, then `Delta { upserted, deleted(uid) }`, `Reconnecting`, `Forbidden { namespaces }` (some namespaces are inaccessible, the rest carry on), `Error` (cannot start). `managedFields` is stripped in the core. `useWatch` puts objects into a `Map<uid, obj>`. With `WatchSpec.metadataOnly`, objects arrive only as `{apiVersion, kind, metadata}`. `watch_start` takes optional `WatchOptions` (#157; window only, agents and extensions keep the defaults): with `progressive`, the first list arrives as `SnapshotPart`s while kube pages through it (500 objects a page) — the first at once, then at most one per 250 ms — and a `SnapshotEnd { items, deleted }` completes them (a list that is in before any part went out is one `Snapshot`); with `maxObjects`, the core keeps (and sends) only the first that many objects, remembers the rest by uid and sends `Capped { total }` after a batch in which the number of matching objects changed (`WatchState.total`, `isCapped`).
- Watch store (#170): the core keeps each watched object as its compact JSON text (`WatchObject`, an `Arc<RawValue>`), written straight from the object kube read (a core Secret goes through `to_json`, which hides its values); a snapshot or delta carries the stored objects themselves and the Tauri channel writes their text as it is, so nothing is parsed again. About 5× less memory per object than a `serde_json::Value` tree; Rust readers that look inside an object (tests) call `to_value()`
- Shared watches (`src/api/watchRegistry.ts`, #157): one stream per (cluster, spec) however many views ask — `WatchOptions` are not part of the key: a holder asking for a cap joins an uncapped stream (it gets every object), and a capped stream is reopened without its cap when a holder wants every object (its rows stay until the full list is in); a failed watch is closed as soon as nobody holds it, so a retry starts anew — `useWatch`, the resource map's shared watches (`features/resource-map/watches.ts`, which adds a 5 s linger, flushed notifications and the following of connections) and the RBAC views (`features/rbac/sharedWatch.ts`) all acquire through it, so a table and the map listing the same objects share one stream; refcounted, closed with the last holder (or after the longest linger a holder asked for); `dropClusterWatches` closes a cluster's watches when its connection changes and moves its epoch, and every holder acquires anew. The problem sources and the palette index keep their own streams (they keep no objects, or only metadata).
- Watch observers (`src/api/watchObservers.ts`): `useWatch`, the problem sources (`features/problems/store.ts`) and the shared watches (`features/resource-map/watches.ts`) pass every update they receive to `reportWatchUpdate`, so a feature can see changes without opening a watch (the change timeline is the one observer). Observers run synchronously in the watch callback, must be cheap, and a throw is swallowed.
- Events (all without a stream id): `cluster-state` (`{ clusterId, state }`), `portforwards` (`ForwardInfo[]`), `mcp-status`, `mcp-confirm`, `mcp-audit`, `mcp-diagnostic`, `mcp-diagnostic-cancel`, `extensions-changed`, `extension-files-changed`, `ext-audit` and `open-about`.
- Subscriptions, streams and sessions live in `AppState` (`subscriptions`, `sessions`); they are closed by `*_stop`, `streams_reset`, window close (`window::on_run_event` → `close_all`) and `AppState::close_cluster` (disconnecting a cluster also closes its port forwards and its local terminals).
- Port-forward management (`src/features/portforward/`) uses one reference-counted list/event snapshot for the cluster page, resource details and creation dialog, with shared pending IDs and no polling. The page provides search, status filtering, separate Namespace/Source/Details columns and confirmed bulk stop; each surface offers stop, copy and open. Explicit retry releases the old listener first and preserves editable parameters on failure. `ForwardInfo.source` is assigned by the backend before publication, independently of `PodFilter`; internal connections are excluded from bulk actions and confirmed individually. Argo CD's private session forwarder keeps its existing ownership. See [ADR-0134](adr/0134-port-forward-management-uses-a-shared-event-snapshot-and-explicit-provenance.md).

### Very large clusters

Measured and bounded in #157 (numbers in the wiki page "Large clusters"). A resource table (`src/components/Table/`) watches with `TABLE_WATCH_OPTIONS` (`limits.ts`): the first list in parts, so rows show while thousands of objects load ("Loading… N so far"), and at most `TABLE_MAX_OBJECTS` (20 000) objects kept, with the notice "Showing the first N of M". Before a namespaced kind is watched in every namespace without a selector, the table counts it (`resource_count`: a metadata-only list of one object per namespace, at most 8 namespaces at once and 10 s per request, the API server's `remainingItemCount`, no object body; cached 60 s in `src/resources/counts.ts`) and, above `TABLE_GUARD_OBJECTS` (10 000), asks first ("Show anyway" is remembered for the session); a count that fails or takes longer than 3 s (`COUNT_WAIT_MS`) does not hold the (capped) watch back. With namespaces listed side by side, the cap is shared while they list. The search's selector terms are sent to the API server 400 ms after the last keystroke (`serverSelectors` in `selectors.ts`): label terms (`app=web`, `tier!=db`, `app=`) become the watch's label selector, terms on fields the API server selects by for the kind (`status.phase`, `spec.nodeName` on pods, `metadata.name` everywhere, …) its field selector, joined with the table's own selectors; the rows of the previous watch stay (filtered in the window, "Updating…") until the narrower one has listed. A selected namespace set is always watched namespace by namespace. The sidebar shows a count next to each kind entry of an open built-in section and next to the open entry (`EntryCount`, the same cache; "999+" above that or when the API server cannot count) — never for closed sections, sections of installed tools or custom resources, and at most `COUNT_REQUESTS_PER_MINUTE` (20) count requests a minute per cluster (a table's check is not held back). The change timeline (`features/timeline/recorder.ts`) takes a list in parts as its baseline and prunes with its end, and does not prune with a list as long as its cap. The SDK's copy of `WatchUpdate` leaves out the window-only updates (`sdk/scripts/sync-types.mjs`, `NARROW`). The palette's metadata index keeps at most `MAX_INDEXED_OBJECTS` (50 000) objects per kind and says when it searched only the first ones. The search predicate is compiled once per query (`compileSearch`) and cells are compared with one `Intl.Collator`. Strings: `src/locales/<lang>/scale.json`. Decision: ADR-0091.

### Discovery

There is one discovery per cluster: `ClusterManager::kinds` hands the shared result to everyone waiting and stops when nobody is left waiting; it is reset on (re)connect and disconnect. Aggregated discovery comes first (two requests), otherwise it goes group version by group version. `ResourceKind.printerColumns` is empty in it: the frontend reads CRD columns lazily, one CRD at a time, when the kind is opened (`useCrdPrinterColumns`, `src/resources/crdColumns.ts`). Built-in kinds are described in the core (`BUILT_IN_KINDS` in `crates/sextant-core/src/resources/get.rs`), and their watch does not wait for discovery. The sidebar takes CRDs from discovery (`customResourceKinds` in `src/resources/useKinds.ts`). Decision: ADR-0015.

### GitOps: Flux and Argo CD

Flux and Argo CD are ordinary CRDs, so everything goes through the Kubernetes API with no CLI of these tools (ADR-0024). Their kinds (`src/features/flux/`, `src/features/argocd/`) are registered in the kind registry under the `flux` and `argocd` sidebar sections; a section is shown only if its kinds are in discovery (ADR-0031). Actions (reconcile, suspend/resume, sync, refresh, terminate) are object patches through the shared `resource_patch` command (ADR-0025). The core picks the kind version through `resolve_kind`: get/watch/patch use the version from discovery, while `replace`/`apply` use the document's version (ADR-0030).

**Discovery reset.** The Flux and Argo CD CRDs show up after the connection is made, so the frontend watches CRDs (`watchCrdChanges`, `src/resources/useKinds.ts`) and calls `cluster_kinds_refresh` when one is added or removed: `ClusterManager::refresh_kinds` resets the cluster's shared discovery without reconnecting (ADR-0026).

**Argo CD: login and diff.** The core (`crates/sextant-core/src/argocd.rs`) finds the Argo CD installation (ADR-0032) and talks to its API through a port-forward to `argocd-server`; TLS verification is disabled only for `127.0.0.1` (ADR-0027). Sessions live in `ArgoSessions` (`src-tauri/src/commands/argocd.rs`, field `AppState.argocd`) and are closed together with the cluster; the commands are in `src-tauri/src/commands/argocd.rs`. The login sources and their order are in ADR-0028, the saved login in the OS keyring is in ADR-0029. Argo passwords and tokens stay in the backend; a saved login is bound to the API server URL, the CA and the kubeconfig entry of the connection it was saved through (`ClusterManager::server_binding` + the entry's ClusterId) and is offered only when all three match. The diff (`argocd_diff`) returns the managed resources with their desired and live state, with Secret values stripped; the login dialog and the diff view built on `@codemirror/merge` are in `src/features/argocd/diff/`, and the `argoDiff` action is attached by a separate feature, `src/features/argocd-diff/`.

**Installing Flux and Argo CD (ADR-0058, ADR-0062).** A cluster without the tool can get it from the user's click in the window, never from an agent or an extension (no MCP tool or extension method; a test keeps it). Split: the core `crates/sextant-core/src/gitops_install.rs` has no network — `prepare` cuts the official `install.yaml` into an `InstallPlan` (Flux without image automation and the source watcher into `flux-system`, Argo CD into `argocd`, a kind allow-list), `apply`/`apply_until` do forced server-side apply object by object (Namespace, CRDs, `refresh_kinds`, the rest), `readiness` lists the Deployments/StatefulSets of the plan (an empty list is not ready), `installed` reports present / partly installed (CRDs + key controllers), `access_check` runs SelfSubjectAccessReviews. `src-tauri/src/gitops_install/` adds what needs the network and the window: `download.rs` fetches only fixed GitHub URLs (release list, Flux `install.yaml` verified against the release's checksums, Argo CD `manifests/install.yaml` shown with its SHA-256) under the shared rules of `src-tauri/src/download.rs`, falling back to the bundled versions; `mod.rs` keeps a prepared plan under a single-use token (10 min) and runs the install as a stream through the channel of `gitops_install_start` (an `InstallEvent` per object, readiness polled every 3 s up to 5 min, then `done`/`timedOut`/`stopped`/`error`). The running task lives in `AppState.gitops` and is stopped by `close_cluster`, a page reload and exit. The dialog (`src/features/gitops-install/`) is mounted once in `AppShell`; entries are in the cluster menu and cluster settings, shown from `gitops_install_status`, not from discovery; the new CRDs show up through the discovery reset above.

### Gateway API

Read-only and entirely in the frontend (ADR-0063); the core and the Tauri layer have no Gateway API code. Data flow: watches of the served Gateway API kinds (`hooks.ts`: nothing before discovery, nothing for a kind the cluster does not serve, namespaced lists only for the involved namespaces) → the pure model in `src/features/gateway-api/model.ts` (listeners and their status, route parents and rules, conditions, backends, ReferenceGrants, problems) → views: the section's tables and details (`register.tsx`, `columns.tsx`, `details.tsx`, `policies.tsx`), reverse links on Services and Secrets (`exposure.ts`), a Gateway's topology (`topology.ts`, `TopologyView.tsx`), the section counter (`problems.ts`) and the "Request check" page with the hostname map (`RequestCheck.tsx`, `HostnameMap.tsx`; the check reads the data through `checkData.ts`/`checkState.ts`). Texts are in `src/locales/en/gateway.json`.

**Matching engine.** `matching.ts` is pure functions over watched objects, with no React: `explainRequest` follows a request (method, URL, headers) through the Gateway listeners (port, protocol, most specific hostname), the attached and accepted routes (`allowedRoutes`, hostname intersection) and the HTTPRoute/GRPCRoute precedence rules of the spec down to the rule, filters and backends, and lists why each other candidate lost; `hostnameMap` lists hostname → listener → route → backends and marks conflicts. Where the spec leaves a choice to the implementation (regular expressions, ordering HTTPRoute against GRPCRoute, namespace selectors without labels) the choice is documented in the header of `matching.ts` and returned as a note in the result. Nothing is sent to a Gateway and nothing is written to the cluster.

**Generic pieces added for it.** `ResourceDef.problem` (`src/resources/registry.ts`) makes `MainView`/`ResourceTable` offer an "Only problems" filter for a kind; `registerSectionBadge` (`src/layout/sectionBadges.ts`) puts a counter on a sidebar section header; `DetailsSectionDef.labelKey` (`src/layout/details/registry.ts`) gives a details tab a translated label; long annotation values and JSON are folded behind "Show" in the details panel (`isLongAnnotation`, `src/features/details/sections.tsx`). Pages registered in a discovered section (`gatewayApi`, `flux`, `argocd`) show only while the cluster serves one of the section's kinds (`buildSections`, `src/layout/sidebar/Sidebar.tsx`).

### Service mesh: Istio and Linkerd

Read-only and entirely in the frontend (#155, `src/features/mesh/`); nothing is written to the cluster and nothing talks to a proxy. The discovered sidebar sections `istio` (VirtualService, DestinationRule, Gateway, ServiceEntry, Sidecar, WorkloadEntry, PeerAuthentication, RequestAuthentication, AuthorizationPolicy, Telemetry) and `linkerd` (ServiceProfile, Server, HTTPRoute, AuthorizationPolicy, ServerAuthorization, MeshTLSAuthentication, NetworkAuthentication) list only the kinds the cluster serves (`kinds.ts`, `register.tsx`, `columns.tsx`); details explain each kind in plain words (`istioDetails.tsx`, `linkerdDetails.tsx`). `store.ts` holds a cluster's Istio configuration once for every view: one shared watch (`resource-map/watches.ts`, `acquireWatch` + `subscribeSharedWatches`) per served Istio kind in all namespaces, plus a metadata-only Service list of the namespaces those objects name (≤ 40, beyond it no host is judged missing); nothing before discovery, released 5 s after the last user, taken anew on reconnect. Pure engines with table-driven tests: `istio.ts` (host rules: short names resolved in the object's namespace, wildcards, specificity, `exportTo`, DestinationRule lookup client → Service → root namespace), `routing.ts` ("Where does this request go?": VirtualServices bound to the gateway or `mesh` and visible to the caller, the most specific host, Gateway merge vs. sidecar oldest-wins, first matching HTTP route by uri/method/scheme/authority/headers/queryParams/port/sourceLabels/sourceNamespace, weights, delegates, DestinationRule subset → pods), `authz.ts` ("Who may call this workload?": CUSTOM → DENY → ALLOW, empty-rule semantics, three-valued matching so an unevaluated condition is "unknown" and an unmodelled DENY/CUSTOM — including one attached by targetRef — never yields "allowed"; `istio.io/dry-run` policies are shown but not enforced, an action Istio does not accept gives "unknown", `remoteIpBlocks`/`remote.ip` need a remote IP of their own), `mtls.ts` (PeerAuthentication precedence workload > namespace > root, UNSET inherits, port-level modes), `membership.ts` (sidecar, native sidecar, ambient, revision, injection; Linkerd proxy and `linkerd.io/inject`) and `problems.ts` (unknown host, missing DestinationRule or subset, missing Gateway, TLS mode against STRICT, conflicting VirtualServices, host `*` on a mesh-bound VirtualService, which Istio rejects and the routing engine skips). Views: the "Service mesh" details section of Pods and workloads (`MembershipSection.tsx`), the "Request routing" page (`RequestCheck.tsx`, built on the Gateway API request-check layout; Services and pods of the destinations' namespaces are watched only while a result shows them), the Istio section counter (`badge.ts`) and the problems category `mesh` (an `external` source whose provider is `provider.ts`; `ResourceDef.problem` of VirtualServices and DestinationRules reads the same findings). The cluster domain is taken as `cluster.local` and the root namespace as `istio-system`. Linkerd golden metrics are in the "Requests" details section (#212, ADR-0095); the Linkerd block points there when linkerd-viz is installed. Texts are in `src/locales/<lang>/mesh.json`. Decision: ADR-0089.

### Argo Rollouts and Argo Workflows

The discovered sections `argoRollouts` and `argoWorkflows` (#213, `src/features/argo-rollouts/`, `src/features/argo-workflows/`) register only their own kinds of the group `argoproj.io` that Argo CD shares. A Rollout's status, step, set and actual weight follow `kubectl argo rollouts get`; its details watch the ReplicaSets and AnalysisRuns of its namespace only while open and pick its own by owner uid. Promote, Promote fully, Abort and Retry are window actions that send the plugin's merge patches — the status part through `resource_patch_status` (`sextant_core::resources::patch_status`, allowed for Rollouts only), the spec part through `resource_patch` — after a confirmation that lists them and a fresh read that refuses to send other patches than the ones shown; Pause and Resume (#237) go the same way (`spec.paused`, and the pause conditions for Resume). Workflows can be suspended, resumed, stopped and terminated (#238) by one merge patch of the object each, as `workflow/util/util.go` builds it (a Workflow has no status subresource; suspend and resume carry the re-read resourceVersion); retry is not offered. Workflows show phase, progress, duration and the failed step; the details draw the node tree (≤ 500 rows, collapsed) with each pod node linked to its pod (named by `workflows.argoproj.io/pod-name-format`) and its logs. Problems: category `rollouts` (Degraded or aborted Rollouts and the failed analyses they report, from the store's Rollout watch) and `workflows` (an external provider with one metadata-only watch of Workflows labelled Failed or Error, ≤ 5000 kept; a failure counts for a day from when the provider saw it enter the list, else from creation; ≤ 500 problems, newest first). Agents and extensions get nothing new. Decision: ADR-0097.

### External Secrets, CloudNativePG, Strimzi, Prometheus Operator

Read-only and entirely in the frontend (#213), one feature per project (`src/features/external-secrets/`, `cnpg/`, `strimzi/`, `prometheus-operator/`), each a discovered sidebar section listing only the kinds the cluster serves, with a status column (ready / progressing / failed in words, the condition's reason) and details from the operator's own status: an ExternalSecret's Ready condition and last error, its store (watched by name while open) and the target Secret as a link — no Secret is read; a CloudNativePG Cluster's instances with roles and health, a switchover or failover in progress, backups and continuous archiving; Strimzi's Ready / NotReady / Warning conditions, a Kafka's listeners with their addresses, topics and users (the user's Secret by name); Prometheus and Alertmanager readiness, PrometheusRule groups, and for a ServiceMonitor/PodMonitor the Services/Pods it selects now (the selector sent as a server-side label selector in ≤ 20 namespaces, port names checked) and which Prometheus picks it up by its selectors (`model.ts` `picksUp`, the resource map's selector semantics). Problems feed the categories `externalSecrets`, `cnpg`, `strimzi`, `prometheusOperator` (kept from agents); monitors that select nothing come from `prometheus-operator/provider.ts`, whose `store.ts` holds the monitors, the Prometheus objects and metadata-only Services/Pods of ≤ 40 namespaces through the shared watches (a monitor picked up only by Prometheus objects with `ignoreNamespaceSelectors` looks in its own namespace). That category is opt-in, and the store rebuilds at most every 500 ms, only when its own watches change. Problem sources may be capped (`SourceDef.maxObjects`: Strimzi topics and users, Kyverno reports); a capped source reports itself truncated. The resource map shows a kind green only when the rules alone judge it (`judgedByRules`), so a ServiceMonitor stays neutral. Decision: ADR-0100.

### Knative Serving, Crossplane, Kyverno

Read-only and entirely in the frontend (#213, ADR-0101), one feature per project (`src/features/knative/`, `crossplane/`, `kyverno/`), each a discovered sidebar section (`knative`, `crossplane`, `kyverno`) listing only the kinds the cluster serves. Knative: Services, Configurations, Revisions, Routes, DomainMappings with a status column and details that name the first failing condition, the latest created and ready revisions and the traffic split with links (`model.ts`, `details.tsx`); a not-ready Service or own Configuration is a problem of the category `knative` (`problemRules.ts`, called by `detect`); Revisions are not watched. Crossplane: XRDs, Compositions, Providers, Configurations, Functions; claim and composite kinds come from the XRDs and one store (`store.ts`) holds the XRD list and the claim/composite kinds of at most `MAX_XRDS` = 20 XRDs through the shared watches, feeding the "Composite resources" page and the external problems provider of the category `crossplane` (`provider.ts`); the details of any claim, composite or managed resource (by shape) follow Claim → composite → composed resources, each named object read once per change with `resource_get` (`chain.ts`, ≤ `MAX_CHAIN` = 30). Kyverno: policies (readiness, mode per rule), `wgpolicyk8s.io` reports and `reports.kyverno.io` ephemeral reports; every object's details get "Policy results" from the one report named by its uid (a name-selected shared watch, `hooks.ts`), a policy's details sum up the reports carrying its label (≤ `MAX_SUMMARY_REPORTS` = 1000); failing objects are problems only through the opt-in category `policies` (`problemRules.ts`). The three categories are in `NEVER_FOR_AGENTS`.

Knative Eventing (#234, ADR-0106) is a second discovered section of the same feature (`knativeEventing`): Brokers, Triggers, Channels, InMemoryChannels, Subscriptions, Sequences, Parallels and the sources (ApiServerSource, PingSource, ContainerSource, SinkBinding, KafkaSource), with the same states, Destinations shown as links plus the address they resolved to, a Trigger's filter in words, and an "Event path" block (sources → Broker → Triggers → subscribers, sources → Channel → Subscriptions, Sequence steps, Parallel branches) built from lists of the hub's namespace only (`eventingPath.ts`, `eventingHooks.ts`). Not-ready Eventing objects join the `knative` problem category (`eventingProblems.ts`), except objects another Eventing object controls and Triggers that fail only because of their Broker.

### Traefik

Read-only and entirely in the frontend (#232, ADR-0108): `src/features/traefik/` is the discovered sidebar section `traefik` (IngressRoutes HTTP/TCP/UDP, Middlewares, MiddlewaresTCP, TraefikServices, TLSOptions, TLSStores, ServersTransports, of `traefik.io` and, where still served, `traefik.containo.us`). Traefik writes no status on these kinds, so the state shown is what the references find (`resolve.ts`): a Middleware, Service, TraefikService, TLSOption or Secret that does not exist breaks the object (a route's own TLS Secret does not: Traefik builds the router and serves another certificate); a reference into another namespace depends on the provider's `allowCrossNamespace`, which no object shows, and another provider's object (`name@file`) cannot be seen — both stay "not all checked", never fine and never broken. Where a cluster serves both groups, a `traefik.io` object's references are looked up in `traefik.io` only (all Traefik v3 reads); a target only in `traefik.containo.us` is "not all checked", and the details name an object's same-named twin in the other group. One store (`store.ts`) holds a watch per served Traefik kind and metadata-only lists of the referenced namespaces' Services (≤ 40 namespaces) for the column, the details, the section counter and the problems provider of the opt-in category `traefik` (never given to agents); it never lists Secrets — the details of one object check its Secret references with one metadata-only list while open. Each list is indexed once per state, so a rebuild is linear. The traffic diagnosis follows an IngressRoute as a kind registered with `src/features/diagnose/routeKinds.ts` (`diagnose/traefik.ts`): entry points, TLS certificate and options (beside the path: a TLS finding never stops the walk), then per route its rule, middlewares and services, TraefikServices down to Services (≤ 4 levels, ≤ 30 services), Services into their own checks.

### Contour

Read-only and entirely in the frontend (#233, ADR-0107): `src/features/contour/` is the discovered sidebar section `contour` (HTTPProxies, TLSCertificateDelegations, ExtensionServices). A proxy's state is what Contour wrote (`currentStatus` valid / invalid / orphaned, `NotReconciled` before any Contour processed it, and the `Valid` condition's `errors` and `warnings`); the details explain it, list the routes with their conditions, each service's share of requests (or the percent a mirror copies), the policies on the host and each route, the includes and the delegation tree. The tree reads compact rows of every HTTPProxy through a row tap on the problems store's cluster-wide HTTPProxy source (category `contour`), so it opens no watch of its own. The diagnosis of an HTTPProxy is a route kind registered with the traffic diagnosis (`src/features/diagnose/contour.ts` through `routeKinds.ts`): Contour's state, a root's host, address, TLS delegation and certificate, then a chain per service and per include (≤ 3 levels, ≤ 30 services). Invalid and orphaned proxies are problems of the category `contour`, never given to agents; an orphan whose include path goes up to an invalid proxy is told through that proxy (the problems store keeps the source's row tap and filters by it, `SourceDef.across`), so a root that fails with 20 includes is one problem. Include prefixes merge as Contour's `mergePathMatchConditions` (concatenated, slashes collapsed, a trailing slash kept).

### Sealed Secrets

Read-only and entirely in the frontend (#240, ADR-0109): `src/features/sealed-secrets/` is the discovered sidebar section `sealedSecrets` (`bitnami.com/v1alpha1` SealedSecret). The state is the controller's one condition `Synced` (True synced, False failed with the unseal or update error, none or an `observedGeneration` behind `generation` pending), the scope comes from the SealedSecret's own `cluster-wide`/`namespace-wide` annotations (what the controller decrypts with), and the target Secret is the SealedSecret's own name, looked up by a metadata-only watch while the details are open to tell whether it is owned by this SealedSecret, taken over (`managed`), patched, or in the controller's way. ### Cluster client: retries and timeouts

`kube::Client` is built in `cluster.rs` with its own retry layer (`RetryPolicy`: 429/503/504, at most 3 times and 5 s, **only GET and HEAD** — a change may have been applied already, so it is never repeated; its 504 becomes `ErrorCode::Timeout` with the text `CHANGE_TIMED_OUT`); the connection uses `CONNECT_TIMEOUT`. Commands that change the cluster are wrapped in `error::with_timeout` (`CHANGE_TIMEOUT` in `src-tauri/src/commands/actions.rs`) and yield `ErrorCode::Timeout`; drain and multi-document apply limit each request (`resources::STEP_TIMEOUT`); Helm calls have time limits and are killed on drop. Decisions: ADR-0016, ADR-0023, ADR-0055.

Proxies: a kubeconfig cluster entry's `proxy-url` is honoured by kube-rs (features `http-proxy` and `socks5` in the workspace `Cargo.toml`) for every request, watch, exec and port-forward of that cluster: `http://` and `https://` proxies are tunnelled with CONNECT (credentials in the URL become Basic auth), `socks5://` resolves host names on the proxy (like kubectl's `socks5h`); kube-rs refuses the `socks5h://` scheme itself, so users write `socks5://` (#184). An entry without `proxy-url` falls back to the app's `HTTPS_PROXY` / `https_proxy` environment variable (kube-rs `ConfigLoader::proxy_url`); `NO_PROXY` is not honoured.

### Secrets

The core does not hand Kubernetes Secret values to the frontend: `resources::get::to_json` for `core/v1 Secret` replaces the `data`/`stringData` values with `""`, sets the `sextant.dev/values-hidden` annotation and removes `last-applied-configuration` — this applies to both watch and `resource_get`. The value of a single key is `secret_value`; the whole object is `resource_get_full`, for editing only. The core rejects saving an object that carries the `values-hidden` marker (`ensure_values_present`). Dry runs (#141) follow the same rule: both sides of `resource_dry_run` and of the MCP `dryRun` result go through `to_json`, a Helm preview masks Secret documents the same way (`helm::diff`), and what changes in a Secret's values is named by key only (`SecretKeyChanges`, compared inside the core). An MCP agent without "Secret values" writes Secrets blind (`resources::SecretWrites::Blind`: forced server-side apply, an immutable Secret's values refused unsent with one text, refusals without the server's message; #169, ADR-0043), so a write does not answer a guessed value; what is still not hidden is listed in ADR-0043. Decision: ADR-0014.

### MCP server for AI agents

Sextant can serve MCP to local agents (Claude Code, Claude Desktop, Cursor). It is optional, off by default (`AppSettings.mcp.enabled`), lives in the app process under `src-tauri/src/mcp/` and stops with the app (ADR-0038). Data flow of one call:

```
MCP client ──► 127.0.0.1:<port>/mcp ──► http.rs: Host / Origin / Bearer / 4 MB body ──► rmcp tool (tools_read / tools_write)
                                                                                              │
   audit.rs (ring of 2000 + mcp-audit.jsonl, event mcp-audit) ◄── result ◄── core call ◄── Guard::check ──► access::decide
                                                                                              │ needs "ask"
                                                                       event mcp-confirm ◄────┘ ──► window dialog ──► command mcp_confirm_answer(id, approved)
```

- The server is a field of `AppState` (`AppState.mcp`); `settings_update` calls `apply_settings` after saving, `close_all` calls `stop`. The state is announced by the event `mcp-status`; the commands are `mcp_status`, `mcp_token`, `mcp_regenerate_token`, `mcp_audit_list`, `mcp_audit_clear`, `mcp_confirm_answer`, `mcp_diagnostic_answer`, `mcp_binary_path`.
- The token is the file `mcp-token` (0600) in the settings directory, shared with `sextant mcp`; the directories are computed without Tauri (`mcp/paths.rs`, ADR-0039).
- Tools do no cluster logic: they call the core (`resources::list/events/resolve`, `logs::tail`, `exec::run_command`, the existing mutate, Helm and port-forward functions). Every tool states the permissions it needs as `(namespace, kind, action)` triples and calls `Guard::check` right before each side effect; the results are truncated and Secret values are cut out unless the Secret values action is granted. A call that needs confirmation waits at most 120 s for the window; without an answer, without a window, or after a stop it is refused.
- Every call, allowed or not, is one record in the activity log, oldest first (summaries only, no values, YAML or output; ADR-0042); a call that never reached a decision is journaled `NotChecked`. The frontend (`src/features/mcp/`) shows the Settings section and the log; the confirmation dialog is shared with extensions and is mounted once in `AppShell`.
- The confirmation map, the journals and the node-shell refusals are not MCP-specific: they live in `src-tauri/src/access_guard/` (`confirm.rs`, `audit.rs`, `mod.rs`) and are used by both the MCP guard and the extension API; `mcp/confirm.rs` and `mcp/audit.rs` only re-export them (ADR-0051).
- **Diagnostic tools** (#210, ADR-0094): `get_problems`, `diagnose_service`, `check_connectivity`, `get_permissions`, `get_recent_changes`, `get_autoscaling_status` (`mcp/tools_diagnose.rs`) answer with the window's own engines. The tool parses strict arguments, opens the cluster, runs `Guard::check` (Read on the asked object) and `Guard::check_reads` (a Read rule in that namespace), then `mcp/window.rs` sends `mcp-diagnostic` (`DiagnosticRequest`: id, tool, cluster, validated arguments, `reads` = the Read rules in force) to the main window without revealing it and waits ≤ 40 s for `mcp_diagnostic_answer` (no window: an error at once; ≤ 4 waiting, ≤ 2 per MCP session; a server stop drops the call, `streams_reset` fails what waits; whenever it stops waiting without an answer it sends `mcp-diagnostic-cancel` and the window drops the worker). In the window `DiagnosticsHost` (`src/features/mcp-diagnostics/`, mounted in `AppShell`, draws nothing) runs ≤ 4 hidden workers at once (as many as may wait, so none queues) with the screens' hooks (problem sources, `useDiagnosisData`, `useNetpolData`, `useRbacData`, the recorder's memory, `useSharedList`) and feeds the engines only what `reads` covers (`canRead`; unreadable lists make the engines answer "unknown") — and reads nothing more: lists the agent may not read everywhere are watched only in its namespaces (`planProblems`, the diagnosis's `DiagnosisScope`), mesh and best-practice findings are computed on that alone (`useAgentMesh`, `useAgentPractices`) and say what they rest on (`refs`), disk usage needs Read on claims and Nodes everywhere, and a TLS certificate is read only with "Secret values" (`checkCertificates`) — in English, answering when loaded or after 20 s (`incomplete`). Back in Rust `mcp/diagnose_answers.rs` reads the answer into its typed shape, re-checks every named object with `access::decide` (`ReadFilter`), drops a problem whose `refs` it may not read, drops opt-in problem categories that are off (and `credentials` always), makes TLS steps "not checked" without "Secret values", recomputes a diagnosis's status and summary from what is left, keeps a Secret's recorded changes as paths only, clips every text, caps every list and adds `dataNotice` (the cluster's text is data, not instructions). No confirmation, one journal entry per call.
- **Restricted RBAC** (#296, ADR-0129):
  - `get_access` (`mcp/tools_read.rs`) returns the rules in force, plus the context's namespace and the known namespaces the agent may read in, from the settings only.
  - A list over all namespaces that the API server refuses falls back to those namespaces one by one, at most 20 (`fallback_namespaces`, `list_each`; `namespaces`/`refused` in the answer).
  - `list_resources` takes `fields` or `summary` (`mcp/projection.rs`, read after `compact`).
  - `get_permissions { mine: true }` (`mcp/effective.rs`) sends the user's SelfSubjectRulesReview only while `clusters[id].agentAccessReviews` is on, cut to the kinds the agent's rules cover.
  - `get_problems` names the lists it could not read (`failed`).
- **`sextant mcp`** is the same binary started with the first argument `mcp`: `main.rs` runs `mcp_proxy::run()` without Tauri and bridges stdin/stdout JSON-RPC lines to the running server, reading the port from `settings.json` and the token from `mcp-token`. It starts no cluster work of its own and never creates the token (ADR-0040).

### Agent access model

Policy is a pure module of the core, `crates/sextant-core/src/access.rs`: per cluster, `ClusterSettings.agent_access` holds a preset (Off, Read-only, Read + write, Full, Custom) and rules `namespaces × kinds × actions (+ "ask")`; the actions are Read, Modify, Delete, Logs, Exec, Port forward and Secret values. A call is allowed if some rule covers `(namespace, kind, action)`; there are no deny rules. Off is the default, and a value that does not parse is read as Off. A preset other than Custom is a function producing rules (`preset_rules`, the only source: the frontend asks for them with `access_preset_rules`); Custom uses the stored rules. Kinds without a namespace are checked with namespace `None`; a Helm release is the pseudo-kind `helm.sh/Release`. The rules are in `settings.json`, written by the frontend (`src/features/agent-access/`), and the server re-reads them on every call. Denials use `ErrorCode::Denied`. Decision: ADR-0041; the JSON patch limit on Secrets is ADR-0043.

### Cloud cluster sources

"Add cluster → From cloud" finds EKS, GKE, AKS and Yandex Cloud Kubernetes clusters through the user's installed CLIs (`aws`, `gcloud`, `az`, `yc`), run by `crates/sextant-core/src/cloud.rs` without a shell, with a cleaned environment and a 60 s timeout, behind the `desktop` feature. The chosen clusters are written to `kubeconfigs/cloud-<provider>.yaml` in the app data directory (0600) with an exec-based authentication that calls the CLI again at each connection; the file is registered as an ordinary kubeconfig source. Sextant never performs a login and never touches `~/.kube/config`; an expired login yields a message with the login command, which the UI can put into a terminal without running it. Commands: `src-tauri/src/commands/cloud.rs`; UI: `src/features/clusters/CloudClusters.tsx`. Decision: ADR-0044.

Yandex Cloud adds staged profile/cloud/folder discovery (`cloud/yandex.rs`, `YandexCloudQuery.tsx`) to the same commands. Its discovery removes inherited `YC_IAM_TOKEN`; the saved exec masks that variable with an empty value, so it cannot override the selected profile credentials. It uses an explicit yc profile on every call and on exec authentication, supports external/internal endpoints and manual folder IDs when enumeration is denied. Cluster discovery follows the selection automatically, debouncing manual folder IDs by 300 ms; refresh retains the chosen folder and successful import markers. Query generations discard responses invalidated by a changed selection; importing still refreshes the shared cluster list even when its original form has changed.

### Virtual clusters (vcluster)

#269, ADR-0122. The page "Virtual clusters" (Cluster section, `src/features/vcluster/`) finds vcluster control planes on the host by the API server's selector `app=vcluster` (StatefulSets and Deployments, `release` = the name, never an object carrying `vcluster.loft.sh/managed-by`) and shows their state, control-plane pods, Service `<name>` and Secret `vc-<name>` (metadata only, bounded); the details of a control plane add the objects the syncer copied (`managed-by=<name>`, metadata only) with their virtual names. The window gets names and the port only. Agents and extensions get nothing new.

### Kubeconfig management

#150, ADR-0084. Window-only: agents and extensions get none of it. **Edits** (`crates/sextant-core/src/kubeconfig/edit.rs`, `KubeconfigEdit`: `renameContext`, `setNamespace`, `duplicateContext`, `deleteContext`, `merge`) are two steps: `kubeconfig_edit_preview` returns an `EditPreview` (entry and field changes with every credential `<hidden>`, `commentsLost`, `layoutChanges`, the real file and backup path, and `base`, a SHA-256 of what the change was computed from); `kubeconfig_edit_apply(edit, base)` recomputes the change and writes only when the file still hashes to `base` (else `conflict`). `ensure_writable` refuses (`denied`) any source that is not Sextant's own file (pasted, cloud, merged in `KubeconfigRegistry::own_dir`) unless its id is in `AppSettings.kubeconfig.writableSources` (frontend-written, off by default; "Allow Sextant to edit" in Settings → Clusters, which first shows `kubeconfig_edit_target`: the file after symlinks and the backup pattern). `replace_file` copies the file to `<real>.bak-<UTC YYYYMMDD-HHMMSS>` (0600, newest `MAX_BACKUPS` = 5 kept, `prune_backups` touches only names of that exact shape), writes a temp file in the same directory with the original's permissions, checks the file once more and renames over it; a symlink keeps pointing at the replaced target. Merge writes `merged.yaml` (`MERGED_FILE`, at most `MAX_MERGE_FILES` = 32 inputs, ≤ `MAX_FILE_BYTES` = 4 MiB each), renames taken names `-2`, `-3`, absolutizes relative paths, and registers it as a `SourceKind::Merged` source. After a write the command moves settings of renamed clusters (`move_cluster_settings`: per-cluster settings, overview selection, muted clusters, last cluster, views, pins, workspaces) and purges those of deleted ones (`forget_cluster_settings`), then disconnects both; the window runs the call through `withBackendSettingsChange` (`src/api/settings.ts`) so its stale copy is not written back. Removing a source drops its writable flag (`forget_source_settings`). **Credential expiry** (`kubeconfig/expiry.rs`, `kubeconfig_credentials`): certificate `notAfter`, JWT and OIDC `id-token` `exp`, files capped at 256 KiB; exec plugins and auth providers are only named, never run; no credential leaves the core. The window reads it with the cluster list and hourly (`src/features/clusters/kubeconfig/credentials.ts`), shows `ExpiryBadge` on the rail and, when the opt-in problem category `credentials` is on, notifies through `CredentialsNotifier` (no watch). **Validation** on add (`kubeconfig/validate.rs`, `kubeconfig_validate`, offline; `kubeconfig_check_connection` only on "Check connection") feeds `ValidationDialog` in `AddClusterDialog`. UI: the cluster menu (rename, namespace, duplicate, delete → `ContextEditDialog` + `Preview`), Settings → Clusters (`SourceSettings.tsx`: writable switch, merge, expiry days), strings `src/locales/<lang>/kubeconfig.json`.

**View and copy** (#228, ADR-0084 amendment): `kubeconfig/view.rs` builds one context's standalone kubeconfig (context, cluster, user, `current-context`; no preferences; file references kept as absolute paths, never inlined). `kubeconfig_view` returns it masked by `kubeconfig/mask.rs` — the one masking, also used by the edit preview; `kubeconfig_copy(clusterId, withCredentials)` writes the full (or the masked) text to the clipboard from Rust (`tauri-plugin-clipboard-manager`, `write_secret` for the full one), so credentials never reach the window. UI `src/features/clusters/kubeconfig/ViewKubeconfig.tsx` (cluster menu "View kubeconfig…", section in the "Connection" tab of the cluster settings; "Copy" confirms first), strings `src/locales/<lang>/kubeconfigview.json`.

### Node shell

A shell on a node is the existing pod exec into a temporary pod `sextant-node-shell-<node>-<rand>` in `kube-system` (privileged, `hostPID`, `hostNetwork`, `nodeName`, `activeDeadlineSeconds` 8 h; image from `AppSettings.node_shell_image`), running `nsenter` into the host (`crates/sextant-core/src/node_shell.rs`, `start_node_shell` in `src-tauri/src/commands/terminal.rs`). The session is registered in `AppState` before the pod is created; the pod is deleted when the tab closes, the cluster is disconnected or the app exits. On connect the core removes only leftovers of the same owner (label `sextant.dev/owner`, a hash of the OS user and machine) and any labelled pod older than 8 h. The user confirms in a dialog first; the MCP server has no tool for it. Node-shell pods are recognised by name or by label (`node_shell::is_node_shell_object`) and are unreachable for agents and extensions, failing closed when the pod cannot be read: no `exec_command`, patch, apply or delete, a drain skips them, and an agent's port forward never reaches them or `hostNetwork` pods: a Pod target is refused, a Service forward skips such pods whenever it picks one and is refused when it has no other (checks in `access_guard/mod.rs`, `mcp/tools_write.rs` and `PodFilter::NoNodeAccess` in `portforward.rs`). Decisions: ADR-0045, ADR-0056.

### Terminal tools

Sextant can install kubectl, Helm, k9s and kubectx/kubens into its own folder `<app data>/tools/<tool>/<vX.Y.Z>/` (`crates/sextant-core/src/tools.rs` — versions, platforms, URLs, checksums, archive extraction and the PATH plan, no network; `src-tauri/src/tools.rs` — `Tools` in `AppState.tools`, the downloads under `download.rs`'s rules with the tools' own allow-list `is_tool_source`). The sources are fixed: `dl.k8s.io` (`stable-<major>.<minor>.txt`, the binary and its `.sha256`), `get.helm.sh` (`helm-latest-version`, the archive and its `.sha256sum`) and the latest GitHub releases of `derailed/k9s` and `ahmetb/kubectx` with their checksum files; a file whose SHA-256 differs is never installed, and an install is written into a temporary folder renamed into place (leftovers swept at start). The backend chooses every version: kubectl is the newest patch of the cluster server's minor version (`apiserver_version`), the others the latest release; the window names only the tool and, for kubectl, the cluster. Only Sextant's terminals use the tools: a cluster's local terminal gets in front of `PATH` the installed kubectl of its server's minor version and the newest of the others, a terminal without a cluster the others only (`Tools::terminal_path`, `pty::spawn_local_shell`); `HelmCli` falls back to the installed Helm when none is found (`helm::cli::set_fallback_tools_dir`). A cluster's terminal shows `KubectlBar` (`src/features/terminal/`) when `tools_kubectl_offer` finds no kubectl, or one out of the supported skew, on that terminal's `PATH` (`AppSettings.terminalTools.offerKubectl`, on by default); Settings → Clusters → "Terminal tools" (`ToolsPanel.tsx`) lists, installs, checks and removes, and the Helm section offers "Install Helm" while none is found. Window only: neither agents nor extensions reach the tools. Decision: ADR-0132.

### Extensions

UI extensions (Lens-style: pages and sidebar sections, details sections, actions, table columns, dock buttons, a settings section) are packages with a manifest `sextant-extension.json`; there are no backend extensions. Each runs in a sandboxed iframe and reaches clusters only through the host's API (ADR-0047, ADR-0049, ADR-0050). Data flow of one call:

An extension may have a backend (ADR-0131): a WebAssembly component (`backend.module`) of the world in `sdk/wit/sextant-extension.wit`, run by `crates/sextant-ext-runtime` (wasmtime; compiled once at install — a component that does not fit is refused before consent — and kept compiled in `<data>/extensions-compiled/`; a fresh instance per call; WASI linked with nothing behind it; limits on time, memory and size). Only the extension's own frames call it, with `backend.call` (`src-tauri/src/extensions/backend.rs`). Inside, `host.call` is the extension API itself (`ExtensionApi::call`, the grant, confirmations and journal), `credentials.get` reads the keyring entries the user entered in Settings → Extensions, and `wasi:http` requests go only to the declared, agreed hosts over HTTPS through the filtering resolver, each journaled. A new backend, host or credential needs consent again (`InstalledExtension.grantedBackend`, `asks_within`). The SDK builds TypeScript backends with componentize-js and Rust ones with cargo; `sdk:check` runs both examples in the runtime.

The extension catalog (ADR-0130) is the fourth install source. Its index (`index.json` of `FriendsOfKubernetes/sextant-extensions`, written by that repository's workflow with the SDK's rules in `sdk/scripts/catalog.mjs`) is fetched only by `src-tauri/src/extensions/catalog.rs` from the one `INDEX_URL`, when the window asks (`extension_catalog`: the Catalog tab open, or Settings → Extensions with a catalog extension installed) and the copy in `<data>/extension-catalog/` is over an hour old, or on Refresh; never with `AppSettings.extensionCatalog.enabled` off. The core (`sextant_core::extensions::catalog`) reads it entry by entry by the workflow's rules and checks a download: `extension_inspect_catalog { id }` takes the entry from the cache, builds the release URLs from checked parts, downloads the package and its `.minisig`, checks size, SHA-256 and the prehashed minisign signature by the entry's `publisherKey` before unpacking, then the manifest's id and version, then the usual consent. The record's source `ExtensionSource::Catalog` pins repository and key: an update from another one is refused, a catalog install never replaces a file/URL install of the same id or the reverse, and a file/URL package with a catalog id is named on the consent screen (`PendingInstall.listedInCatalog`). Window only. Publishers sign with `sextant-ext keygen|sign` (`sdk/scripts/minisign.mjs`, minisign's own format).

```
extension frame ──postMessage {sextant:1, doc, id, method}──► src/extensions/bridge.ts (checks the frame window and `doc`)
   local methods (ui.*, context.get, resources.unwatch) answered in the window
   REMOTE_METHODS ──► api.extensions.call ──► extension_call (src-tauri/src/extensions/api.rs)
        installed + enabled? ─► cluster in `granted.clusters`? ─► decide_extension per (namespace, kind, action)
        ─► node-shell refusal ─► confirmation if needed (mcp-confirm, source "extension") ─► core call ─► extensions-audit.jsonl (ext-audit)
   resources.watch ──► channel onEvent of extension_call (WatchUpdate) ──► bridge ──► {stream, event} back to the frame
```

- **Package and permissions (core)**, `crates/sextant-core/src/extensions/`: `manifest.rs` parses strictly (unknown field → error with its path) and is checked against `manifest.schema.json` (the SDK validates with the same rules; the cases both must agree on are `sdk/test/fixtures/manifest-cases.json`, read by a Rust test too); `permissions.rs` reuses the agent access model (clusters by context name × namespaces × kinds × read/modify/delete/logs/secretValues, `decide_extension`); `package.rs` inspects a zip or folder under limits and installs atomically to `<data>/extensions/<id>/<version>/`; `resolve_package_file` opens a requested file without following links or leaving the package. `AppSettings.extensions` (installed list, source, enabled, **granted** permissions) is owned by the backend (ADR-0052).
- **Serving and managing (Tauri)**, `src-tauri/src/extensions/`: `protocol.rs` serves `sextant-ext://<id>/<file>` (Windows: `http://sextant-ext.localhost/<id>/<file>`) from the installed version or the dev folder; every answer carries a CSP built from that extension's base URL (never `'self'`, ADR-0048), `nosniff` and `no-store`; a disabled or unknown extension is 404. `manage.rs` inspects a file, a folder or a GitHub Release URL into a pending install (token, 10 min; spent only by a successful install, a failed one can be retried, `extension_install_cancel` drops it and its copy at once), installs it only after the user's consent click, and enables, disables, removes and reloads; `dev.rs` polls a dev folder every second (`extension-files-changed`); a manifest that widens its permissions pauses the extension (`needsConsent`; a folder is reviewed in place, a file or link install by installing it again), one that asks for less narrows what is granted to it. Installing is from a folder, a `.zip`/`.sextant-ext` or a GitHub Release link; there is no catalog and no signing (ADR-0053). Storage (`storage.*`) is one JSON file per extension in `<data>/extensions-data/`.
- **Host (frontend)**, `src/extensions/`: `protocol.ts` is the single source of the wire protocol (the SDK keeps a test-checked copy); `bridge.ts` routes messages; `ExtensionFrame.tsx` draws the iframe (sandbox without `allow-same-origin`, theme, language and context pushed in, auto-height for details sections, "Extension failed" with Reload); `contributions.tsx` registers what manifests declare into the registries below with ids `ext:<extId>:<id>` and removes them with `unregisterExtension`; problem rules (`contributes.problems`, sextantApi 2, ADR-0137) are compiled by `problemRules.ts` and registered as the problems category `ext:<extId>` (`src/features/problems/extensionCategories.ts`): the problems store judges them on its own watches, narrowed to the namespaces Rust allows (`extension_problem_scopes`, for the kinds the user agreed to, `InstalledExtension.grantedProblems`), and no extension code runs for them; `ExtensionsHost.tsx` mounts it. The manager (list, consent, permissions, activity, dev reload) is `src/features/extensions/`, a Settings section.
- **SDK**, `sdk/`: types, the frame client (`connect()`, `api.*`, `ui.*`, `storage.*`), `sdk/scripts/{build,pack,check,sync-types}.mjs` (the `sdk:*` npm scripts), `sdk/template/`, and two examples. It is in the repository and not on npm (ADR-0054).

### Tray, window and single instance

`src-tauri/src/tray.rs` creates the tray icon once at start (`tray::install`, desktop only) with the menu Show/Hide, About Sextant, Quit (English texts from `src/locales/en/tray.json` at build time; the window sends the `tray` texts of its UI language with `tray_set_texts` on every language change, `src/features/settings/trayTexts.ts`, and the menu and tooltip are relabelled); `tray::available` is true only if the icon exists and, on Linux, either a StatusNotifier host is registered on the session bus (the `dbus` crate; GNOME without the AppIndicator extension shows nothing) or GTK draws through X11 and a tray owns `_NET_SYSTEM_TRAY_S<screen>` (the XEmbed fallback of i3bar, older XFCE); Wayland without a host is unavailable. The Show/Hide item follows `WindowToggle`: on Linux it says Hide only while the window is visible and focused and otherwise reveals it (GTK on Wayland never reports a minimized window, #115); on Windows and macOS it is visible and not minimized, since opening their tray menu takes the focus. Settings → Window offers `closeToTray` (frontend-written, off by default; disabled with an explanation when `tray_status` says unavailable). `window::on_window_event`: on close, if `hides_on_close(closeToTray, tray_available)` the window is only hidden and `close_all` is not called, so connections, forwards, terminals, the MCP server and installs keep running; otherwise closing exits as before. `window::reveal` is the one way to bring the window back (tray, macOS reopen, a second launch, a confirmation); `lib.rs` `ask_in_window` reveals it and asks the OS for attention before emitting `mcp-confirm`. Single instance (`tauri-plugin-single-instance`, `with_single_instance`) is registered in release builds only, so debug builds, `tauri dev` and e2e run beside an installed copy. Decisions: ADR-0059, ADR-0060.

**About.** The tray menu emits `open-about` (no payload) after `reveal`; `src/features/about/` (`AboutHost`, mounted once in `AppShell`) opens `AboutDialog`, which shows the version, bundle kind, OS and WebView (`about_info`, no paths or user names), the update check and "Copy version info". Settings has an "About" button calling `openAbout()`. ADR-0061.

### Command palette

`src/features/palette/` (`PaletteHost`, mounted once in `AppShell`) opens on Ctrl+K / Cmd+K (`shortcut.ts`; inside text fields, terminals and editors only with Shift). `items.ts` builds what it offers from the existing registries — sections and pages of the active cluster (`getPages`, the resource registry, discovered sections), Settings tabs, clusters — and an object's actions come from the action registry, so they ask the same confirmations as the buttons and extension contributions appear the same way. Objects are found by name through `objectIndex.ts`: metadata-only watches, started only at the first typed character, for `COMMON_KINDS` the cluster serves plus the open table's kind; other kinds when the query starts with a kind (`deploy web`, `crd:`) or after "Search all kinds" (at most 80); at most 6 kinds listed at once, events never, unwatchable kinds skipped silently; a watch nobody uses is kept 30 s and then stopped; at most `MAX_INDEXED_OBJECTS` objects of a kind are kept (`WatchOptions.maxObjects`) and the footer says when a kind was searched only partly. Ranking is `fuzzy.ts`; recent items are kept in `store.ts`.

### Logs of several pods

A merged logs tab is the ordinary `logs` dock tab with a `MultiLogsPayload` (`src/features/logs/multi/open.ts`): a label selector in a namespace (a workload, a ReplicaSet, a Service, or typed), followed as pods come and go, or a fixed set of pods selected in a table. `session.ts` runs one ordinary log stream (`api.logs.start` through `openStream`) per container run — a restarted container is a new run — at most 20 at once (the rest wait for a slot), stops the stream of a target that went away while keeping its lines, and flushes into one bounded buffer every 100 ms; the line and text caps of `buffer.ts` apply to the merged buffer. `model.ts` holds the pure parts: targets, stable per-pod colours (`--logs-src-<n>` in both themes), JSON parsing with levels, the text or regex filter. No backend code was added.

### Logs of gone pods (Loki)

Window only (#265, ADR-0118). `sextant_core::loki` finds Loki like Prometheus — the Services the Loki Helm charts create (`loki-gateway`, `loki-query-frontend`, `loki-read`, `loki`, and the loki-distributed / loki-stack names) in a few namespaces and by `app.kubernetes.io/name`, probed through the API server's service proxy — or takes the Service, port and path prefix named in `clusters[id].loki` (also Off, and a tenant sent as `X-Scope-OrgID`). `/loki/api/v1/labels` picks one of two label schemes (`namespace`/`pod`/`container`, or the OpenTelemetry `k8s_*_name` labels). The window sends only names, a range (≤ 24 h) and a line limit (≤ 5000); the core writes the one stream selector and every parameter, reads `query_range` in pages of 1000 the way `logcli` does (the boundary timestamp's lines deduplicated), within 30 s and 8 MiB per request, and sends pages through the read's channel (`loki_logs_start`, a subscription in `AppState` like a log stream). In the pod logs tab, "Load older lines from Loki" ends the read where the shown container run began (now for a gone pod), so Loki's lines, marked "Loki", come before the live ones; with timestamps on, those the oldest live lines repeat are dropped. A workload's details list the pods its controller made that Loki has lines of (label values with an anchored name pattern, ≤ 200), each opened in a tab of Loki's lines only.

### Rollout history and rollback

Deployments, StatefulSets and DaemonSets get a "History" details tab (`src/features/rollouts/`): the rollout status, the revisions (the ReplicaSets or ControllerRevisions the workload controls, from watches), a side-by-side diff of two pod templates (`TemplateDiff.tsx`) and "Roll back to revision N" (`RollbackDialog.tsx`, also the `rolloutUndo` action), whose JSON patch (`model.ts`) is what `kubectl rollout undo --to-revision` sends and goes through `resource_patch`. The MCP tool `rollout_undo` uses the same rule implemented in the core (`crates/sextant-core/src/resources/rollouts.rs`: `history`, `undo`) under Modify on the kind. Decision: ADR-0068.

### Restart

"Restart" (`src/features/restart/`, one action for one object or a multi-selection) plans a step per object (`model.ts`): a rollout restart of a Deployment, StatefulSet or DaemonSet (`workload_restart`; a paused Deployment refused), `spec.restartAt` of an Argo Rollout (`kubectl argo rollouts restart`'s merge patch, `argo-rollouts/patches.ts`), the owning Deployment or Rollout of a ReplicaSet (one step per owner), the pods of an unowned ReplicaSet deleted one at a time — each after the ReplicaSet has as many Ready pods again, followed by one shared pod watch, at most 5 minutes per pod —, and a pod of a ReplicaSet, StatefulSet, DaemonSet or ReplicationController deleted with its uid precondition. Bare, Job, mirror, node-shell and debug-copy pods are not offered. One confirmation lists every step (20 named, the rest counted) and the patches; `run.ts` reads each object again right before sending, sends each request once, one step at a time, and "Stop" starts nothing more; the result lists what was restarted, failed (and why), stopped partway or not started. No command was added; agents and extensions get nothing new. Decision: ADR-0112.

### Actions on selected rows

While rows of a resource table are selected, `ResourceTable` renders the selection bar (`src/features/bulk/SelectionBar.tsx`) between its header and its rows: "N selected", the actions and "Clear selection", a labelled toolbar with a polite live region for the size. The actions are the registry's (`selectionActions`): the table's action ids with `multiple`, judged by each action's own `appliesTo`, danger last — the bar special-cases none. An action that applies to only part of the selection is offered with "2 of 4" and first opens `PartialDialog`, which lists what it leaves out and why (`ActionDef.notApplicableReason`; Restart's `whyNotRestart`), then runs it on the applicable part through its own confirmation. The Delete key on a selected row takes the same path for Delete. Delete itself (`src/features/actions/DeleteDialog.tsx`, one object or many) names the objects (50, then a count), marks those a controller or Flux / Argo CD will bring back, warns about Namespaces, asks for the count above 20, and `deleteRun.ts` sends one `resource_delete` at a time with the confirmed uid as precondition (a replaced object is kept), Namespaces last, never repeated, with Stop and an outcome per object; the run is kept per dialog entry (`deleteStore.ts`). No command was added; agents and extensions get nothing new. Decision: ADR-0126.

### Set image

"Set image…" on Deployments, StatefulSets, DaemonSets, CronJobs and bare Pods (`src/features/set-image/`) lists the containers and init containers with their images (ephemeral containers never), checks each typed reference by the image grammar (`reference.ts`) and sends `workload_set_image`: the core (`crates/sextant-core/src/resources/set_image.rs`) reads the object, checks every named container and its shown image, and sends one strategic-merge patch of `{name, image}` entries with that read's `resourceVersion`. `workload_set_image_dry_run` is the same patch with `dryRun=All`, shown by the safe-apply preview (first, on a cluster that previews changes). A Pod a controller owns gets its owner offered instead (the core refuses it and a static Pod's mirror too). A change confirmed from a preview carries the `resourceVersion` the preview read and is refused (`conflict`) when the object changed since; the dialog then shows a fresh preview. Window only. Decision: ADR-0098.

### Safe apply: dry run and diff

Before the editor's Save (PUT) or an apply of YAML ("Create resource") is sent, `resource_dry_run` (`crates/sextant-core/src/resources/dry_run.rs`) sends the same request with `dryRun=All` and the `sextant` field manager and returns, per object, the live object and what the API server would store (defaulting, admission webhooks and validation included), without `managedFields`, `resourceVersion` and `generation`; an apply keeps a refused document's error with that document. A Helm upgrade or install is previewed by `helm_upgrade_preview` / `helm_install_preview`: `helm … --dry-run=server --output json` through `HelmCli` (its scrubbed environment and temporary kubeconfig) against the release's stored manifest, both cut into documents (a `List` item by item) and ordered by object, Secrets and unclassifiable objects masked or left out (`helm::diff`); the render runs under a 120 s limit as a tracked task (`AppState.subscriptions`, stopped by `helm_preview_stop`, closing the cluster, a reload or exit). The frontend (`src/features/safe-apply/`) shows both sides with the rollouts' `TemplateDiff`. Per cluster, `clusters[id].previewChanges` (frontend-written; `null` follows the name: on when the display name, context or cluster name has `prod`/`production` as a word) makes the preview a step of every such change; off, it stays a button. MCP `apply_yaml` / `patch_resource` take `dryRun: true`: the same requirements, checked by `Guard::check_dry_run` (rules decide, nobody is asked; a dry run touching a Secret also needs "Secret values" and never says whether a value would change, ADR-0043), journaled as `<tool> (dry run)`; every write tool refuses unknown argument fields, so a misspelt `dryRun` (or `dryRun` on `delete_resource`) never makes the change; the agent gets field-level changes clipped like the journal (`src-tauri/src/mcp/dry_run.rs`). Extensions get nothing new. Decision: ADR-0074; the Secret rules for agents are ADR-0043.

### Debug containers and copying files

**Debug containers** (`crates/sextant-core/src/debug.rs`, `kubectl debug`): `debug::start` either patches the pod's `ephemeralcontainers` subresource with `debugger-<rand>` (optionally targeting a container's processes) or creates a copy `<pod>-debug-<rand>` without the original's labels, owners, node and probes, with a shared process namespace, an 8 h deadline, the debug container and optionally a replaced command, labelled `managed-by=sextant`, `sextant.dev/debug-copy`, `debug-session`, `debug-owner`. The terminal attaches to the debug container's own process (`exec::attach_terminal`), and closing it ends that process. `debug_start` (`src-tauri/src/commands/terminal.rs`) registers a placeholder session in `AppState` before anything is sent; the copy (`DebugCopyPod`) is the session's guard, deleted on tab close, `close_cluster`, `streams_reset` and exit (`debug::wait_for_deletions`). Starting a copy sweeps this owner's copies of other runs and anyone's older than 8 h in that namespace. The dialog (`src/features/terminal/DebugDialog.tsx`) opens from a container in pod details (`ContainerTools.tsx`) and from a shell tab; the default image is `AppSettings.debug_image`. Agents cannot `exec_command` in a debug copy (`refuse_live_debug_copy` in `mcp/tools_write.rs`, fail closed). Decision: ADR-0064.

**Copying files** (`crates/sextant-core/src/files.rs`, `kubectl cp`): `tar` runs in the container over exec. `files_stat` reads the first tar header (kind, size, link target; a folder's size from `du -sk`); `files_download_start` streams `tar cf -` into `receive`, which accepts a single regular entry with the asked name (unpacked) or keeps a folder as `.tar.gz`, writes to an exclusive `.sextant-download-*.part` next to the destination and renames it only on success; `files_upload_start` writes a tar stream of one local file into `tar xf -`. Transfers are streams whose `TransferEvent`s come through the channel of their start command (progress at most every 100 ms, `done`, `error`) and subscriptions of their cluster in `AppState`, stopped by `files_transfer_stop`, disconnect, `streams_reset` and exit (`src-tauri/src/commands/files.rs`). UI: `src/features/terminal/FilesDialog.tsx`. Neither debug containers nor file copy is an MCP tool or an extension method. Decision: ADR-0065.

**Image files** (#216, ADR-0103): an image's files read straight from its registry, without exec or a pull. The core (`crates/sextant-core/src/image_fs/`, no network) parses references, challenges, Docker configs and manifests, reads a pod's image and pull secrets (`pull_secrets::pod_image`, the pod's then its ServiceAccount's), indexes a layer stream given as `std::io::Read` (sha256 and size counted on the compressed bytes, gzip/zstd under a decompression-ratio limit, tar with pax and GNU long names) into a `LayerIndex`, merges indexes into a `MergedTree` per the OCI layer rules (whiteouts, opaque folders; NUL-joined keys so a folder lists by range seeks), finds one file's data again (`extract_file`, `save::save_file` through an exclusive `.part` file renamed only after the layer's digest checked), and caches indexes by layer digest (`cache.rs`, 256 MiB LRU). The app (`src-tauri/src/image_files/`) holds the one HTTP client that fetches from a host the app did not choose: `registry.rs` — HTTPS only, a filtering DNS resolver and URL checks that refuse loopback/link-local/metadata addresses, the Bearer token flow with a self-built pull scope, same-origin manifest redirects, credential-free blob redirects — and pumps response bodies into blocking indexer threads (`BodyReader`). `image_files_open_start` / `image_files_read_start` / `image_files_download_start` are streams through `openStream`, subscriptions in `AppState`; an opened image is an `ImageSession` in `AppState.image_files` (≤ 4) under its open stream's id, closed by `image_files_stop`, its pod's cluster closing, `streams_reset` and exit. UI: the "Image files" page in Workloads (`src/features/image-files/`), opened from a pod's container header. Window only.

**Split panes, snippets and broadcast** (#154, frontend only): every terminal dock tab ("exec", "terminal") is a `PaneLayout` (`src/features/terminal/PaneLayout.tsx`) over a layout tree (`layout.ts`: split, close, resize, neighbour for Ctrl+Shift+Arrow; at most 8 panes). Panes are absolutely positioned and keyed by id, so splitting or closing never remounts the other panes' terminals. Each pane is its own backend session started by the same commands as a tab (local, container, node, debug; node and debug panes ask the same confirmations), so flow control and caps apply per pane. Snippets are the frontend-written `AppSettings.snippets` (read entry by entry, `settings/snippets.rs`); `{{namespace}}`, `{{pod}}`, `{{container}}`, `{{cluster}}`, `{{context}}` are filled from the focused pane, each value quoted for that pane's shell (POSIX `'…'\''…'`; PowerShell, the local shell on Windows, `'…'` with ASCII and typographic single quotes doubled; an unknown shell refuses values with quotes; backslashes, control, invisible and text-direction characters are refused everywhere), the text typed on one line without control, zero-width or bidi characters (which a snippet may not contain at all); only "Run" adds Enter, and only into the focused pane, also while broadcast is on. Broadcast input (`broadcast.ts`) is off by default: the user picks at least two target panes (panes of other clusters are listed apart and never preselected), every target shows a banner naming the clusters, the first keystroke of each activation opens a confirmation that takes the keyboard focus, and everything typed before confirming is dropped (never broadcast), and broadcast ends when it is turned off, the confirmation is refused or a target pane closes. Nothing of this is offered to MCP agents or extensions. Decision: ADR-0088.

### Cluster problems and notifications

Entirely in the frontend (#136, #135). `src/features/problems/model.ts` is the one set of pure detection rules — pods (CrashLoopBackOff, image pulls, OOM kills, recent restarts, pending with the scheduler's reason, not ready), nodes (NotReady, pressure), workloads with unavailable replicas (not during a rollout), failed Jobs, pending/lost claims, cert-manager Certificates (not ready, issuance failed, expiring within `notifications.certExpiryDays` — 14 by default —, expired), Flux/Argo CD/Gateway API objects judged by their sections' own helpers, and Warning events (screen only). TLS Secrets are not a source (ADR-0069). A rule says when a problem starts to count (`since` + a grace, or `activeFrom`) and until when, so `isActive(problem, now)` needs no new update. `store.ts` shares one watch per (cluster, kind) between every user (`acquireSource`, refcounted, closed 5 s after the last release) and keeps only the problems of each update, never the objects (at most 2000 objects with problems per kind); when a cluster connects or disconnects its sources are dropped at once and users acquire anew (`epochOf`), since the backend closes a cluster's watches without a word. Notifications follow an owner where runs or replicas come and go (a CronJob for its Jobs, the workload of a pod: `notifyKey`). The page "Problems" (section "Cluster", after "Overview"; the section header counts, through `registerSectionBadge`, the problems of the open cluster that would notify — not a pending pod, a single restart or a Warning event) groups them by category and namespace, follows the namespace filter and has "Only new since…".

Notifications (`src/features/notifications/`) are on by default but watch only clusters that are already connected and not muted, and only the enabled categories (`AppSettings.notifications`, frontend-written: `enabled`, `disabledCategories`, `enabledCategories` — the opt-in categories, off until turned on: `security`, `practices` —, `mutedClusters`, `mutedUntil`); `NotificationsHost` (in the `railFooter` slot, draws nothing) hands each source to `engine.ts`: the first look at a source is quiet, a state (`Problem.notifyKey`) is told once while it lasts and again only after a 30 min cooldown, what starts within 3 s is shown one by one up to 3 or as one summary, at most 6 a minute, a notification whose problem went away while it waited is dropped, and "Mute for 1 hour" sends what is due only to the in-app history (last 100, on the problems screen). Text from the cluster is clipped and made inert (`&`, `<`, `>` become look-alikes), since Linux notification servers read the body as markup. The OS shows them through the Tauri notification plugin (`api.notifications`, wrapped in `transport.ts`, permissions in `src-tauri/capabilities/notifications.json`); a click (`tap`) reveals the window (`reveal_on_notification_click` in `lib.rs`) and the page opens the object, the notification's "Mute for 1 hour" button sets `mutedUntil`. Nothing leaves the machine. Decisions: ADR-0066 (one rule set), ADR-0067 (notifications).

### Metrics sources: Prometheus and VictoriaMetrics

Every Prometheus query goes through one client (`crates/sextant-core/src/metrics/prometheus.rs`, `Prometheus`) to a `PrometheusTarget` — a Service reached through the API server's service proxy (namespace, name, port, path prefix) or a URL — and "Prometheus" in the metrics code means any Prometheus-compatible HTTP API. Auto-detection (`detect`, cached a minute per cluster) lists the Services of `CANDIDATE_NAMESPACES` (7, in parallel), matches them by `known` names — Prometheus (`prometheus-operated`, `prometheus-server`, `*-kube-prometheus-prometheus`, `prometheus`), VictoriaMetrics single-node (`vmsingle-*` on 8429/8428, `*victoria-metrics-single*-server` on 8428) and a VictoriaMetrics cluster's vmselect (`vmselect-*`, `*-vmselect` on 8481, path prefix `/select/0/prometheus`) — and probes them in order: every Prometheus first, then VictoriaMetrics, each by namespace and rank. The probe is `api/v1/status/buildinfo`, and `vector(1)` when something answered that with an error (VictoriaMetrics before v1.77). `source_kind` tells the window what a target is (`MetricsStatus.prometheusKind`); the manual address in the cluster settings has presets that fill the port and path prefix (`SettingsSection.tsx`). The same fixed queries serve both: VictoriaMetrics' differences (rate without extrapolation, answers 30 s behind `now`, step-time `timestamp()`) are measured in `tests/victoria_metrics.rs` and bounded in ADR-0102.

### Request metrics

Request rate, error rate and latency of a workload or pod, and CPU throttling per container (#212). Core `crates/sextant-core/src/metrics/requests.rs` (+ `requests/services.rs`) and the PromQL in `metrics/prometheus/requests.rs`: `request_sources` asks the cluster's Prometheus (and, without Linkerd metrics there, linkerd-viz's own `prometheus:9090`) which of 12 known metric names exist (one `label/__name__/values` request with `match[]`, kept 5 minutes per connection and Prometheus settings) and derives the sources — Istio, Linkerd, ingress-nginx, Grafana Beyla, Cilium Hubble; `request_health` validates the `RequestTarget` (strictly read: names only), builds each source's label matchers (`request_selectors`: workload labels where the source has them, else the controller-made pod names of right-sizing; ingress-nginx through the Services that select the pods, read in the core), runs one tagged instant query (rate, errors, p50/p95/p99 over 5 minutes) and one range query (last hour, step 60 s) per source, and the throttled share of CFS periods over the last hour per container (≤ 50). `metrics_request_health` is window-only and read-only. Frontend `src/features/request-health/`: the "Requests" details section of Deployments, StatefulSets, DaemonSets and Pods (order 52, after the CPU/memory metrics), polled once a minute through the metrics feature's shared pollers while shown, with small charts, a "no source" state naming what would provide the data, and a CPU-limit hint tied to right-sizing's recommendation. Decision: ADR-0095.

### Alerts (Prometheus and Alertmanager)

Window only (#264, ADR-0119). `sextant_core::alerts::report` asks two sources in parallel and reports each one's state: the Prometheus-compatible source of the cluster settings (`metrics::Prometheus::get_raw_limited`, `api/v1/alerts`; for VictoriaMetrics `vmalert/api/v1/alerts`, which single-node and vmselect proxy only with `-vmalert.proxyURL`) and the Alertmanager — found by its chart and operator Service names in `metrics::CANDIDATE_NAMESPACES` (≤ 100 Services per namespace, ≤ 4 probes of `api/v2/alerts`, kept 5 minutes per connection, "not found" one) or named by `clusters[id].alertmanager` (`validate_target`), reached only through the service proxy with two fixed GETs (`api/v2/alerts`, `api/v2/silences`). Answers are capped (20 s, 8 MiB, 5000 alerts and silences), read element by element, clipped, and every text and link cleaned (`clean_text`/`safe_uri`); firing Prometheus alerts that Alertmanager holds (a label subset) are dropped. The window (`src/features/alerts/`) polls `alerts_list` once a minute per cluster while the page, a details section, the settings block or the opt-in `alerts` problems source holds it (`store.ts`), maps alerts to objects by fixed label names (`model.ts` `TARGET_LABELS`, skipping the labels the scrape target adds) and lists a workload's pod alerts through the shared workload pod watch.

### Traffic graph

Who calls whom with an end in up to five namespaces, how often, how many calls fail and how slow (#211, ADR-0096). Core `crates/sextant-core/src/metrics/traffic.rs` and the PromQL in `metrics/prometheus/traffic.rs`: the edge sources come from the same `request_sources` lookup as the request metrics (`RequestSources.edges`: Istio, Linkerd, Grafana Beyla's service graph, Cilium Hubble — all through Prometheus, no Hubble Relay); per source a fixed table of series families (`EdgeShape`/`Part`) that each count a call once (where a source reports a call at both ends — Hubble, Beyla — the callee's report, plus the caller's only for pairs the callee does not report: `or on(<pair>)`), summed by the source's own labels; each part's `End` tables say which label names which end, read back by `assemble`. Each part is asked on its own: its `topk(200)` busiest edges over 5 minutes or an hour (the only query that may fail the source), then errors, HTTP status classes and p50/p95, each best-effort (a failed one is named in the edge's `missing`) and restricted to the busiest edges (`and on(...) topk`) only when the part has more (then its count is asked too); every URL stays under 6 KiB (≤ 5 KiB of query with five 63-character namespaces, a test), a URL-mode Prometheus gets a form POST after a 414/431, the service proxy says the query was too long (`queryTooLong`); 8 MiB / 4000 series per answer. Ends without a name are "unknown" nodes; a TCP edge beside an HTTP/gRPC edge of the same source and ends is dropped. Command `metrics_traffic_graph` (window only, read-only). Frontend `src/features/resource-map/traffic/`: the "Traffic" tab of the map page, laid out by the map's `placeColumns` (callers left), lines as thick as their request rate (per pair of ends the busiest source's, so Istio and Hubble on one cluster are not added up; TCP connections per second kept apart) and coloured by their error rate through theme tokens, filters that only change the drawing, a node or line opening a side panel whose ends are looked up on the click (Deployment, StatefulSet, DaemonSet or Service; at most three GETs, only for names the kind can have; "not found" believed for a minute) and opened in the details, or at their Requests section; a "List" tab with the same calls for the keyboard and screen readers. Polled by the metrics feature's shared pollers (a tick is skipped while the last load is in flight) only while the tab is shown and the window visible.

### Charts from metrics-server and a node's pods

Without a Prometheus-compatible source, the charts of a pod's, a workload's or a node's details are drawn from metrics-server (#280): `HistoryCharts` (`src/features/metrics/components.tsx`) samples the values the window already polls every 30 s (`usePodUsageIn`, `useNodeUsage`) into a ring per (cluster, target) in `src/features/metrics/history.ts` while the chart is shown — one sample per poll answer, the last hour, ≤ 150 samples, ≤ 30 rings per cluster and 100 overall (a shown ring is never pushed out), kept 10 minutes after the last view, dropped when the cluster's connection changes — and says "Since opened · metrics-server, no history"; no request is added and nothing is persisted. The table search matches the text of every shown column (#279): `createRowText` (`src/components/Table/search.ts`) builds each object's column texts once (`ColumnDef.searchText` where the cell shows something else than `value`, e.g. the age), and only the timed texts again as the table's clock moves. A Node's details have the tabs "Pods" (the resource table of the node's pods, one watch by `spec.nodeName`) and "Resources" ("Allocated resources" as in `kubectl describe node` and each pod's requests, limits and usage) from `src/features/node-pods/`. Decision: ADR-0125.

### Right-sizing

Requests and limits against usage (#137). The core builds fixed PromQL for a scope — namespaces (≤ 200), a workload or a pod — over the last day or 7 days (`crates/sextant-core/src/metrics/history.rs`, `metrics/prometheus/rightsizing.rs`): per namespace, pod and container the p95 of the 5-minute CPU rate, the peak working set, the throttled share of CFS periods, first and last sample. Names are validated (`validate_scope`) and escaped; a workload's pods are selected by the names its controller gives them (anchored regex over Kubernetes' safe alphabet), so pods replaced inside the window count and similarly named workloads do not; queries are bounded (`timeout=18s`, client 20 s) and the answer capped at 5000 containers. `metrics_usage_history` resolves the cluster's Prometheus from the cluster settings (`notFound` without one). The frontend (`src/features/rightsizing/`) groups live pods into workload rows (`group.ts`: the owning workload, the newest running pod's requests and limits including native sidecars, OOM kills in the last 7 days, gone pods by name), applies the rules of `recommend.ts` (headrooms, rounding, flags, confidence, waste) and shows them on the "Right-sizing" page of the Workloads section (≤ 10 namespaces of the filter, ≤ 1000 rows, history polled every 5 minutes) and as a details section of Deployments, StatefulSets, DaemonSets and pods. Without Prometheus it falls back to a metrics-server snapshot (no recommendation) or to the specs alone. Read-only: the result is a `resources:` snippet on the clipboard. Decision: ADR-0070.

### cert-manager and TLS certificates

The sidebar section `certManager` (a discovered section, shown only while the cluster serves a cert-manager kind) lists Certificates, CertificateRequests, Issuers, ClusterIssuers, Orders and Challenges with Ready and reasons, an "Only problems" filter and a counter (`src/features/cert-manager/`). Details explain the common failures in plain words and show the issuance chain Certificate → CertificateRequest → Order → Challenge by owner references (`model.ts`, `details.tsx`). No "renew" action. For any Secret with `tls.crt` the "Certificate" details section asks the backend for the parsed chain and `ca.crt` (`tls_certificate_info`), and the "TLS certificates" page (Config section) lists the `kubernetes.io/tls` Secrets of the namespaces in view by expiry (`tls_expiry_scan`) when opened, when the filter changes and on Refresh. `crates/sextant-core/src/tls.rs` reads Secrets with the user's credentials, parses only `tls.crt`/`ca.crt` (`x509-parser`), wipes every other value and annotation at once and the certificates after parsing, validates names before any request, bounds every request by `STEP_TIMEOUT` and caps the input (256 KiB per value, 16 certificates, 1000 Secrets, 200 namespaces). "Expiring" everywhere is `AppSettings.notifications.certExpiryDays` (frontend-written, 1–365, default 14; `CertExpiryField.tsx` in Settings → Notifications and on the TLS page); the problems store applies a change to the problems it holds (`applyCertExpiryDays`). Decision: ADR-0069.

### Security posture

Frontend only and read-only (#143, `src/features/security/`). `pss.ts` evaluates the Pod Security Standards (Baseline and Restricted, as of Kubernetes v1.37) on a Pod or the pod template of a Deployment, StatefulSet, DaemonSet, ReplicaSet, Job or CronJob — every container list including init and ephemeral containers, pod-level settings inherited where the standard says so, the Windows exemptions, the user-namespace relaxations, and controls or allowed values added in later versions only from that version (`<mode>-version` labels). A finding has the exact field path from the object's root, the value found and a fix as a strategic merge patch (`snippet.ts` writes it as YAML; nothing is applied). Hardening hints (read-only root filesystem, requests/limits, an unpinned image, the service account token) are `hint`, never violations. `namespaces.ts` reads the `pod-security.kubernetes.io/enforce|audit|warn` labels and says which workloads each would reject, record or warn about. The "Security" page (section "Cluster": a cluster-wide posture like the problems screen it feeds; Access Control holds RBAC objects) is bounded by the namespace filter like right-sizing (a choice of namespaces, at most 20 watched, only while open); the "Security" details section covers workloads and Pods. Trivy Operator (`aquasecurity.github.io`) has a discovered sidebar section `trivy`; a workload's reports are found by the operator's labels (`trivy-operator.resource.kind/name`, a Deployment's through its live ReplicaSets) and watched in its namespace by label selector only while shown; counts come from the reports' own `summary` and at most 50 rows (10 in a workload's details) are listed. A Pod, ReplicaSet or Job is judged itself only when no judged controller holds its template (a Rollout's ReplicaSet, a static Pod, a bare ReplicaSet are); the page and the details also read the live Pods of the workloads in view and report on the owner, marked "added at admission" and without a fix, the violations a Pod has and its template does not (a webhook-injected `istio-init`). Baseline violations feed the problems screen, the Cluster counter and the notifications as the opt-in category `security`, off until `notifications.enabledCategories` has it (one saved setting: the problems screen's "Security findings" and Settings → Notifications write it). Its sources are its own (`sourceKey` adds `|security`): they watch Pods, Deployments, StatefulSets, DaemonSets, ReplicaSets, Jobs and CronJobs only while the category is on, and nothing of them reaches the other categories, the map's colours (`resolve` judges a source's own category) or their `MAX_PROBLEM_OBJECTS`. Trivy reports are not a problem source (a background watch of every report would move whole vulnerability lists for a count). Decision: ADR-0076.

### Best practices

Frontend only and read-only (#207, `src/features/practices/`). `model.ts` reduces a Deployment, StatefulSet, DaemonSet, CronJob or Job (a CronJob's Jobs are judged through it) to a compact `WorkloadInfo` once per object version, and HPAs, PodDisruptionBudgets, LimitRanges and live Pods (node by workload) to rows of their own; `checks.ts` runs pure, conservative checks over them — reliability: readiness probe (only when a container declares a port; Deployments, StatefulSets, DaemonSets), liveness probe (Deployments, StatefulSets), one probe of a kind anywhere in the pod suffices, init containers skipped; `:latest` or untagged images (a digest pins); `imagePullPolicy: Always` on a digest; one replica (0 and `Recreate` ignored; an HPA's `minReplicas` 1 counts); several replicas without a PDB; a PDB that lets nothing be evicted (rounded like the disruption controller, at the current replicas and the PDB's `expectedPods`); every live replica on one node without spread or anti-affinity in a cluster with ≥ 2 schedulable nodes — efficiency: CPU/memory requests (a limit set alone or a LimitRange default counts), a memory limit (no CPU limit is asked for), limits ≥ 2× the right-sizing recommendation (Prometheus history only, #137), an HPA with min = max. A check whose input is unknown (a list not read, forbidden or truncated) is skipped. Each finding has a severity, the field path (on the HPA or PDB when that object holds it), why it matters and a fix (a strategic merge patch, or a whole PDB to create) written by the Security page's `snippet.ts`. The "Best practices" page (section "Cluster", after Security: both judge pod templates across namespaces) is bounded like the Security page (a choice of namespaces, at most 20 watched, with the Security page's specs so the lists are shared); the details section reads its namespace's HPAs, PDBs and LimitRanges through the resource map's shared watches and the workload's pods through the right-sizing/cost watch; the node count is a tap on the problems store's Node watch. `AppSettings.practices` (frontend-written, read leniently and capped in `settings/practices.rs`): `disabledChecks` (a check not listed is on) and `excludedNamespaces` (default `kube-system`, `kube-public`, `kube-node-lease`), applied to the page, the details and the problems. The opt-in problems category `practices` (in `OPT_IN_CATEGORIES`, off by default) has an `external` source (key `|practices`): its provider (`provider.ts`) taps the store's cluster-wide watches — the `workloads`, `jobs`, `pods` and `nodes` sources (shared) and CronJobs, HPAs, PDBs and LimitRanges (held only while the category is) — reduces each update to rows at once and looks again at most every 500 ms; one problem per workload and check, only High and Medium ones notify; the right-sizing check is not a problem (it needs history).

### Resource map

Frontend only (#139, `src/features/resource-map/`). `relations.ts` turns watched objects into a graph whose edges point from the object that names or selects to the one named or selected: owners, label selectors with per-kind semantics (`selectors.ts`), EndpointSlices, Ingress and Gateway API backends, parents and TLS references (through the Gateway API model), pods → ConfigMaps / Secrets / ServiceAccounts / claims / nodes, PVC → PV → StorageClass, HPA → target, classes. `impact.ts` states what a deletion would do (cascade by owner uid only and only when every owner is gone, what recreates it, what fails; `optional` references ignored), one i18n sentence per consequence. `data.ts` plans the watches — a namespaced object's namespace lists of `NAMESPACE_KINDS` the cluster serves, a cluster-scoped object's few naming lists (`nodePlan`) — and `watches.ts` shares them between views (one per kind and namespace, released 5 s after the last user, flushed every 100 ms, dropped on connect/disconnect by `epochOf`). Views: the details tab "Related" of every kind (≤ 4 namespaces at once; a Service also gets routes of other namespaces through the Gateway API reverse links) and the page "Map" in the Cluster section (≤ 3 namespaces of the filter, layered columns without a graph library, groups above 5 per owner or 30 per kind, ≤ 400 nodes, health from the problem rules via `health.ts`). Decision: ADR-0072.

### RBAC: who can do what

`src/features/rbac/` (#140). `engine.ts` mirrors the RBAC authorizer over watched Roles, ClusterRoles, RoleBindings and ClusterRoleBindings (wildcards, subresources, `resourceNames`, RoleBinding scope, ServiceAccount users and groups, aggregation with not-yet-stored rules marked pending); `hooks.ts`/`sharedWatch.ts` watch the four lists only while a view needs them, shared and refcounted, namespaced lists only in the namespaces of the filter, and report a forbidden list as unknown. The "Permissions" page (Access Control section) has Subject (a verbs × resources matrix per namespace, each cell naming the bindings, roles and rules, ≤ 500 rows), Who can (≤ 1000 grants) and Can I — SelfSubjectRulesReview and SelfSubjectAccessReview through `crates/sextant-core/src/rbac.rs` (`rbac_rules_review`, `rbac_can_i`: ≤ 64 questions, 8 in parallel, each under `STEP_TIMEOUT`), which is authoritative for the current user, while the computed tabs leave out other authorizers and `system:masters`. Details sections explain Roles and ClusterRoles, bindings and ServiceAccounts and open the page on a subject. Decision: ADR-0071.

### Known namespaces and the access check

A user who may not list Namespaces (#285, ADR-0124) would see every cluster-wide watch refused. Per cluster the window keeps known namespaces (`ClusterSettings.knownNamespaces`: everything typed or selected in the namespace filter, plus what "Accessible namespaces" in the cluster settings adds; read leniently in the core) and, once per connection, asks the API server about the user's own permissions (`src/features/namespaces/accessStore.ts`): one SelfSubjectAccessReview "list namespaces"; when refused, candidates from the context's namespace, the ServiceAccount's (SelfSubjectReview, `rbac_whoami`), OpenShift projects and the known names, each asked "list pods in it?" in batches of 64, cluster-scoped kinds by access reviews and namespaced kinds by up to 10 rules reviews. While restricted, "All namespaces" is the accessible known and found namespaces (≤ 20) in one place, `useSelectedNamespaces`, and the problems store and the palette index watch the same scope; a table whose kind cannot be listed says "No access" once instead of starting a refused watch. Everything is window-only and in memory per connection.

### Overview of several clusters

Frontend only and read-only (#144, `src/features/fleet/`). "All clusters" at the top of the cluster rail sets `useAppStore().homeView = "fleet"`: the active cluster steps back (its connection stays) and the main area draws the `home` slot; opening a cluster (rail, palette, notification, a link on the page) or picking one to connect in the welcome area clears `homeView`, so the page unmounts and its watches close. The chosen clusters are `AppSettings.fleet.selected` (frontend-written). Per connected selected cluster the page holds: the problem sources of every category except the opt-in `security` (`useClusterProblems`, shared with the problems screen and the notifications; the Warning events table reads their `events` source instead of watching events again), the metrics pollers (shared cache), compact node rows and, for the open tab only, compact rows of Pods or Deployments/StatefulSets/DaemonSets. Rows are taps on the problems store's watches (`rowsStore.ts` → `acquireRows`: each update reduced to a few fields, at most `MAX_KEPT_ROWS`), so there is never a second watch of a (cluster, kind). At most `MAX_SELECTED` (10) clusters are chosen, and "Connect all selected" connects `CONNECT_CONCURRENCY` (2) at a time. Tables show at most `MAX_SHOWN_ROWS` per cluster after the cluster and namespace filters and count the rest. "Find by name" uses the palette's `useObjectIndex` (metadata-only, at most six default kinds per cluster or the one kind the query names) and `objectGroups`. A link opens the object in its cluster (`openTarget` of the notifications, over the table of its kind). Decision: ADR-0077.

### Cleanup

`src/features/hygiene/` (#147), the "Cleanup" page of the Cluster section: objects that look unused or left over, each with why (an i18n reason), what its age counts from (created, finished, in its phase) and the resource map's deletion impact. `rules.ts` is the one pure rule set: claims no Pod or template mounts (StatefulSet claim templates, VolumeSnapshots and data sources keep them; the bound volume's reclaim policy is said), Released or unclaimed Available PersistentVolumes (a Released one with reclaim policy Retain is shown as kept on purpose, never offered), Services without endpoints whose selector matches no Pod or template, ReplicaSets beyond `revisionHistoryLimit`, finished Pods not run by a Job or an unknown controller, finished Jobs without a CronJob or `ttlSecondsAfterFinished`, empty namespaces in view, and — only when the user turns them on (`AppSettings.cleanup.checkConfigMaps` / `checkSecrets`, off by default, with a warning that Sextant cannot see every reference) — ConfigMaps and Secrets nothing names: pods and every pod template (CSI and in-tree volume secrets included, via the resource map's `podSpecReferences`), container arguments and environment values naming `ns/name`, ServiceAccounts, Ingress TLS and ingress-nginx annotations, Gateway listeners and ReferenceGrants, StorageClass secret parameters (a templated name keeps every Secret of the namespaces whose claims use the class) and PersistentVolume secret references, and the Secrets/ConfigMaps/ServiceAccounts that cert-manager, Flux, KEDA, External Secrets, Prometheus operator, Velero, Istio, Traefik and Gateway ListenerSet objects name by field shape (`scan.ts`). A candidate needs every list that could name it read in full; ConfigMaps, Secrets and claims of a namespace, and the namespace itself, also need its sample (`cleanup_sample` → `resources::sample_namespace`: every served namespaced kind except Events, a metadata-only list of at most 5 names each, 8 requests at a time, once per page open and on "Check again") to show no object of a custom kind the page does not read — an empty namespace none at all beyond what Kubernetes creates; a failed sample offers nothing there. ### Change timeline

"What changed before it broke" (#145, `src/features/timeline/`), read-only. **Recording** opens no watch of its own: the watch layers report every update they receive (`reportWatchUpdate` in `src/api/watchObservers.ts`, called by `useWatch`, the problem sources of `features/problems/store.ts` and the shared watches of `features/resource-map/watches.ts`), and `recorder.ts` keeps a short text of each object it saw (`model.ts`: everything but `status`, `apiVersion`/`kind` and bookkeeping — `resourceVersion`, `generation`, `managedFields`, `uid`, timestamps — and without annotations controllers rewrite, such as `last-applied-configuration` or `deployment.kubernetes.io/revision`; `kubectl.kubernetes.io/restartedAt` stays). A newer version that differs is recorded as a diff by field path (list items by `name`), values clipped, at most 30 fields; an object first seen in a fresh list after a while is a "late" change, a creation or deletion is recorded only for objects without a controller. Pods, ReplicaSets, ControllerRevisions, Events, Endpoints/EndpointSlices, Leases and a CronJob's Jobs are never recorded (their owners tell the story); metadata-only watches are ignored, and so is every watch narrowed by a label selector or by a field selector other than `metadata.name=` (`followsDeletions`: an object leaving such a list stopped matching, it was not deleted); an older version delivered by a lagging second watch is dropped by `resourceVersion`. A Secret arrives without values and its text keeps key names only, so no value is ever recorded. **Who**: watches carry no `managedFields`, so after a change `timeline_managers` reads the object's field managers (metadata-only GETs, ≤ 50 per call, one call per cluster at a time, ≤ 200 waiting) and names those whose `time` moved since the last read, else the most recent non-`status` one as "probably". Bounded: per cluster a ring of 5000 changes and about 4 MB, object texts 24 MB over all clusters (beyond it, or past 64 KB for one object, an object is kept as a hash: a change is noticed without its fields), at most 20 000 objects per cluster. **Persistence** is off by default (`AppSettings.timeline.persist`, frontend-written): when on, each cluster's ring is saved a few seconds after it changes through `timeline_save` (one file per cluster under `<app data>/timeline/`, the name a hash of the cluster id, at most 8 MB, written to a temporary file and renamed, a Secret's values stripped again before writing) and loaded with `timeline_load` when the recorder first sees the cluster; turning it off removes every saved file (`timeline_remove_all`), also of clusters no longer in any kubeconfig. **Before Sextant** (`crates/sextant-core/src/timeline.rs`, `timeline_history` for ≤ 10 namespaces of the filter, `timeline_object_history` for one object): the last change of each field manager of each object (metadata-only lists, ≤ 1000 objects per list, `status` writes left out), rollout revisions (ReplicaSets by their revision annotation, ControllerRevisions with their `data` dropped at once, a workload's through `rollouts::history`) and Helm release revisions from the release Secrets' labels (metadata only) — shown as "partial". **Correlation** (`correlate.ts`): the problems and Warning events of the problem sources that began from 1 min before to 30 min after a change, on the object or what depends on it — the resource map's graph (`dependents`: what names or owns it, three hops, and what an HPA, Service or policy picks) when the namespace is watched, else pods and Jobs named after a workload. The page "Timeline" (section "Cluster") watches, for ≤ 3 namespaces of the filter, the namespace lists the map shares plus ConfigMaps and Secrets while open; the details tab "Changes" of every kind (but Events) shows one object's changes. Neither agents nor extensions get any of it. Decision: ADR-0079.

### Network connectivity

"Can pod A reach pod B?" (#148, `src/features/netpol/`), read-only and frontend-only. Every policy flavour is normalised to one model (`model.ts`: `Policy` → `Rule` → `Peer`/`PortSpec`, three-valued matches): Kubernetes NetworkPolicy (`kubernetes.ts`, the networking.k8s.io/v1 semantics: policyTypes defaulting, rules ORed, peers and ports ORed and ANDed with each other, podSelector + namespaceSelector in one peer ANDed, ipBlock with except over IPv4/IPv6 in `cidr.ts`, named ports resolved on the destination pod, endPort), Cilium (`cilium.ts`: the L3/L4 subset, deny rules, `ingress: [{}]` matching nothing) and Calico (`calico.ts` + `calicoSelector.ts`: ordered first match, Kubernetes policies as order 1000, the default tier only). `engine.ts` evaluates the source's egress and the destination's ingress separately (a Service destination per selected pod at its target port), plus the kube-dns egress check; what it cannot decide — an ipBlock holding a pod IP, an unreadable list, a feature it does not model (L7, FQDN, tiers, Pass), an object of a policy kind it does not evaluate (`UNEVALUATED_KINDS`: AdminNetworkPolicy/BaselineAdminNetworkPolicy/ClusterNetworkPolicy, Antrea, OVN EgressFirewall and external routes, GKE FQDNNetworkPolicy; for its namespace, or everywhere when cluster-wide), a failed discovery — is "unknown", never "allowed"; hostNetwork pods are not subject to policy. `hooks.ts` watches through the resource map's shared watches only the namespaces a question names (pods and policies), Services where asked, Namespaces, cluster-wide policy kinds the cluster serves and the DNS pods by label. Views: the page "Connectivity" (Network section) with the check and a per-namespace policy map, the details section "In plain words" of every policy kind and "Network policies" (isolation) of pods. Policy coverage (#239, `coverage.ts`): per pod and direction "isolated" / "not isolated" / "unknown" (never "not isolated" while a policy might apply; a Calico Pass rule of the direction makes its policy "unknown" for it; a hostNetwork pod is "unknown" while a host policy — a Cilium policy with `nodeSelector`, any Calico GlobalNetworkPolicy — exists) and a namespace's default deny, shown in the page's "Coverage" tab, the namespace table's "Ingress isolated" / "Egress isolated" columns and the pod's details, only for the first 10 namespaces of the filter. Agents and extensions get nothing new. Decision: ADR-0082.

### Traffic path diagnosis

"Why does this Service / Ingress / route get no traffic?" (#208, `src/features/diagnose/`), read-only and frontend-only: from objects only, no probe pod and no traffic. A pure engine walks the path link by link into a `Chain` of findings (`ok`/`warn`/`broken`/`unknown`, plain words as i18n phrases); a chain stops at its first broken link while sibling chains (an Ingress's paths, a route's backends) go on. Service (`service.ts`, `serviceSteps.ts`): ExternalName sanity, selector (the resource map's `selectors.ts`; near misses named), Ready pods (reasons from the problems model's `detect`), target ports by number or name with protocol, EndpointSlices against the Ready pods (`publishNotReadyAddresses`), network policies, then exposure (node ports, load balancer address and how long pending, session affinity). Ingress (`ingress.ts`, `controllers.ts`, `tls.ts`): IngressClass by `ingressClassName`, the legacy annotation or the default class; the controller's pods only for a few known controllers (`KNOWN_CONTROLLERS`, label selectors), otherwise "unknown" unless it published an address; TLS Secrets through `tls_certificate_info` (values stay in the core) with expiry and host coverage; pathType semantics; backend Service and port, then the Service checks. HTTPRoute/GRPCRoute (`route.ts`): the Gateway API model's parent statuses, listeners and `backendIssue`, then the Service checks. Policies (`policies.ts`) use the connectivity engine's `evaluateSide` for the backend pods' ingress, from the controller's pods when known, else from an unknown client outside the namespace (a rule that selects sources by labels makes it "depends on the source"). Data (`hooks.ts`): per-(kind, namespace) shared watches of the involved namespaces only (≤ 4), `useNetpolData` for pods and policies, IngressClasses and a known controller's pods by label selector cluster-wide; nothing before discovery. Entry points: the `diagnose` action (Services, Ingresses, HTTP/GRPC routes; a dialog) and the "Diagnosis" details tab. Strings `src/locales/<lang>/diagnose.json`.

### Autoscaling insights

"Why it did or did not scale" (#146, `src/features/autoscaling/`), read-only and frontend only. Data (`hooks.ts`): nodes and the requests of bound pods are taps on the problems store's cluster-wide Node and Pod watches (`acquireRows`, compact rows, held 60 s after the last view so the next Pending pod does not relist); namespace lists (HPAs, ScaledObjects, pods, claims) and the cluster-wide Karpenter lists are the resource map's shared watches; an object's events and single objects by name are plain watches; the status ConfigMap is read only after Cluster Autoscaler wrote an event about the pod. No Rust command; nothing for agents or extensions. Decision: ADR-0080.

### Schema-aware YAML editor

The editor's "edit" and "create" (Apply YAML) tabs use the cluster's OpenAPI v3 schema (#151); Helm values editors and extensions' editors do not (`YamlEditor` gets `schemaCluster` only from those two tabs). ### Storage insights

Fill levels, VolumeSnapshots and Velero (#152, `src/features/storage/`). `crates/sextant-core/src/metrics/volumes.rs` reads the kubelets' stats summaries through the API server (`/api/v1/nodes/<node>/proxy/stats/summary`): node names from a metadata list (≤ 500 nodes), 8 nodes at a time, 10 s and 16 MiB per answer, 40 s per round (nodes not reached count as failed; the readings of the nodes that answered stay, and the round counts as forbidden only when every node refused), and of each summary only the claims' volume fields are deserialized (namespace, name, capacity, used, available, inodes); one entry per claim (the fullest reading); "used" is capacity − available where both are known (reserved blocks count, as in `KubePersistentVolumeFillingUp`), inodes likewise total − free, ≤ 10 000 claims. ### Resource details sections

Resource cards use shared heading disclosures in their Overview ([ADR-0133](adr/0133-resource-details-use-shared-disclosures-and-per-kind-preferences.md), `src/layout/details/disclosure.tsx`, `disclosureState.ts`). Expand all explicitly includes YAML.

Explicit semantic block paths are scoped by API group/kind. Settings → Appearance chooses global memory (default), per-cluster memory or none; global and cluster banks stay independent. Session-only choices survive tab changes in the same card, then reset on reopening or object change. Controls and source acquisition wait for the initial settings response. YAML starts closed and its masked serialization/editor are lazy. Closing removes the body and releases its owned sources; other users of shared watches/polls, visible fields and header actions retain the data they need and the existing linger policy. Conditional sections can first check applicability with `src/features/details/disclosureProbe.ts`; a closed probe settles on a completed present, absent or unknown result. Failed, forbidden or capped lists never prove absence. Persistence reuses the settings queue, reports session-only failures and bounds maps in Rust; there is no new command, SDK method or dependency.

### Resource details width

The right-hand resource card remains an overlay. `src/layout/details/DetailsPane.tsx` owns its size and reuses `Splitter` on its left edge ([ADR-0135](adr/0135-resource-details-widths-use-a-resizable-frame-and-independent-kind-and-shared-banks.md)). Drag left to widen, right to narrow; Left/Right keys use 16px steps. The default is 725 CSS pixels, the minimum 480 and the maximum the workspace width. A window up to 768px, or a workspace no wider than 480px, uses full width without the handle. One workspace `ResizeObserver` limits the displayed size without changing the remembered preference.

Settings → Appearance → Resource details chooses widths per API group/kind (default) or one shared width, with an independent session-only checkbox. `appearance.detailsWidthScope` and `detailsWidthSessionOnly` choose the policy; `window.detailsWidths` stores `group/Kind` entries and `*` for the shared bank. Namespaces, API versions and clusters share a kind's width. Both banks remain independent. `useLayoutPersistence` restores them once and merges changes through the settings queue after 300ms. Session-only mode cancels pending width saves; a new launch starts at 725px without discarding previously saved banks. Turning persistence back on merges session edits with those banks. Failed writes leave the in-memory size intact and a later edit retries. The sizing frame retains its child identity, and the shell is memoized against parent settings updates. Namespace restoration reads only settings-load readiness through `useSettingsSelector`, while live namespace choices still come from the cluster store. Resizing and its completed save therefore do not remount the details or rerender the main table.

### Accessibility

Keyboard, screen readers, contrast and motion (#158, frontend only). The shared `Dialog` (and the agent/extension confirmation, the narrow-layout drawer) traps the focus with `useFocusTrap` (`src/components/useFocusTrap.ts`). Open modals form a stack and only the top one takes Tab and Escape; the agent/extension confirmation is `alwaysOnTop` while shown (nothing opened later takes the focus, and the palette does not open over it). A modal on top takes the focus: `data-autofocus`; in a confirmation or a dialog with a danger button, "Cancel"; else the first text field (never a checkbox); else the first footer button. On close the focus goes to the modal now on top, or back to the opener unless what the dialog opened took it; an opener removed with a closed popup (a menu item) stands for that popup's opener (the row's "⋮"). Popups (`usePopup`) return the focus to their opener. "Allow" in the agent/extension confirmation ignores keyboard activation for 1 s and clicks for 300 ms after a request appears (Deny works at once), so a request that pops up while typing cannot be approved by Tab, Enter. The details panel focuses its heading when it opens and gives the focus back to the trigger on Escape or Close. Resource tables keep one row in the tab order (roving tabindex, by object uid): ↑/↓, Home/End, Page Up/Down move between rows (scrolling the virtual list), Enter opens the details, Space selects, the context-menu key or Shift+F10 opens the actions, Ctrl+C / ⌘C copies `namespace/name` (ADR-0105); a row's checkbox and "⋮" are tab stops only in that row. The dock's tab list holds only the tabs; it is a real box (WebKit drops a `display: contents` tablist from the accessibility tree) that spans a grid of tab/close column pairs and lays its tabs out by subgrid, the close buttons taking the columns between (engines without subgrid get `@supports not (grid-template-columns: subgrid)` in `layout.css`: tabs of one width, `--dock-tab-width`, in a flex row, each close button placed over its tab's right end by `--dock-tab-index`); only the active tab's close button is a tab stop. ←/→, Home/End, Delete closes, Escape returns the focus to what was focused before the tab opened. In a terminal, Ctrl+Shift+E moves the focus to its dock tab — matched by the letter typed (Dvorak), by the physical key only when the layout types no Latin letter there (Cyrillic); xterm keeps every other key, and the key is announced through the input's `aria-describedby`; while the focus is in a running terminal a small hint ("Ctrl+Shift+E — leave the terminal", `terminal:leaveHint`) is laid over the screen's top-right corner (`.terminal__leave-hint`, `aria-hidden`, so nothing moves). Known conflict: an IBus setup that binds Ctrl+Shift+E to emoji input (a default of several IBus versions on GNOME) takes the key before the window; such users change or turn off that IBus shortcut. Log views are `role="log"` with `aria-live="off"`; `LogAnnouncer` says "N new lines" at most every 15 s and only while the focus is in the log tab (the region is emptied before each message, so a repeat is read again); a table announces its row count only after the search or filter changed. Visible focus: a global `:focus-visible` ring in `--color-focus`. Theme tokens (`src/styles/global.css`) meet WCAG AA in both themes — text and status colours 4.5:1, focus rings, chart lines (`--color-chart-*`) and the edge of text fields, selects and text areas (`--color-control-border`, also a `:where(…)` base rule in `global.css` for fields whose own rule sets no border; dividers keep the lighter `--color-border`; the test also finds fields by the classes components put on `<input>`/`<select>`/`<textarea>`) 3:1, accent text that may sit on a hovered or selected background (the active sidebar entry, links in table rows) `--color-accent-strong` 4.5:1, text on fills via `--color-accent-text` / `--color-on-status` — computed from the token values by `src/styles/contrast.test.ts`; status is never colour only (the cluster connection mark is a dot, a ring or a diamond). Settings → Appearance holds three accessibility choices in `AppSettings.appearance` (frontend-written, read leniently by `settings/appearance.rs`; applied by `useApplyAccessibility`, `src/app/accessibility.ts`): "Reduce motion" System / On / Off sets `<html data-motion="reduce"|"full">` (none for System), and the reduced-motion rules of `global.css` and `loading.css` apply under `prefers-reduced-motion` unless `full`, and always under `reduce` (transitions, animations, smooth scrolling; the terminal cursor stops blinking, `reducedMotion()`); "Interface text size" 90/100/110/125/150 % is the font size of `<html>` in percent — every `font-size`/`line-height` in `src/**/*.css` is in rem (16px root at 100 %, so 100 % keeps the old pixel sizes; a test fails any px value) and so are `--control-height`, `--control-height-compact`, `--control-font-size`, `--table-row-height` (`calc(2rem + 1px)`) and `--log-line-height`; the virtualised resource table and log lists measure those tokens (`useCssLength`) instead of a fixed row height and re-place their rows when the size changes, the terminal scales its 13px font (`scaledPx`) and refits, the YAML editor measures again, and a `resize` event lets charts lay out; "Screen reader support in the terminal" (off by default, it slows xterm down) is xterm's `screenReaderMode`, followed live by open terminals. The cluster avatar's initials and the rail's connection seconds are CSS generated content from `data-text`, so the rail button's visible text is only the cluster name it is labelled with (WCAG 2.5.3). Ctrl+= / Ctrl+- / Ctrl+0 zoom the window (`zoomHotkeysEnabled`, permission `core:webview:allow-set-webview-zoom`); Tauri's hotkey script counts from 100 % on each page load, so the page sets the web view back to 100 % when it loads (`resetZoomOnLoad`, `src/api/zoom.ts`). Extensions get `--color-focus` and `--color-on-status` among `THEME_TOKENS`; the checkbox mark follows `--color-accent-text` per theme. axe-core (a dev dependency) runs in Vitest over the main screens (`src/test/a11y.test.tsx`) and every registered page (`src/test/a11y-pages.test.tsx`); jsdom cannot judge colours or layout, so contrast is the token test above. Decision: ADR-0092.

Sidebar tree appearance (#282, a contribution in #283, frontend only). Settings -> Appearance -> Sidebar holds two independent choices: "Indent child items" (`appearance.sidebarIndent`) moves a nested group's leaf entries to the icon column of its child groups, and "Show tree guides" (`appearance.sidebarGuides`) draws a guide under each parent's chevron with an elbow to each child. Indentation is on by default since 0.25 (settings version 2 turns a version-1 `false` on once: 0.24.1 wrote its old default into every file), guides are off. Both are frontend-written and read leniently by `settings/appearance.rs` (anything but a boolean reads as the default); `Sidebar.tsx` puts them on the sidebar as `data-sidebar-indent` / `data-sidebar-guides`, and `sidebar.css` does the rest, so every cluster's sidebar follows a change at once.

### Column widths

Every table's columns can be resized (frontend only, `src/components/Table/`). The resource table puts its handles in a grid of their own over the header, laid out by the same `--rt-columns` template as the rows; plain tables are `ResizableTable` (a drop-in for `<table>` with a `tableId`), whose handles sit in a layer above the header placed from the table's own offsets, so a wrapper that scrolls sideways does not shift them; they are placed again only when a header cell changes size or the header changes (`ResizeObserver`, `MutationObserver`), not per render. Handles are never inside a header cell (they would become part of its accessible name), so header texts stay what e2e and screen readers read. A column of a plain table is keyed by its `data-col` (a key that is not translated; required on tables whose columns come and go) or else its position; a header cell without text gets no handle. While a column is dragged the width changes once per animation frame through the CSS variable or the `<col>`, never through a React render of the rows; the width is committed when the drag ends. After a resize a plain table switches to `table-layout: fixed` (the other columns keep the widths they had), cells are cut with an ellipsis, and `showCutText` sets the whole text as the tooltip of a cut cell on hover (and removes a tooltip it wrote once the text fits; a cell's own tooltip is left alone). Keyboard: the handles of a table are one tab stop (roving tabindex); each is a focusable `separator` ("Resize column <name>", `aria-valuenow` in px, a hidden description of the keys); ← → change the width by 16 px (Shift: 64), Home / End set the narrowest (48) / widest (1600), Enter and a double click restore the default width, Ctrl+← → (⌘ on macOS) move to the previous / next column's handle. Widths are saved in the frontend-written `AppSettings.columnWidths` (table id → `{columns: {columnId: px}, used}`: `kind:<group>/<Kind>` for resource tables, a stable name such as `helm.releases` or `details:service.ports` for the others, never derived from translated text), written 500 ms after the last change and merged per column with what is stored, so two mounted tables of the same id keep each other's widths. At most 300 tables are kept: the frontend drops the least recently changed before it writes and the core keeps the most recent when it reads (`settings/columns.rs`, lenient, 64 columns per table, widths clamped). "Reset column widths" in a resource table's Columns menu clears its widths.

### Resource table filters

The main kind tables and the primary Events list opt into `ResourceTable`'s filters (`src/features/table-filters/`); Helm and tables inside an object's details do not. The "Filters" control sits between namespaces and search. Column editors offer included/excluded values or a typed condition, header buttons open the same editor, and the condition bar can remove a filter. Right-clicking a header's filter button clears every rule for that column, including advanced rules, with Undo. Quick filters are combined with AND; an advanced expression adds nested AND/OR groups through the shared `Dialog`. Namespace selection, text search and sorting keep their own state. Filters only narrow the already loaded objects, before sorting and virtualization; a capped list says that only the loaded part is filtered. Selection and its actions use the retained rows.

`ColumnDef.filter` supplies raw values, types, units and an optional shared-data observer where the sort value has a different meaning (owner kind, age, metrics); otherwise the existing `value` getter is used. Cell HTML and translated text are never parsed. `model.ts` compiles predicates when the filter or column definitions change, short-circuits them and reads a referenced column at most once per row, with scratch space proportional to the referenced columns rather than the rows. `facets.ts` builds bounded candidates only for the open editor, keeps saved selections and puts empty first; no index of every column or copy of the watched objects is retained. Watch revisions, the existing age tick and shared metrics observers invalidate the relevant result, including while a metric column is hidden or no row is visible. Per-cluster, per-kind persistence and compatibility are described in [ADR-0127](adr/0127-resource-table-filters-use-typed-local-predicates-and-cluster-kind-settings.md).

## Module boundaries

- **`sextant-core`** owns everything about clusters: kubeconfig, connection and discovery, watch, actions on resources, logs, exec, port-forward, metrics (metrics-server and Prometheus or VictoriaMetrics, the right-sizing usage history), TLS certificate parsing (`tls`), access reviews (`rbac`), server-side dry runs (`resources::dry_run`), the upgrade-readiness scan (`upgrade`), Helm, settings on disk. It hides `kube-rs`, reflectors, Helm secret parsing, Prometheus/VictoriaMetrics auto-detection; it also owns the extension manifest, permissions and package format (`extensions/`). It does not depend on `tauri` or `portable-pty`; everything that launches OS processes (the `helm` binary) sits behind the `desktop` feature (in default). `scripts/check-core-deps.mjs` verifies this.
- **`sextant`** (`src-tauri/`) owns `AppState`, commands, events, the local PTY (`pty.rs`), the window geometry and the tray-aware close/reveal (`window.rs`, `tray.rs`), the shared GitHub download rules (`download.rs`), the Flux / Argo CD install flow (`gitops_install/`), the MCP server (`mcp/`), what MCP and extensions share (`access_guard/`), the extension host (`extensions/`) and the `sextant mcp` bridge (`mcp_proxy.rs`); `rmcp` and `axum` are its dependencies only. A command contains no cluster logic — it calls the core. A new kind of subscription or session is registered in `AppState`, otherwise `close_cluster` will not close it.
- **`src/api/`** is the only place where `invoke` / `listen` are called, stream channels are created and `@tauri-apps/api` is imported (eslint forbids it everywhere else). An exception under ADR-0011: the cluster hooks live in `src/features/clusters`.
- **`src/features/<name>/`** are vertical features. A directory with `index.ts` is picked up automatically (`import.meta.glob` in `src/app/features.ts`); a feature wires itself in through registrations, without editing other people's files.
- **`src/layout/`** is the shell (`AppShell`: cluster rail, sidebar, `MainView`, details panel, dock). It knows nothing about specific resource kinds.
- **`src/resources/`** is the kind registry (`ResourceDef`: columns, details, actions); for CRDs the columns come from the CRD's own `printerColumns`, read lazily (`crdColumns.ts`).
- **`src/components/`** are shared components with no knowledge of Kubernetes kinds: `Button` (`variant`, `size`, `icon`, `iconOnly` + a required `label`), `Checkbox` and `Radio` (the app has no native checkboxes or radio buttons), `Tabs` (a `tablist` with the ←/→/Home/End keys), `icons.tsx` (`Icon`, `IconName`, `renderIcon`), `LoadingIndicator` (with a hint if the wait is long), `Dialog`, `ConfirmDialog`, `ErrorState`, `EmptyState`, `Badge`, `Age`, `usePopup`; the resource table is in `src/components/Table/` (`ResourceTable`, `LoadingTable`). Exports are in `src/components/index.ts`; features import from there, not from one another.
- **`src/features/gateway-api/`** is the read-only Gateway API section (see "Gateway API"); it works through watches and the registries only.
- **`src/features/mesh/`** holds the read-only service mesh sections (see "Service mesh: Istio and Linkerd"); it works through shared watches and the registries only.
- **`src/features/flux/`, `src/features/argocd/`, `src/features/argocd-diff/`** are GitOps (see "GitOps: Flux and Argo CD"); they work only through the api and registries, and the core needs only `resource_patch`, `cluster_kinds_refresh` and the `argocd` module for them.
- **`src/features/mcp/`, `src/features/agent-access/`** are the agent features (see "MCP server for AI agents", "Agent access model"); the first embeds into Settings and the cluster rail (`railFooter`), the second into cluster settings (`registerClusterSettingsSection`).
- **`src/extensions/`** is the extension host, part of the shell (not a feature folder); **`src/features/extensions/`** is its Settings UI. Extension contributions reach the app only through the registries (see "Extension points"). **`sdk/`** is a separate npm package used by extension authors; the app does not import it.
- **`src/features/gitops-install/`, `src/features/about/`** are window-driven features mounted once in `AppShell` (the install dialog and the About dialog); both are opened by store calls or events, not by routes.
- **`src/features/rightsizing/`, `src/features/cert-manager/`, `src/features/resource-map/`, `src/features/rbac/`** are read-only views (see their sections above) that work through watches, the registries and a few read commands (`metrics_usage_history`, `tls_*`, `rbac_*`); none of them is offered to agents or extensions.
- **`src/features/upgrade/`** is a read-only view as well (see "Upgrade readiness"): one read command (`upgrade_scan`) and the built-in deprecation table; not offered to agents or extensions.
- **`src/features/security/`** and **`src/features/fleet/`** are read-only and frontend only (see "Security posture", "Overview of several clusters"): watches, the registries (`registerPage`, `registerDetailsSection`, the `home` and `clusterRail` slots) and the problems store; no Rust command.
- **`src/features/autoscaling/`** is read-only and frontend only (see "Autoscaling insights"): details sections, the `keda`/`karpenter` sidebar sections, taps on the problems store and the resource map's shared watches; no Rust command.
- **`src/features/timeline/`** is read-only (see "Change timeline"): it observes the watch layers through `src/api/watchObservers.ts` and opens only its page's shared watches; its Rust side is `sextant_core::timeline` behind the `timeline_*` commands (reads and the opt-in file), not offered to agents or extensions.
- **`src/features/netpol/`** is read-only and frontend only (see "Network connectivity"): a pure engine over the resource map's shared watches and the registries; no Rust command.
- **`src/features/compare/`** is read-only (see "Comparing objects"): four window commands (`compare_*`), the registries and `secret_value` on request; not offered to agents or extensions.
- **`src/features/hygiene/`** is the "Cleanup" page (see "Cleanup"): watches and the registries; its only change is the ordinary `resource_delete`, after a confirmation listing every object.
- **`src/features/safe-apply/`** holds the preview components and the per-cluster policy (see "Safe apply"); the editor and the Helm dialogs embed them, and the change is still sent by its own caller.
- **`src/features/updates/`** are the application updates and its version (see "Application updates"); it does not hook into the registries, and its components are embedded by `src/features/settings`.

## Buttons, icons, tabs

- All icons come from the `lucide-react` set, imported only in `src/components/icons.tsx`: `IconName` holds the names from the set, `renderIcon(name)` draws an SVG (`aria-hidden`, no text and no `<title>`). Features import `Icon`/`renderIcon` from `src/components`, not `lucide-react` (ADR-0033). `icons.test.tsx` requires every name to be used.
- Sizes are `:root` tokens in `src/styles/global.css`: `--control-height` 32 px, `--control-height-compact` 28 px (the "⋮" button and table row buttons, closing a dock tab), `--control-font-size`, `--icon-size`; `.btn`, `.btn--compact`, `.btn--icon`, `.icon-btn` take their sizes from there (ADR-0034).
- A button with an icon instead of a label (`iconOnly`) keeps the former label in `aria-label` and `title`; vitest and e2e find buttons by these names.
- Icons in the registries: `ActionDef.icon: IconName` (`src/features/actions/registry.ts`, rendered in `ActionBar` and in the table's `ActionMenu`), `DockActionDef.icon?: IconName`, `SidebarEntry.icon?: IconName` and `SECTION_ICONS` (the icon of a section and of single pages, keyed by `SidebarSection | "settings"`) with the fallback `DEFAULT_ENTRY_ICON` — `src/resources/registry.ts`, `PageDef.icon?: IconName` — `src/layout/pages.ts`. A feature sets the icon with the `icon` field in its registration; the sidebar draws it to the left of the label.
- `Tabs` — the caller holds the selected-tab state; the pod's container tabs (`ContainerList`, `src/features/details/kinds/pods.tsx`) keep the selection by the object key `clusterId|namespace|name`, so a pod update does not reset it.
- Pod requests and limits are computed by the frontend: `podResourceAmounts` (`src/features/metrics/requests.ts`, CPU in millicores, memory in bytes) — they are visible even without metrics-server (ADR-0037).

## Cluster icon and rail

`ClusterSettings.icon` (Rust `ClusterIcon`: `Text { text }` or `Image { dataUrl }`) and `WindowLayout.railExpanded` live in `settings.json` and are written by the frontend (`settings_update`). `readIconImage` (`src/features/clusters/iconImage.ts`, input up to 5 MB) fits the image into a 96×96 PNG; `iconOf` (`clusterSettings.ts`) returns the image only if it is `data:image/png;base64,`, otherwise text (`icon.text` or the name's initials); the shared renderer is `ClusterAvatar`, used for the rail and the preview; its letters are white or black, whichever contrasts more with the label color (`initialsColorOn`; every offered color reaches 4.5:1). `ClusterRail` (`src/layout/ClusterRail.tsx`) reads `railExpanded` from the store (`setRailExpanded`) and shows names when expanded; what expands is the narrow cluster rail, not the section menu (ADR-0035, ADR-0036).

## Saved views, pins and workspaces

`src/features/views/` (#149, ADR-0083). The table state a view captures lives in the store per cluster (`ClusterView.search`, `.namespaces` and `.table`: "Only problems", label selector, sort, hidden columns, tied to the view id and reset when another kind opens); `MainView` passes it to `ResourceTable` (controlled `sort`, `hiddenColumns` with the "Columns" menu, `labelSelector` asked from the watch). Views, pins, workspaces and `activeWorkspace` are frontend-written fields of `settings.json`; the core reads each list entry by entry (`settings/views.rs`: invalid or repeated entries are left out, lists are capped). The feature hooks in through `registerTableTool` (`src/layout/main/tableTools.ts`), the `sidebarTop` and `clusterRail` slots, `registerNavigationProvider` (palette) and `extendActionsForAll` (pin/unpin on every kind). A workspace only filters the rail (the active cluster stays shown); it never connects or disconnects. Export writes JSON through the save dialog and `file_save` (clusters by source path and context only; shareable cluster settings; agent access only when ticked); import goes through `views_import_open`, which shows the open dialog in the backend and reads only the file picked there (a regular file, at most 1 MiB; the window never names a path), parses strictly (unknown fields are listed), previews per section and applies only on confirmation, replacing differing entries only when allowed. A cluster of the file matches exactly (same id, or same source path and context) or by context name only; agent access rules are applied only on an exact match and only when "Apply the agent access rules from the file" is ticked. The file never carries kubeconfig contents, credentials, tokens, extensions or their grants. Version 2 of the file adds the required `snippets` section (terminal snippets, #154); a version 1 file is still read (without snippets), each version strictly. A renamed context takes its views, pins and workspace places along and a deleted one loses them (`move_cluster_settings` / `forget_cluster_settings`, see Kubeconfig management).

Resource-table filters are separate from that transient table state: `ClusterSettings.tableFilters` is keyed by the existing resource view id and survives navigation. `SavedView.tableFilters` captures the target table's filters; opening an older view without that field clears them. Export version 4 carries filters in views and shareable cluster settings; import still reads versions 1–3 without them. Writes use the existing settings queue and preserve other settings; a failed write leaves an explicit session-only state in the window. See [ADR-0127](adr/0127-resource-table-filters-use-typed-local-predicates-and-cluster-kind-settings.md).

## Conventions

- Names in code are English. Everything that goes to the frontend is `#[serde(rename_all = "camelCase")]` and `ts-rs`; TS types are generated into `src/api/generated/` (`npm run gen:types`), are not edited by hand, and the generated files are committed. Command and event names are not part of the generation: they are written by hand in `src/api/commands.ts`, `src/api/events.ts` and `src-tauri/src/lib.rs`, and a typo is caught only by a test or at runtime.
- Every UI string is an i18next key in `src/locales/<lang>/<namespace>.json`, one namespace per feature; the list of languages is built from the directories found. eslint forbids literals in JSX. `AppSettings.language` is a directory name (an explicit choice) or `system` (the default of a new install; an `en` from a file written before `settingsVersion` 1 was the old default and is migrated to `system`), which follows the OS language (`navigator.languages`, mapped by `matchLanguage` in `src/i18n/index.ts`) or English; a missing key, an empty text or a missing namespace file reads in English. Counts use plural keys (`_one`/`_other`, CLDR forms per language); dates, numbers and list separators go through `src/i18n/format.ts` in the UI language (`formatList` for lists of names, `formatParts`/`dotSeparator` for parts of one line, `common:list.dot`). Translators' rules and the glossary: `src/locales/TRANSLATING.md`; `src/locales/locales.test.ts` checks every language against English.
- One error for the whole core: `CoreError { code: ErrorCode, message }`. kube errors always go through `error::kube_error` (it strips exec-plugin secrets). In the frontend it is `ApiError { code, message }`, and the `ErrorCode` is translated by the key from `errorKey`.
- Secrets from kubeconfig are not logged and do not go to the frontend. Kubernetes Secret values go out only on explicit request (`secret_value`, `resource_get_full`); any new path by which a Secret object reaches the frontend must go through `resources::get::to_json`.
- The terminal and `helm` get a temporary single-context kubeconfig with mode 0600 (`write_temp_kubeconfig`, ADR-0010). The terminal's file belongs to the session (`TermSession.guard`) and is removed synchronously when it stops, its file is `sextant-kubeconfig-<pid>-*`, and leftovers are removed at startup only for dead PIDs (old names without a PID after 24 h; ADR-0019); the user's shell gets `KUBECONFIG` back after its rc (ADR-0018). `HELM_KUBE*`, `HELM_NAMESPACE`, `HELM_DRIVER`, `KUBECONFIG` are scrubbed from the environment of a `helm` call; the only launch point is `HelmCli::command()`.
- Mutating core calls are signed with the field manager `sextant`. A namespaced reference without a namespace yields `invalid` (`ObjectRef::required_namespace`). A YAML replace without `resourceVersion` is `invalid`.
- The streams rule: the frontend creates the id and the channel before `*_start(…, streamId, onEvent)`, so the backend holds back output with neither pauses nor a buffer: watch delivers the first snapshot immediately and then no more than once per 250 ms (`resources::watch::BATCH_INTERVAL`), logs in 100 ms batches (`logs::BATCH_INTERVAL`), the terminal immediately. A stream is opened only through `openStream`; the id is checked by `check_stream_id` (`[A-Za-z0-9_-]`, ≤128, an id already in use is `invalid`), and the subscription is registered in `AppState` before the core starts working. Decisions: ADR-0013, ADR-0078 (channels, not events).
- Settings: `settings_update` changes only the frontend's fields; the fields written by the backend (`kubeconfigSources`, window geometry, `extensions`) are kept as the backend wrote them. A new backend field must be added to the list of preserved ones in `update_settings`; `clusters[id].agentAccess`, `clusters[id].previewChanges`, `AppSettings.mcp`, `AppSettings.fleet`, `AppSettings.notifications`, `AppSettings.views`/`pins`/`workspaces`/`activeWorkspace`, `AppSettings.kubeconfig` (`writableSources`, `credentialExpiryDays`), `node_shell_image` and `closeToTray` are frontend fields; a backend command that changes frontend fields itself (`kubeconfig_edit_apply`) is run through `withBackendSettingsChange`, which re-reads the settings after it. An unreadable `settings.json` is not overwritten (`settings_status`, ADR-0017).
- The application version is one across five manifests (`Cargo.toml`, `Cargo.lock`, `tauri.conf.json`, `package.json`, `package-lock.json`); `scripts/check-version.mjs` checks it (`npm run check:version`, in `npm run check` and in `release.yml`).
- Forwarded ports listen only on 127.0.0.1, and so does the MCP server. Secrets that guard agent access (the MCP token) are files with mode 0600 and are never printed.
- Docs, ADR, the glossary and `AGENTS.md` are written in English (ADR-0046).
- The word "Lens" is not used in the product; the product is Sextant (`dev.sextant.app`).

## Test seams

1. Core without a cluster: unit tests next to the code; those that need to see HTTP go to the fake API server `crates/sextant-core/src/fake_api.rs` (visible only under `cfg(test)`; the test sets the replies, every request is recorded).
2. Core against kind: `crates/sextant-core/tests/<feature>.rs` + `crates/sextant-core/tests/common/mod.rs`; the GitOps tests (`gitops*.rs`; the install is covered by unit tests on `FakeApi` in `gitops_install.rs` and `src-tauri/src/gitops_install/tests.rs`) additionally need `SEXTANT_TEST_GITOPS=1` and a cluster brought up with `up --gitops`, and are skipped without them; without `SEXTANT_TEST_KUBECONFIG` a test returns early and counts as passed. Heavy measurements (a big cluster) use the fixture `scripts/fixtures/load/load.sh`. Scale measurements (#157) are ignored tests run by hand: `cargo test --release -p sextant-core --lib scale_watch -- --ignored --nocapture` (a `FakeApi` paging 10k–50k realistic pods), `--test watch_scale -- --ignored --nocapture` against kind, and `SEXTANT_SCALE=1 npx vitest run scale` in the window (`src/test/scale.ts`; `SEXTANT_SCALE_OUT=<file>` collects the lines).
3. Commands: `src-tauri/tests/commands.rs` calls every command on the Tauri mock runtime, isolated from `KUBECONFIG` and `~/.kube/config` (`set_env`); a command that goes to the network or launches `helm` is replaced there.
4. Frontend: Vitest + Testing Library without Tauri, the backend is replaced by `mockBackend` from `src/api` (including updates and the application version).
5. SDK: `sdk/test/` (Vitest, `npm run sdk:check`) checks the manifest validator against `sdk/test/fixtures/manifest-cases.json`, the protocol copy against `src/extensions/protocol.ts`, `sdk/src/generated/` against `src/api/generated/`, building and packing. Extension calls in Rust: `src-tauri/src/extensions/api_tests.rs`, the protocol handler tests in `protocol.rs`.
6. The whole window: `e2e/` (WebdriverIO + `tauri-driver`) against kind, with its own XDG directories in a temporary folder.
