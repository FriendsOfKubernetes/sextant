# Sextant — a Kubernetes desktop client (Rust/Tauri 2 + React/TS, a Lens analogue) for developers and SREs, with a built-in MCP server for AI agents

## Commands

First of all: `export PATH="$HOME/.cargo/bin:$HOME/.local/bin:$PATH"`. Run everything below from the repository root.

- Install: `npm ci`
- Frontend bundle (the `sextant` crate embeds `dist/`): `npm run build`
- Everything at once (CI does the same): `npm run check` — file-name case collisions, `check:version`, `check:packaging` (package-manager manifests rendered from a fixture release), fmt, clippy `-D warnings`, `scripts/check-core-deps.mjs`, Rust tests, TS type check against Rust, tsc (+ `e2e/`), eslint, vitest, `npm run sdk:check`. Green: Rust 1449 tests, vitest 3282, SDK 227. `vite build` warns INEFFECTIVE_DYNAMIC_IMPORT for `src/features/argocd/server.ts`: known, harmless.
- Run: `npm run tauri dev` (Vite on 1420, `strictPort`)
- Installers: `npm run tauri build` — needs the updater signing key (see Pitfalls); without the key: `npm run tauri build -- --config '{"bundle":{"createUpdaterArtifacts":false}}'`. Binary without a bundle: `npm run tauri -- build --debug --no-bundle` → `target/debug/sextant`
- Trap: `npm run check` rebuilds `target/debug/sextant` WITHOUT the embedded frontend. e2e copes by itself: its own build stamps the binary (`target/debug/sextant.e2e-stamp`, size + mtime, `e2e/build.ts`), and with `SEXTANT_E2E_SKIP_BUILD=1` a missing or mismatched stamp makes it rebuild (it logs why). Before running the binary by hand, run `npm run build && npm run tauri -- build --debug --no-bundle` again.
- On a loaded machine vitest can fail on its 5-second timeouts (`src/features/logs/logs.test.tsx` first): `npx vitest run --maxWorkers=4`.
- Version in all manifests: `npm run check:version`; match with the release tag: `node scripts/check-version.mjs --tag vX.Y.Z`
- One test: `cargo test -p sextant-core <name>` · `cargo test -p sextant <name>` · `npx vitest run <file>`
- Regenerate TS types from Rust: `npm run gen:types`; then copy the ones the SDK shares into `sdk/src/generated/`: `npm run sdk:sync-types` (`sdk/test/generated.test.ts` fails on drift)
- Extension SDK (`sdk/`): `npm run sdk:check` (tsc + vitest + `sdk/scripts/check.mjs`); build a project: `npm run sdk:build -- sdk/template` (also `sdk/examples/hello-page`, `sdk/examples/crd-view`) → `<project>/dist`, JS/CSS inlined unless `--no-inline`; pack: `npm run sdk:pack -- <project>/dist` → `<id>-<version>.sextant-ext` (`--dry-run` only checks)
- Test cluster (kind `sextant-test`; needs `kind`, `kubectl`, docker; a second kind cluster beside another fails at `fs.inotify.max_user_instances=128`: `sudo sysctl -w fs.inotify.max_user_instances=512 fs.inotify.max_user_watches=524288`): `scripts/test-cluster.sh up` (`up --prometheus` also installs Prometheus in `monitoring`; `up --gitops` also installs Flux v2.9.6 (`flux-system`) and Argo CD v3.5.5 (`argocd`) from the official manifests and the fixtures in `scripts/fixtures/gitops/`; `up --gateway` also installs the Gateway API v1.6.3 standard CRDs and the fixtures in `scripts/fixtures/gateway-api/` (namespaces `gw-infra`, `gw-shop`, `gw-payments`; no controller, so the status is patched in from `status.yaml`); `up --victoria-metrics` also installs VictoriaMetrics v1.154.0 in `victoria-metrics` from `scripts/fixtures/victoria-metrics/` (vmagent scraping what the Prometheus fixture scrapes into a single-node `vm-victoria-metrics-single-server:8428` and a cluster behind `vmselect-vm:8481`, the empty `vm-replay:8428`, the ServiceAccount `vm-reader`); with `--prometheus` `crates/sextant-core/tests/victoria_metrics.rs` compares the two; the flags combine), `scripts/test-cluster.sh kubeconfig` (the path, `~/.cache/sextant-test/kubeconfig` by default), `scripts/test-cluster.sh down`
- Load fixture (150 CRDs and 500 pods in the `sextant-load` namespace; needed by the test `the_first_nodes_come_within_2_seconds_on_a_big_cluster`, which is skipped without it): `scripts/fixtures/load/load.sh apply`, after measuring `scripts/fixtures/load/load.sh delete`
- Core integration tests against a cluster: `SEXTANT_TEST_KUBECONFIG=$(scripts/test-cluster.sh kubeconfig) cargo test -p sextant-core --tests -- --test-threads=1`
- GitOps integration tests (`crates/sextant-core/tests/gitops*.rs`) need `SEXTANT_TEST_GITOPS=1` and a cluster brought up with `--gitops`: `SEXTANT_TEST_GITOPS=1 SEXTANT_TEST_KUBECONFIG=$(scripts/test-cluster.sh kubeconfig) cargo test -p sextant-core --test gitops --test gitops_flux --test gitops_argocd --test gitops_argocd_diff -- --test-threads=1`; without `SEXTANT_TEST_GITOPS=1` they are skipped (and count as passed)
- Real Flux + Argo CD install (opt-in, a throwaway kind cluster; never `~/.kube/config`): `kind create cluster --name sextant-install-test --kubeconfig /tmp/sextant-install-kc && SEXTANT_TEST_INSTALL_KUBECONFIG=/tmp/sextant-install-kc cargo test -p sextant-core --test gitops_install real_install -- --nocapture; kind delete cluster --name sextant-install-test --kubeconfig /tmp/sextant-install-kc` (~1.5 min; skipped when the variable is unset or the cluster already has either tool)
- E2E (WebdriverIO + tauri-driver; needs `tauri-driver` and `webkit2gtk-driver`, and a cluster with `--prometheus`): `SEXTANT_E2E_SKIP_BUILD=1 npm run e2e` → 13 passing (the container-shell test is flaky, issue #107), plus 2 in `rail-order.e2e.ts` and 14 in `a11y.e2e.ts` (axe on the real page, both themes), plus 5 GitOps scenarios (`e2e/specs/gitops.e2e.ts`: Flux list/details/suspend+resume, Argo CD list/details) on a cluster brought up with `--gitops` — without the Flux/Argo CD kinds they are skipped (pending); without the variable it builds the debug binary itself (see the trap above). The e2e setup also needs `helm`: it installs a Helm release and the namespace `sextant-e2e` into the test cluster (`setUpCluster` in `e2e/cluster.ts`, config/cache in a temp dir) and removes them at the end; the GitOps install is not exercised by e2e. Failure screenshots are in `target/e2e/`. A run overwrites `docs/screenshot.png`: afterwards `git checkout -- docs/screenshot.png`.
- README demos (`docs/demo.gif`, `docs/demo-mcp.gif`, and `target/demo/<name>.mp4` for posts): `SEXTANT_E2E_SKIP_BUILD=1 scripts/demo-gif.sh` (both) or `scripts/demo-gif.sh readme|mcp`; scenarios in `e2e/demo/*.demo.ts` (`e2e/demo.conf.ts` reuses the e2e setup and writes the profile: dark theme, no update check, MCP on port 47491 (not the default 47391) for `mcp`). Needs `Xephyr` (the app runs on a nested display `:99`, so only its window is recorded), `ffmpeg`, a cluster with `--prometheus`, and `fs.inotify.max_user_instances` ≥ 512 (otherwise kind ends followed logs with "too many open files"). The MCP agent is a scripted client named `claude-code` in `mcp.demo.ts`; the server, guard, confirmation and log are real.

## Pitfalls

- `target/` bloats to tens of GB (35 GB when checked) because of debug info; for local builds and checks: `CARGO_PROFILE_DEV_DEBUG=0 CARGO_INCREMENTAL=0 npm run check`.
- Integration tests without `SEXTANT_TEST_KUBECONFIG` are silently skipped and count as passed (stderr only says "skipped"); a green `cargo test --workspace` without a cluster proves nothing about the cluster. Tests that stop the kind container (`connect.rs`, `watch.rs`) run only with `SEXTANT_TEST_DOCKER_RESTART=1`.
- The `sextant` crate embeds the built frontend from `dist/`: on a clean clone `npm run build` is needed before `npm run check` (CI does the same).
- Do not edit `src/api/generated/` by hand: `npm run check` compares it with what Rust generates. A type that starts crossing the boundary gets `serde(rename_all = "camelCase")` + `ts-rs`, then `npm run gen:types` and commit the result.
- Command and event names are not part of the generation: when adding a command, edit by hand `src-tauri/src/lib.rs` (`generate_handler!`), `src/api/commands.ts` and `src-tauri/tests/commands.rs`; a typo shows up only in a test or at runtime.
- String literals in JSX are forbidden by eslint (`i18next/no-literal-string`); a string goes through `src/locales/en/<ns>.json`, a field value is built outside JSX. `@tauri-apps/*` outside `src/api/` is forbidden by eslint too (plugins go through `transport.ts`).
- **Every new or changed UI string goes into every language, in the same change** (ADR-0073): `src/locales/locales.test.ts` compares each `src/locales/<lang>/` with `en/` (files, keys, no empty text, the same `{{placeholders}}`, `$t(…)` and tag-like text, exactly the language's CLDR plural forms) and fails `npm run check` otherwise; the runtime English fallback is not a way out. Plurals: English `_one`/`_other`, each language exactly its CLDR categories (ru/uk/pl `_one/_few/_many/_other`, fr/es/it/pt-BR `_one/_many/_other`, zh/ja/ko `_other`), and every form, `_one` included, keeps `{{count}}` (Russian `_one` is also 21); a text for exactly one object without a number is its own key. Never glue keys or fragments into a sentence (`n + " pods"`, `t(a) + t(b)`): one key per sentence, a list as one placeholder joined by `formatList`. Dates and numbers through `src/i18n/format.ts`, never `toLocaleString()` without the UI language. Kubernetes kinds and API terms stay English in every language (`TRANSLATING.md`). A new language is a new directory whose name is a canonical BCP 47 tag that `matchLanguage` maps to itself (the test checks it), plus a row in `TRANSLATING.md`.
- `sextant-core` must not pull in `tauri` and `portable-pty`: OS processes (`helm`, the cloud CLIs) sit behind the `desktop` feature; a violation is caught by `node scripts/check-core-deps.mjs`.
- Streams (watch, logs, terminal, extension watches, GitOps installs, file transfers): the frontend creates the id, `openStream` (`src/api/stream.ts`) creates a Tauri `Channel` (`streamChannel` in `transport.ts`) before `*_start(…, streamId, onEvent)`, and the backend sends with `channel.send` — never as events, which Tauri delivers by `eval` of the inlined payload and WebKit keeps the memory of (ADR-0078); so the backend holds nothing back: the first watch snapshot goes out at once, then batches no more often than every 250 ms (`BATCH_INTERVAL`), logs every 100 ms. Do not add delays and do not start a stream bypassing `openStream`. The id is `[A-Za-z0-9_-]`, ≤128; an id in use or malformed is `invalid` (`check_stream_id`). The page calls `streams_reset` (`resetStreams()`) once on load, and a start that outlived the reset is rejected (`AppState::undo_if_reset`); a `*_start` command registers the subscription in `AppState` before the core works (`start_watch`), otherwise a stop during the start will not interrupt it. A new start command takes `on_event: Channel<Payload>` as its last argument (and an entry for `onEvent` in `later_argument_names_match_the_frontend`, `src-tauri/tests/commands.rs`); in tests `mockBackend` delivers `backend.emit("<prefix>:<streamId>", …)` to it (`STREAM_PREFIXES`), and Rust module tests receive through `events::test_channel`.
- A new subscription, stream or session must live in `AppState` (`src-tauri/src/state.rs`), otherwise `close_cluster` and closing the window will not close it.
- Secret values are stripped in the core (`resources::get::to_json`: values `""`, annotation `sextant.dev/values-hidden`, no last-applied), so they are in neither watch nor `resource_get`. The full value is available only through `secret_value` (one key) and `resource_get_full` (for the editor). `resource_replace`/`resource_apply` reject an object with the marker annotation (`ensure_values_present` in `Document::from_value`) — do not remove that call when editing `mutate.rs`.
- Discovery is one per cluster (`ClusterManager::kinds`, a shared result for everyone waiting); `ResourceKind.printerColumns` from it is always empty — CRD columns are read lazily, one CRD at a time (`useCrdPrinterColumns` in `src/resources/crdColumns.ts`). Built-in kinds (`BUILT_IN_KINDS` in `crates/sextant-core/src/resources/get.rs`) open without discovery. CRDs in the sidebar come from discovery (new CRDs are picked up without reconnecting, see `watchCrdChanges` below). The column cache keeps an empty list only for `forbidden`/`notFound`; another error (network, 5xx) removes the key from the cache and the next open reads the CRD again.
- `WatchSpec.metadata_only` (TS `metadataOnly`) returns only `{apiVersion, kind, metadata}`; for lists that need metadata alone (Helm releases) rather than whole objects.
- Timeouts: connecting — 10 s per connection and 20 s per check; changes are under `CHANGE_TIMEOUT` = 30 s per request (`src-tauri/src/commands/actions.rs`: scale, restart, cordon, trigger, suspend, replace, delete); drain and applying several documents — 30 s per request (`resources::STEP_TIMEOUT`), with no limit on the whole operation. A `timeout` does not cancel the operation on the server. The client itself retries only GET/HEAD (reads) on 429/503/504, at most 3 times and for no longer than 5 s (`cluster::RetryPolicy`; kube's `server_retry` is off); a change is never repeated, and its 504 becomes `Timeout` with `cluster::CHANGE_TIMED_OUT` (ADR-0055).
- `settings_update` does not overwrite what the backend writes (`kubeconfigSources`, window sizes): a new backend field has to be added to `update_settings` (`src-tauri/src/commands/settings.rs`); `AppSettings.extensions` is backend-owned too (changed only by the `extension_*` commands; a stale frontend copy must not enable an extension or widen its grant, ADR-0052); frontend fields (`clusters[id].agentAccess`, `clusters[id].previewChanges`, `AppSettings.fleet`, `AppSettings.timeline` (`persist`, off by default), `AppSettings.cleanup` (`excludedNamespaces`, `minAgeDays`, `checkConfigMaps`/`checkSecrets` off by default), `AppSettings.mcp`, `node_shell_image`, `debug_image`, `close_to_tray`, `notifications` (also the volume levels `volumeWarnPercent` 85 / `volumeCriticalPercent` 95), `views`, `pins`, `workspaces`, `activeWorkspace`, `snippets` (terminal snippets, read entry by entry), `kubeconfig` (`writableSources` — off by default — and `credentialExpiryDays`)) are written by the frontend and are not in that list; a backend command that changes frontend fields itself (`kubeconfig_edit_apply` moving/purging cluster settings) runs through `withBackendSettingsChange` (`src/api/settings.ts`) so a stale frontend copy is not written back. `settingsVersion` is backend-owned and never goes down (`SettingsStore::update`); a version-0 file's `language: "en"` (the old default) is migrated to `system` once (`settings::migrate`). An unreadable `settings.json` is not overwritten (copy `.bak-…`, `settings_status`).
- All kube errors go through `error::kube_error` (it strips exec-plugin secrets); run `helm` only through `HelmCli::command()` (it scrubs `HELM_KUBE*` and `KUBECONFIG`); a real helm is not run in `src-tauri/tests/commands.rs`.
- The terminal's temporary kubeconfig lives in `TermSession.guard` and is deleted synchronously when the session stops; temp kubeconfigs are `sextant-kubeconfig-<pid>-*`; `remove_stale_temp_kubeconfigs` at startup removes only those of dead PIDs (old names without a PID after 24 h), `sextant-shell-*` directories are not cleaned.
- A feature is wired in only through `src/features/<name>/index.ts` (`import.meta.glob`); a directory without `index.ts` does not reach the app. There are no native checkboxes or radio buttons: use `Checkbox` and `Radio` from `src/components`.
- The application version is written in five places (`Cargo.toml` `[workspace.package]`, `Cargo.lock`, `src-tauri/tauri.conf.json`, `package.json`, `package-lock.json`) and must match the release tag; bump all of them at once and check with `npm run check:version`.
- Updates: `bundle.createUpdaterArtifacts` is on in `src-tauri/tauri.conf.json`, so a release build signs the artifacts with the key from `TAURI_SIGNING_PRIVATE_KEY` (+ `_PASSWORD`) and fails without it; locally, build with the `--config` from Commands. The public key is `plugins.updater.pubkey` in `tauri.conf.json`: without a key or an endpoint the plugin is not registered (`updater_configured` in `src-tauri/src/lib.rs`, the same rule is `updaterConfiguredIn` in `src/api/updater.ts`) and the interface shows updates as disabled. If the private key is lost, installed copies will not accept updates (ADR-0022).
- GitOps (Flux, Argo CD) works only through the Kubernetes API: actions are `resource_patch` (`api.resources.patch`, `PatchType` merge/json), no `flux`/`argocd` CLI (ADR-0024, ADR-0025). The one install path is the window's `gitops_install_*` commands, from the projects' official manifests, started by the user's click only (ADR-0058); never add it to the MCP tools or the extension methods (a test in `src-tauri/src/gitops_install/tests.rs` asserts no install name there). A patch that names `sextant.dev/values-hidden` is `invalid`.
- GitOps install: `readiness` returns an empty list while no workload exists yet — an empty list is not "ready" (nothing is done until every Deployment/StatefulSet of the plan exists and is ready); `installed` means CRDs + key controllers, otherwise "Partly installed" and the install is offered again (ADR-0058). The prepared plan waits under a single-use token (10 min, bound to its cluster); the running install is a task in `AppState.gitops`, stopped by `close_cluster`, a page reload and exit (the window still gets a final `stopped`/`error` event). The Flux/Argo manifest is cut by `gitops_install::prepare` (fixed namespaces, kind allow-list, ADR-0062): a new upstream kind outside the allow-list is refused until the list is extended.
- A new download source goes through `src-tauri/src/download.rs` rules and an allow-list of exact URLs built by Sextant (as `gitops_install/download.rs`): HTTPS only, no automatic redirects (each one only to GitHub asset hosts), size and time limits, errors without the URL. Never fetch a URL the user, an agent or an extension typed.
- **Image files (ADR-0103)** are the one exception to the rule above: the registry named in an image reference (a pod's spec or typed), only through `src-tauri/src/image_files/registry.rs` — HTTPS only (no insecure switch), never a loopback/link-local/metadata address (checked on every URL and again on every resolved address by its `FilteringResolver`), the token realm asked for `repository:<repo>:pull` only, blob redirects without credentials, every blob verified by its digest. Pull secrets and Docker credentials stay in the backend (`Credential`'s `Debug` is `<hidden>`); the user's Docker config (and its credential helpers) only with `imageFiles.dockerCredentials` (off by default). Layers are streamed and indexed within `image_fs::limits`, never stored; only indexes are cached (`<app cache>/image-files/`). Window only: no MCP tool, no extension method.
- A new CRD (including one installed by Flux/Argo after connecting) is visible without reconnecting: `watchCrdChanges` (`src/resources/useKinds.ts`, a metadata watch on CRDs, debounce `CRD_REFRESH_DELAY` = 1 s) calls `cluster_kinds_refresh` (`ClusterManager::refresh_kinds`), which resets the discovery cache (ADR-0026). Do not bring back "only after reconnecting".
- The Flux and Argo CD sections are registry kinds in the `flux`/`argocd` sections (`SidebarSection` in `src/resources/registry.ts`, ADR-0031); without the kinds in discovery the section is hidden. A page registered in a discovered section (`DISCOVERED_SECTIONS`: `gatewayApi`, `flux`, `argocd`) is shown only while that section has at least one served kind (`buildSections` in `src/layout/sidebar/Sidebar.tsx`), so such a page needs no check of its own; a page in any other section is not checked against discovery.
- `resolve_kind` (`crates/sextant-core/src/resources/get.rs`): the requested kind version if discovery serves it, otherwise the version from discovery (discovery keeps one, the preferred) — this is for get/watch/patch by `ObjectRef`; `replace_yaml`/`apply_yaml` use the version from the document (`resolve_document_kind`) if the group serves it, otherwise `notFound` without a request (ADR-0030).
- Logging in to Argo CD goes only through `ArgoSessions` (`AppState.argocd`): the Argo API is reached by a port-forward to `argocd-server`, TLS is not verified only for `127.0.0.1` (ADR-0027); the source order is the saved login, `argocd-initial-admin-secret`, a Secret labelled `app.kubernetes.io/part-of=argocd` with a `token` key, otherwise `unauthorized` (ADR-0028). Argo passwords and tokens never go to the frontend (`SecretString` prints `<hidden>`, Secret values are stripped in `ManagedResource`) and are never logged.
- The saved Argo login is in the OS keyring: service `sextant`, user `argocd:<ns>@<kubeSystemUid>` (the UID of the cluster's `kube-system` Namespace, read once per connection; never keyed by the API server URL, which several clusters can share behind a proxy), or `argocd:<clusterId>:<ns>` when `kube-system` cannot be read (the binding comes from `ClusterManager::server_binding`); an old `argocd:<clusterId>:<ns>` entry is not moved — under a UID key it is deleted unread, value JSON `{username,password}` or `{token}` plus `binding: {server, caSha256, entry}` (`entry` — the `ClusterId` of the kubeconfig entry it was saved through) — a login is offered only when the API server URL, the CA and the entry all match the current connection (clusters behind one proxy URL and CA are told apart by the entry); a value without a binding or without `entry` (v0.6.1, v0.7.0) is never offered and is deleted unread under any key (ADR-0029, #116); the store is read once per entry and run (cached in `ArgoSessions`). A candidate rejected by Argo CD is not tried again until its source changes (the secret's resourceVersion, a new save, a new input; `is_refusal`, `standard_credentials_with_origin`), the user signs out, or the cluster is closed or reconnected (all Argo state of a cluster — server, forward, session, typed login, keys, refusals — is tied to `ClusterManager::connection` and dropped when it changes, since a reconnect may reach another cluster); an unreachable server is not remembered. Plain HTTP to Argo CD only with `server.insecure: "true"` in `argocd-cmd-params-cm` — never as a fallback after a TLS error (ADR-0027).
- The Argo CD server is looked up only in the installation namespace; the installation is determined by the ClusterRoleBinding `argocd-application-controller`/`argocd-server` (binding name and SA name, including Helm's `<release>-…`), without it (a namespaced install, no rights on CRBs) — candidates by `argocd-cm`/`argocd-initial-admin-secret`; ambiguity is `notFound` with the prefix `argocd::AMBIGUOUS_INSTALLATION` naming the candidates, and the frontend opens nothing until the user picks one; the pick is `clusters[id].argocdNamespace` (frontend-written), taken by the backend only among its own candidates (ADR-0032). `argocdNamespace` in the frontend is `api.argocd.status().namespace`.
- Icons go only through `src/components/icons.tsx` (`Icon`, `renderIcon`); do not import `lucide-react` directly (ADR-0033). `icons.test.tsx` requires every name of the set to be used somewhere: adding a name without a use, or removing the last use, turns it red. `ActionDef.icon` and `DockActionDef.icon` are `IconName` (there is no `IconSpec` any more); an extension's unknown icon string is mapped to a default by the host.
- Button sizes are the tokens `--control-height` (32 px) and `--control-height-compact` (28 px, table rows) in `src/styles/global.css`; use the shared `Button` (`variant`, `size`, `iconOnly`+`label`); do not add local overrides of button height and font, `.btn--small` is gone (ADR-0034).
- A button that became an icon keeps its former text in `aria-label` (+ `title`): vitest and e2e depend on these names. E2E finds menu items by the button's direct text node (`button=<text>`), so icons and chevrons in them are SVG with no text and no `<title>`.
- eslint: the attributes `variant`, `size`, `icon` and `on[A-Z].*` are excluded from `i18next/no-literal-string` (`eslint.config.js`).
- The cluster icon in `settings.json` is `clusters[id].icon`: `{type:"text",text}` or `{type:"image",dataUrl}`; `dataUrl` is a 96×96 PNG, drawn only with the prefix `data:image/png;base64,`. The rail view is `window.railExpanded` (written by the frontend, ADR-0035, ADR-0036). A new settings field also goes into `defaultAppSettings()` (`src/api/settings.ts`) and `defaultClusterSettings()` (`src/features/clusters/clusterSettings.ts`).
- A pod limit is shown only if it is set on all containers (otherwise "no limit (set on N of M containers)"); `podResourceAmounts` on the frontend computes it from `spec.containers` (ADR-0037).
- MCP access rules parse strictly (ADR-0041): any unknown field or action reads as Off, so the rules editor must write exactly the shapes of `access.rs` (`{"type":"all"}` / `{"type":"only",…}`); preset rules come only from `access_preset_rules`, do not duplicate them on the frontend. Agent access is closed by default; "Secret values" is its own action that no preset grants.
- `Guard::check` (`src-tauri/src/mcp/guard.rs`) must run right before every side effect of a tool, not at the start of the handler: it re-reads the settings, asks for confirmation and refuses after a server stop. A tool that touches several objects checks all of them before sending anything. For a kind without a namespace pass `None` (the empty string `""` also counts as `None`) whatever the agent sent, otherwise "team-a × all kinds × Delete" would delete a Node.
- A JSON patch on a core Secret, when the agent lacks Secret values, may contain only `add`/`replace`/`remove`; every `path`/`from` must be a string starting with `/` (ADR-0043). Helm names, namespace, chart and version are validated before the Guard.
- The MCP token is the file `mcp-token` (mode 0600 on Unix) in the settings directory, read by the app and by `sextant mcp` (ADR-0039): never print it to logs, errors, the activity log or test output (`Token` prints `<hidden>`); `sextant mcp` must not create it (`token::load` creates nothing). The directories are computed without Tauri (`src-tauri/src/mcp/paths.rs`), and a test keeps them equal to Tauri's `app_config_dir`.
- The server listens on `127.0.0.1` only; a request with `Origin`, a foreign `Host`, a wrong Bearer or a body over 4 MB is refused before the MCP layer. Stopping the server (`McpServer::stop`, from `close_all`) cancels in-flight calls, refuses pending confirmations and closes what the agent started (`McpContext.agent_forwards`); an agent may stop only its own port forwards. `sextant mcp` may print nothing but JSON-RPC to stdout (diagnostics go to stderr, ADR-0040).
- The activity log (`mcp-audit.jsonl`, ring of 2000, oldest first) holds summaries only (a call that never reached a decision is `NotChecked`): no Secret values, YAML or command output, and text is clipped (`audit::clip`). A confirmation is answered in 120 s or counts as refused; without a window it is declined (ADR-0042).
- Cloud CLIs (`aws`, `gcloud`, `az`) run without a shell, with a cleaned environment (`pty::shell_environment`; `KUBECONFIG` removed), a 60 s timeout, only through the one launch function behind the `desktop` feature; Sextant never runs a login — it shows the login command and puts it into a terminal without executing it. Clusters go to `kubeconfigs/cloud-<provider>.yaml`; `~/.kube/config` is never touched (ADR-0044). Tests use fake CLIs in `PATH`; real accounts were not tried.
- Node shell (ADR-0045): the pod `sextant-node-shell-<node>-<rand>` in `kube-system` is registered in `AppState` before it is created and deleted on tab close, disconnect and app exit; the sweep on connect deletes only pods with the user's own `sextant.dev/owner` label, plus any labelled pod older than 8 h — never a colleague's live shell. Node-shell pods are recognised by name or by label (`node_shell::is_node_shell_object`, fail closed, ADR-0056): agents get no node shell, cannot `exec_command`, patch, apply to or delete them, a drain keeps them (`DrainOptions.keep_node_shells`), and port-forward to them or to `hostNetwork` pods is refused; extensions cannot modify or delete them either (`access_guard::refuse_*_node_shell`).
- Extension calls are checked in Rust (`extension_call` → `decide_extension` against `granted`, confirmation, journal), never only in the frontend: the iframe is untrusted. The grant is by cluster context name and covers same-named contexts of every kubeconfig source. Do not widen `ExtensionPermissions` actions beyond read/modify/delete/logs/secretValues; `resolve_package_file` is the only way the protocol opens package files (no links, no `..`).
- Extension CSP is built per response from the extension's base URL (`extension_csp(base)` in `src-tauri/src/extensions/protocol.rs`) and never uses `'self'`: the frame's origin is opaque, and on Windows all extensions share one origin `http://sextant-ext.localhost` (ADR-0048). The app CSP (`src-tauri/tauri.conf.json`) has `frame-src sextant-ext: http://sextant-ext.localhost`; a test pins it.
- The iframe `sandbox` (`FRAME_SANDBOX`, `src/extensions/ExtensionFrame.tsx`) never gets `allow-same-origin`. Every bridge message carries `sextant:1` and the per-document `doc` (`[A-Za-z0-9_-]{16,128}`); the host and the SDK ignore messages of another `doc`; limits: 32 watches per document, 8 documents per frame. A wire change goes into `src/extensions/protocol.ts` and `sdk/src/protocol.ts` together.
- A new `extension_*`/`ext-*` command or event: `src-tauri/src/lib.rs`, `src/api/commands.ts` or `events.ts`, `COMMANDS` in `src-tauri/tests/commands.rs`. Extension host strings live in `src/locales/en/extensions.json`; the host's contributions are registered with ids `ext:<extId>:<id>` and removed together by `unregisterExtension`.
- Confirmations: at most `MAX_PENDING_PER_EXTENSION` = 4 pending per extension, then the call is refused without asking; the principal shown is "Extension <name>". `apply` from an agent or an extension is checked on the same parsed documents that are applied (`resources::parse_documents` / `plan_apply`, ADR-0057): do not re-parse the YAML for the check.
- Keep in tray (ADR-0059): closing with `closeToTray` hides the window and never runs `close_all` (connections, forwards, terminals, MCP and installs keep running); it is offered and honoured only while a tray icon is really shown (`tray::available`: on Linux needs a StatusNotifier host; `defers_close` holds the close while that is checked). Only tray "Quit" or `app.exit` ends the app. Every "bring the window back" path uses `window::reveal`; confirmations from agents and extensions go through `ask_in_window` (`lib.rs`: reveal + attention + `mcp-confirm`, declined only with no window), so they also work from the tray.
- Gateway API views (ADR-0063) are read-only and pure frontend: no Rust command was added, nothing is written to the cluster, no request is sent to a Gateway. Watches are opened only for kinds the cluster serves (`hooks.ts`) and, for namespaced lists, only for the involved namespaces; nothing is watched before discovery. The matching engine's implementation-specific choices are documented in the header of `matching.ts` and surface as notes in the result: a RegularExpression path is ranked between Exact and PathPrefix, regular expressions use the JavaScript dialect, and the hostname decides before the route kind (HTTPRoute vs GRPCRoute). Do not add controller-specific knowledge beyond what `status` says.
- Tray Show/Hide (#115, ADR-0059): on Linux the label is "Hide" only while the window is visible and focused (`WindowToggle::by_focus`; GTK on Wayland never reports a minimized window), any other state brings it back; Windows and macOS use visible and not minimized (`by_minimized`). On Linux an X11 session whose tray owns `_NET_SYSTEM_TRAY_S<screen>` (XEmbed: i3bar, older XFCE) counts as an available tray; Wayland without a StatusNotifier host does not.
- Single instance is registered in release builds only (`with_single_instance`, `cfg(not(debug_assertions))`, ADR-0060): `npm run tauri dev`, `target/debug/sextant` and e2e run beside an installed Sextant and share its settings directory. A second release launch exits before `setup` and reveals the first.
- Debug containers (ADR-0064): an ephemeral container can never be removed from its pod (the dialog says so; closing the tab only ends its shell with Ctrl+C, Ctrl+D and closed stdin); a debug copy `<pod>-debug-<rand>` (no labels or owners of the original, no node, no probes, `shareProcessNamespace`, `activeDeadlineSeconds` ≤ 8 h) is a `DebugCopyPod` in `AppState.sessions`, registered before it is created and deleted on tab close, disconnect and exit (exit waits through `debug::wait_for_deletions`, `NODE_SHELL_DELETE_WAIT`); a create without an answer is deleted by name for 75 s. `sweep` runs only when a copy is started in that namespace and deletes only this owner's copies of other runs and anyone's older than 8 h. Debug copies are recognised by `managed-by=sextant` + `sextant.dev/debug-copy=true` (`debug::is_debug_copy_object`): an agent's `exec_command` re-reads the pod right before running and is refused there, failing closed when the pod cannot be read; neither debug nor file copy is an MCP tool or an extension method.
- File copy (ADR-0065) runs `tar` in the container (no `tar` → a clear `notFound`); the member is passed as `./<name>` so a leading `-` is never an option; long-name/pax headers before one entry are capped at 2 MiB. A download writes to `.sextant-download-*.part` created exclusively (`tempfile`, O_EXCL) next to the destination and renamed over it only on success (a link there is replaced, never followed); a cancelled or failed one leaves nothing. A single file is accepted only as exactly one regular entry with the asked name (no absolute path, `..`, link or second entry), re-checked against the kind `files_stat` saw; a folder is saved as `.tar.gz` and never unpacked. An upload asks first and may leave a partly written file in the container. A transfer is a subscription in `AppState` (stopped by `files_transfer_stop`, disconnect, `streams_reset`, exit); progress at most every 100 ms.
- Problems (ADR-0066): one rule set (`problems/model.ts`) feeds the page, the badge and the notifications; do not add a second detector elsewhere. A rule returns `since`/`activeFrom` and `until`, so `isActive(problem, now)` decides without a new update (hooks tick every 30 s). `store.ts` shares one watch per (cluster, kind), refcounted, closed `LINGER_MS` = 5 s after the last release, and keeps problems, never objects (≤ 2000 objects with problems per kind). A connect or disconnect drops the cluster's sources and bumps `epochOf`: a user of `acquireSource` must depend on the epoch and acquire again, or it keeps a watch the backend already closed silently.
- Notifications (ADR-0067): `AppSettings.notifications` is frontend-written and on by default; only already connected, not muted clusters and enabled categories are watched (Warning events never notify); the first look at a source is quiet; one notification per `notifyKey` with a 30 min cooldown, grouped within 3 s (≤ 3 shown, else a summary), ≤ 6 a minute; mute and settings are read when a notification is due, a muted one goes only to the history (100). Text from the cluster goes through `clip` (200/100 code points) and `inert` (`&<>` → look-alikes, because Linux notification servers read markup); never pass cluster text to `api.notifications.show` any other way.
- **Set image (ADR-0098)** is a strategic-merge patch built only by the core from `SetImageChange`s, after a fresh read that checks each container's list and shown image (and refuses an owned Pod or a static Pod's mirror) and with that read's `resourceVersion`; a change confirmed from a preview also sends the preview's `resourceVersion` (`SetImagePreview`) and is a `conflict` when the object changed since — the dialog then previews again. Images are printable ASCII only in the core (`is_ascii_graphic`). Never send it through `resource_patch` and never widen `PatchType` (that would reach `patch_resource` and extensions). Window only; no change-cause annotation.
- **Argo Rollouts actions (ADR-0097)** send exactly `kubectl argo rollouts`' patches (`argo-rollouts/patches.ts`, cite the plugin source when changing them), after a confirmation that lists them and a fresh read that refuses to send patches other than the ones shown. `resource_patch_status` reaches the status subresource of `STATUS_PATCH_KINDS` only (Rollout); never offer it to agents or extensions (a test in `commands/actions.rs`). Argo CD, Argo Rollouts and Argo Workflows share the group `argoproj.io`: match kinds by group and kind, never by group alone.
- Rollback (ADR-0068) exists twice by design: `src/features/rollouts/model.ts` (the window, through `resource_patch`) and `resources/rollouts.rs` (the MCP tool `rollout_undo`, Modify on the kind, `Guard::check` right before the patch). Both must send what `kubectl rollout undo --to-revision` sends (Deployment: template without `pod-template-hash` + the ReplicaSet's annotations except `ANNOTATIONS_TO_SKIP`; StatefulSet/DaemonSet: the ControllerRevision's template), refuse a paused Deployment and skip a revision equal to the live template; change one, change the other.
- Multi-pod logs and the palette open ordinary watches and log streams through `openStream` and are bounded (20 log streams per merged tab, the shared line/text caps of `buffer.ts`; palette lists ≤ 6 at once, metadata only, stopped 30 s after use). Keep the bounds when extending them; the palette searches nothing before the first typed character.
- TLS certificates (ADR-0069): only `tls.crt` and `ca.crt` are parsed, in Rust (`sextant_core::tls`); the API server sends the whole Secret, so every other value and every annotation is wiped as soon as the Secret is in hand, `tls.crt`/`ca.crt` after parsing — keep `certificate_values` doing that and never return or log a value. Names are DNS-1123-checked before any request, every request is under `STEP_TIMEOUT`, input is capped (256 KiB, 16 certificates, 1000 Secrets, 200 namespaces) and a parse error never echoes the content. TLS Secrets are deliberately **not** in the problems screen or notifications (a background check would re-read every TLS Secret, keys included, on a timer); only cert-manager Certificates are, by `status.notAfter`. The scan runs only on the TLS page's open, filter change and Refresh. "Expiring" is `notifications.certExpiryDays` (default 14) everywhere — do not hard-code 14 again. Neither TLS nor RBAC nor history commands are MCP tools or extension methods (tests in their command files).
- Right-sizing (ADR-0070): the PromQL is fixed in the core; never pass PromQL or an unvalidated name from the frontend (`validate_scope` runs first, names are escaped as well). A workload's pods are matched by the names its controller gives them (Deployment `<name>-<hash>-<5>`, StatefulSet `<name>-<ordinal>`, DaemonSet `<name>-<5>`, the generated parts in Kubernetes' safe alphabet, anchored) so a pod of `web-api` is never counted for `web`. No recommendation from a metrics-server snapshot or from < 6 h of history. The page works only on ≤ 10 namespaces picked in the filter ("All namespaces" asks for a choice). It changes nothing: the snippet goes to the clipboard.
- RBAC (ADR-0071): the computed views (`engine.ts`) see only Roles, ClusterRoles and bindings — other authorizers (Node, webhooks, ABAC) and `system:masters` are outside them, and the page must keep saying so; SelfSubjectAccessReview/SelfSubjectRulesReview (`api.rbac`) are the authoritative answer for the current user. A RoleBinding to a ClusterRole grants only in the binding's namespace and never cluster-scoped resources or non-resource URLs; a list the user may not read is unknown, not empty.
- Resource map (ADR-0072): watches are bounded — a namespaced object's namespace lists of served kinds, a cluster-scoped object's few naming lists, ≤ 4 namespaces in the Related tab and ≤ 3 on the Map, shared and released 5 s after the last user, dropped on connect/disconnect (`epochOf`); keep the bounds. Impact follows owner references by uid only, a dependent is deleted only when all its owners are, `optional` references do not count, and each consequence is a whole i18n sentence.
- Safe apply (ADR-0074): a dry run returns both sides through `to_json`, so a Secret is stripped on both sides and what would change in it is told by key names only (`SecretKeyChanges`, compared in the core); a preview never carries a value or a value comparison. MCP `dryRun: true` goes through `Guard::check_dry_run` (the rules decide, nobody is asked, journaled as `<tool> (dry run)`); a dry run touching a core Secret also needs "Secret values" and never says whether a value differs (ADR-0043). Write-tool arguments are `deny_unknown_fields` so a misspelt `dryRun` fails instead of making the change: keep it on every write-tool argument struct.
- Helm previews: a Helm before 3.13 is asked again with plain `--dry-run` after `--dry-run=server` fails — never drop the dry-run switch in that fallback. A preview is a task in `AppState.subscriptions` under its frontend id with the 120 s `PREVIEW_TIMEOUT`, stopped by `helm_preview_stop`, `close_cluster`, a reload and exit (its `helm` is killed); hooks are not compared.
- The deprecation table `src/features/upgrade/deprecations.json` is not fetched: update it for every Kubernetes minor release by `src/features/upgrade/DEPRECATIONS.md` (raise `reviewedFor`, keep the order; `table.test.ts` checks it). `upgrade_scan` is a window command only (no MCP tool, no extension method); of a Helm manifest only apiVersion/kind/name/namespace leave the core, and a release Secret is refused past 32 MiB unpacked.
- The `security` problem category is opt-in (`OPT_IN_CATEGORIES`, on only while `notifications.enabledCategories` has it) and its sources are separate (`sourceKey` adds `|security`): they never feed the other categories, the map's colours or their caps, the fleet cards never watch it, and Trivy reports are never a problem source.
- All clusters never connects a cluster without the user's click ("Connect" or "Connect all selected", ≤ `CONNECT_CONCURRENCY` at once); do not connect on opening the page or restoring the selection. The problems store's row taps (`acquireRows`) are the only watch per (cluster, kind): a new fleet table taps the problems source, never opens a watch of its own.
- **Cleanup safety rules (ADR-0081) are the boundary of the feature — never relax any of them without a review and a change of the ADR**: ConfigMap and Secret rules are off by default (`cleanup.checkConfigMaps`/`checkSecrets`); an object is a candidate only when every list that could name it is read in full (when in doubt, not a candidate); ConfigMaps, Secrets and claims of a namespace are judged only when its sample (`cleanup_sample`) shows no unknown custom kind, and a failed sample offers nothing there; references are scanned (`rules.ts` for pods, pod templates, arguments and env; `scan.ts` for tools' fields) — a new reference shape goes into them with a test, never a looser rule; an empty namespace only if every served namespaced kind holds nothing but the root CA ConfigMap, the `default` ServiceAccount and its token (an unreadable or truncated sampled kind counts as something); a Released PV with reclaim policy Retain is never offered; owned, managed (Helm/Flux/Argo CD/`managed-by`), system and excluded-namespace objects are never offered; the deletion carries uid + resourceVersion preconditions, re-checks each object right before deleting it, waits `SETTLE_MS` first, goes one at a time (namespaces last) and makes the user type the count above 20; agents and extensions get nothing new (no bulk delete, `cleanup_sample` is window-only).
- Change timeline (ADR-0079): never open a watch for recording and never record from a label- or field-selected watch (`followsDeletions`; only `metadata.name=` is allowed) — an object leaving such a list is not deleted; a new watch layer reports through `reportWatchUpdate` and an observer must stay cheap and never throw. Keep the memory caps of `recorder.ts` (ring 5000 / ~4 MB per cluster, 24 MB of object texts over all clusters, 64 KB per object, 20 000 objects per cluster) and the 8 MB file cap; a Secret's text keeps key names only, and `timeline::save`/`load` strip values again. Persistence is off by default; turning it off calls `timeline_remove_all`. The `timeline_*` commands are window-only (a test asserts no MCP tool or extension method).
- Autoscaling (ADR-0080): the HPA formulas in `hpa.ts` follow `horizontal.go` / `replica_calculator.go` (tolerance, missing-metric holding, behavior step limits with `selectPolicy`, min/max clamping) and are labelled an estimate (replica count instead of ready pods, stabilization explained from conditions, never recomputed); change them only against the controller source, with a table test. The scheduling check says what it does not judge; do not turn it into a verdict.
- Connectivity (ADR-0082): the answer is from objects, never live traffic; anything the engine cannot decide (an unreadable list, failed discovery, an `ipBlock` holding a pod IP, an unmodelled Cilium/Calico feature, an object of `UNEVALUATED_KINDS`) is "unknown", never "allowed" — a `maybe` must not round up. A new policy kind or field is either modelled with tests or routed to "unknown", never ignored.
- **Kubeconfig writes (ADR-0084)** go only through `kubeconfig/edit.rs` (`preview_edit` → `apply_edit` with the preview's `base` hash; backup `<real>.bak-<UTC time>` 0600, newest 5; temp file + rename; symlink target replaced) — never write a kubeconfig any other way, never skip the preview or the hash check. Writability is enforced in the backend (`ensure_writable`): only Sextant's own files, or a source the user allowed (`kubeconfig.writableSources`, off by default); never touch `~/.kube/config` or a `KUBECONFIG` file without that flag. Never return, log or put in an error any credential (previews show `<hidden>`), and never run an exec plugin (expiry and validation are offline; the server is contacted only on "Check connection"). Agents and extensions get no kubeconfig command.
- A context rename changes its `ClusterId`: everything kept under the old id moves (`move_cluster_settings`, which first forgets what is under the new id), and a deleted context's settings, views, pins and workspace places are purged (`forget_cluster_settings`); a new per-cluster settings field or list keyed by `ClusterId` must be added to both.
- Views import (ADR-0083) reads only the file picked in the backend's own open dialog (`views_import_open`, ≤ 1 MiB) — never add a command that reads a path the window names; the parse is strict, the preview comes first. An export never carries kubeconfig contents, credentials, tokens, the MCP token, extensions or their grants; agent access rules go out only when ticked and come in only when ticked and only on an exact cluster match (never on a context-name-only match).
- **OpenAPI schemas (ADR-0085)**: never send a whole OpenAPI document to the window — `openapi_kind_schema` returns one kind's root and its reachable definitions (≤ 600); never parse a group/version document into a `serde_json::Value` — read it with `openapi/stream.rs` (only `components.schemas`, one schema at a time, off the async runtime; `tests/openapi_memory.rs` guards the peak). The cache is per cluster and per connection (`SchemaCache` in `ClusterManager`, dropped by `refresh_kinds`/`disconnect`, a generation check before storing); the frontend asks only for kinds discovery serves (`schemaSourceFor`). The editor must keep working without a schema.
- **`resource_create` is create-only (ADR-0086)**: one POST, never repeated, AlreadyExists is the answer for a taken name. Use it (not `resource_apply`/`replace`) wherever an existing object must never be modified — storage actions (VolumeSnapshot, restored claim, Velero Backup/Restore) go only through it. Window only: never add it to MCP tools or extension methods.
- Volume usage (ADR-0086): used = capacity − available (reserved blocks count), inodes = total − free — not the summary's `usedBytes`; keep the kubelet and Prometheus paths on the same formula. The Prometheus fallback runs only fixed `kubelet_volume_stats_*` queries naming no object. "Disk almost full" (`disk`) is opt-in and `external` (no watch of its own); the window polls `storage_volume_usage` only while a view holds it (`acquireVolumeUsage`).
- **Cost (ADR-0087)**: requests to OpenCost/Kubecost go only through the API server's service proxy with the parameters `cost::client::request_uri` builds from a validated `CostQuery` (window, aggregate, ≤ 200 namespaces) — never a port-forward, never a path, filter or parameter typed by the user; keep the 30 s / 8 MiB / 2000-row caps. Never install OpenCost. Estimates (monthly, savings) are labelled as estimates in the UI.
- **Terminal (ADR-0088)**: each pane is its own backend session (started like a tab, node/debug panes confirm like tabs). Snippet values are quoted per shell by `quoteFor` (POSIX, PowerShell, unknown) and refused when unsafe (backslash, control, invisible, text-direction characters; quotes in an unknown shell) — never substitute a value unquoted; snippets go only into the focused pane, only "Run" adds Enter. Broadcast never sends input typed before its confirmation (dropped), never preselects panes of other clusters, and ends when a target pane closes.
- **Service mesh (ADR-0089)** is read-only and answers from objects only (never istiod, a proxy or linkerd-viz). Anything the engines cannot evaluate is "unknown" ("Cannot tell"), never "allowed": a dry-run policy (`istio.io/dry-run`) is shown but not enforced, an action Istio does not accept and a DENY/CUSTOM attached by `targetRef` give "unknown". The cluster domain `cluster.local` and root namespace `istio-system` are assumptions (`CLUSTER_DOMAIN`, `ROOT_NAMESPACE`); Istio objects come from the one shared store (`mesh/store.ts`), not from new watches.
- **Compare (ADR-0090)** is read-only and window-only (a test keeps the `compare_*` commands out of MCP tools and extension methods) and never connects a cluster itself. Secrets are compared only through `compare_secrets`/`compare_secret_namespaces`: values are hashed in the core and neither values nor hashes go to the window; a value is shown only through `secret_value` after "Show values". Ignore paths are `AppSettings.compare.ignorePaths` (frontend-written, key `group/Kind`).
- **Watches (ADR-0091)**: a view acquires lists through the shared registry (`acquireWatch`/`useWatch`, key = cluster + spec: kind, namespaces, label and field selectors, `metadataOnly`; `WatchOptions` are not in the key) — do not open a second stream for a list another view holds. Caps belong to the consumer: a table asks `TABLE_WATCH_OPTIONS`, a view that needs every object asks none and lifts the cap of the shared stream. Field selectors go to the API server only for the fields mapped per kind in `selectors.ts` (an unsupported field makes the API server refuse the whole list); add a field there only from the API server's own list. The window-only updates (`snapshotPart`, `snapshotEnd`, `capped`) stay out of the SDK (`NARROW` in `sdk/scripts/sync-types.mjs`); agents and extensions get the default options.
- **Accessibility (ADR-0092)**: a new modal uses `Dialog` or `useFocusTrap` (the modal stack decides who takes Tab and Escape), never its own focus handling. The approval delay of `ConfirmHost` ("Allow" ignores the keyboard for 1 s, clicks for 300 ms) must stay. Every new screen or page gets an axe check (`axeViolations`; registered pages are covered by `a11y-pages.test.tsx`). Colours only through the theme tokens of `global.css`, in both themes; a new colour token goes into `src/styles/contrast.test.ts`. A terminal must keep Ctrl+Shift+E as the way out.
- **VictoriaMetrics (ADR-0102)** is a `PrometheusTarget` like any other: never fork a query into a MetricsQL variant — a new or changed query must stay valid PromQL that VictoriaMetrics answers alike (`tests/victoria_metrics.rs` on `up --prometheus --victoria-metrics`). Auto-detection keeps every Prometheus before every VictoriaMetrics, so a cluster with both keeps its Prometheus; a new known name goes into `known` with its source (chart template or operator code) cited in ADR-0102. VictoriaMetrics answers "now" 30 s behind (`-search.latencyOffset`), `rate` without extrapolation and `timestamp()` as the step time: compare with tolerances, never exact values, and do not send `latency_offset`. Window texts that mean any source say "Prometheus-compatible source". `MetricsStatus.prometheusKind` is optional and saved settings have no new field.
- **Request metrics (ADR-0095)**: sources are found only by asking Prometheus for the fixed `RequestSourceKind::known_metrics` names (`match[]`, cached per connection); a new source is a new `RequestSourceKind` with its row in ADR-0095 (detection names, workload/pod labels, what an error is), a `shape` and `request_selectors` arm, and a fixture in `metrics/requests/testdata/`. The command takes a strictly read `RequestTarget` (names only, `validate_target` first); never pass PromQL, a metric name, a label or a Service name from the window. A source without series of the target is left out of `golden`, a failed one is in `failed` (unknown, not absent). linkerd-viz's Prometheus is asked only when the cluster's has no Linkerd metrics. Window only (a test keeps it out of MCP tools and extension methods).
- **Traffic graph (ADR-0096)**: edges only from Prometheus (no Hubble Relay client); a new edge source is a row in ADR-0096, its `edge_metrics` names and an `EdgeShape` in `metrics/prometheus/traffic.rs` whose parts pick disjoint series (each call counted once: a server report, plus a client report only for pairs the server does not report) and are read with the source's own labels, plus a fixture checked by a real Prometheus. Keep the longest encoded query under the length a test pins (5 KiB) so proxies with an 8 KB URL buffer accept it. The command takes namespace names (1–5, `validate_namespaces`) and a window only. Keep every query restricted to the `topk(MAX_TRAFFIC_EDGES)` edges, each answer under `MAX_TRAFFIC_BODY`/`MAX_TRAFFIC_SERIES`, and an end without a name as an "unknown" node, never dropped. The view polls only while the mode is shown and the window visible, and looks ends up on a click (no watches). Window only (a test keeps it out of MCP tools and extension methods).
- **MCP diagnostic tools (ADR-0094)** compute in the window, never in a Rust copy of an engine: a tool checks Read with `Guard::check` on the object it asks about (and `Guard::check_reads` for the namespace) before the window is asked, passes the Read rules (`reads`) so the window feeds its engines only readable lists (`canRead`; unreadable means "unknown", never "allowed" or empty), and reads the answer back through a typed shape in `diagnose_answers.rs`, where every named object is re-checked (`ReadFilter`) — keep all three steps for a new tool, keep its argument struct `deny_unknown_fields`, never journal the answer. The window reads only what the agent may read: watches of only its readable namespaces/kinds (cluster-wide only with Read everywhere), cross-object findings (mesh, practices) computed on that alone and kept only when everything they rest on was read, their `refs` re-checked in Rust, disk only with Read on claims and Nodes everywhere (else `notChecked`), and a TLS certificate only with "Secret values" (`checkCertificates`; otherwise `tls_certificate_info` is not called and the step is "not checked"); a diagnosis's status and summary are recomputed from what is left; every answer carries `dataNotice`; when Rust stops waiting it sends `mcp-diagnostic-cancel`. `get_problems` gives opt-in categories only while on and `credentials` never; `get_recent_changes` reads only the recorder's memory (no watch) and a Secret's changes leave as paths; `get_permissions` is always labelled computed and the access reviews stay window-only. Tool names must not contain the window-only words the command tests forbid (`timeline`, `history`, `rbac`, `review`, `tls`, `cert`, `compare`, `count`, …): hence `get_recent_changes`.
- A kubeconfig `proxy-url` may be `http://`, `https://` or `socks5://` (kube features `http-proxy` + `socks5`; host names resolved by the SOCKS proxy, #184); kube-rs refuses `socks5h://`, so documentation says `socks5://`. Without `proxy-url` kube-rs falls back to `HTTPS_PROXY`; `NO_PROXY` is not honoured.
- `TypeScript` is pinned to `~6.0` (a typescript-eslint limit) — do not upgrade blindly.
- E2E: `e2e/wdio.conf.ts` hardcodes the tauri-driver port 4444, the native port is not set (default 4445); if the ports are taken or coincide, the driver fails at start — `tauri-driver --port 4447 --native-port 4448` worked (not in the config). A run overwrites `docs/screenshot.png`.
- E2E: WebKitWebDriver loses repeats and spaces in `browser.keys` (for text there is `typeText` in `e2e/app.ts`) and prints `/` and `:` wrongly — do not enter such characters through `browser.keys`.
- CI (`ci.yml`) runs on push and PR to the `main` branch and manually, on ubuntu, macOS and Windows, `core.autocrlf false`. macOS and Windows cannot be checked here — CI only. What broke there and does not show on Linux: file names that differ only by case (caught by `scripts/check-case-collisions.mjs`), GNU-only utilities in test scripts (`stat -c`), `/proc`, `Path::is_absolute` by the host's rules, the path `tauri://localhost` in IPC tests (on Windows it is `http://tauri.localhost`), hashes of paths with `/`.
- Release: a `v*` tag or a manual run `gh workflow run release.yml --ref vX.Y.Z -f tag=vX.Y.Z` (rebuilds an existing tag without rewriting it, with the workflow the tag was released with; run from main for an older tag, the workflow builds what that checkout knows — no `scripts/packaging.mjs` means the pre-ADR-0104 layout: no arm64 row, no `.rpm`, no portable zip, no `packages` job, and only `linux-x86_64`, `darwin-*`, `windows-x86_64` required in `latest.json`; the publish job's script always comes from the workflow's own commit). `release.yml` checks the tag against the version, builds .deb/.AppImage, a universal .dmg and .msi, assembles `latest.json` and publishes the release only if it has all platforms (`node scripts/packaging.mjs latest-json` in the publish job: every entry checked against the assets, every signature taken from its `.sig` asset, entries that concurrent build jobs overwrote rebuilt from the assets and their `.sig` — `updaterKeysOfAsset` maps asset names to keys — and a failure only when a required platform has no signed asset); on a rebuild of an already published release the build jobs do not touch `latest.json` (`includeUpdaterJson` off), the publish job refreshes its signatures from the `.sig` assets and swaps it in as `latest.json.new` → delete → rename (a leftover `latest.json.new` of a stopped run is picked up by a re-run); the installers are not signed with OS certificates. Since 0.19 (ADR-0104) the Linux matrix also builds `.rpm` and a native arm64 row on `ubuntu-22.04-arm`, the Windows job packs `Sextant_<version>_x64_portable.zip` from the unpatched `target/release/sextant.exe` and uploads it itself (if `check-unbundled` finds it patched, the zip is skipped with a warning and the `packages` job leaves the Scoop manifest out; arm64 stays a hard gate); a copy run from Scoop's `apps\sextant\<version>` directory reports the bundle kind `scoop` (`installedBundleKind`, `src/api/updater.ts`), so About and the updater say "update with Scoop"; the publish check requires `linux-aarch64` and both arches' `-deb`/`-rpm` keys too. The winget installer manifest carries `AppsAndFeaturesEntries` from `msiIdentity` (product name, the MSI Manufacturer — `bundle.publisher`, else the identifier's second part, `sextant` — and the UpgradeCode pinned in `bundle.windows.wix.upgradeCode`, equal to Tauri's derived default; never change it). A dry run renders the manifests from its own bundles and sends nothing; a dry run for a tag not pushed yet builds the commit it was started from (`gh workflow run release.yml --ref main -f tag=v<next> -f dry_run=true`, the manifests' version must already be `<next>`), so workflow changes are tried before tagging. A new asset name the manifests use goes into `assetNames` in `scripts/packaging.mjs` and the fixture.

## How Autopilot works here

Builds are run by the `/autopilot` skill. Requirements, the specification and tasks are in `.autopilot/`.
Progress is in `.autopilot/dashboard.html`. A requirement from `manifest.md` can be dropped
only by the user. An interrupted build is resumed by the phrase «продолжи автопилот» (the user types it in Russian; keep it as is).

### Changes without Autopilot

A small bug or a polish after a build is an ordinary session, without a run.

Read first:
1. `.autopilot/PROGRESS.md` — what is unfinished, known bugs, what was agreed with the user.
2. What was changed after the last build — the first row of the table in "Git history".
3. Only if the change touches them: why it is done this way — `docs/adr/`; what the words mean — `CONTEXT.md`;
   what exactly was asked — `manifest.md` in the build folder (named at the top of `PROGRESS.md`).

After the change:
- commit — by the rules in "Git history";
- a line in "Changes without Autopilot" in `PROGRESS.md`: date — what — why;
- a fixed item from "Unfinished" or "Known bugs" — delete it;
- if something was agreed with the user that the next build must not revisit, add a line
  to "Agreed", in the user's words.
- Write ADRs, `docs/architecture.md`, `CONTEXT.md` and this file in English (ADR-0046).

### Git history

Do not read it whole — take a slice for the question:

| Question | Command |
|---|---|
| what was changed after the last build | `git log --oneline "$(git log -1 --format=%h -E --grep='^Autopilot: (build landed|сборка сдана)$')"..HEAD -- . ':(exclude).autopilot'` |
| everything done for a requirement | `git log --oneline --grep="R02"` |
| history of a file | `git log --oneline -10 -- <file>` |
| when code appeared or disappeared | `git log --oneline -S "<fragment>"` |
| why a line is the way it is | `git blame -L <from>,<to> <file>`, then `git show <sha>` |
| what is inside a commit | `git show --stat <sha>` |

A slice longer than ~30 commits — give it to a subagent and take a ten-line digest.

Commits are in English only: the title says what (`fix: one date format`), the body says why, the trailer
`--trailer "Requirements: R02"` if the change touches a requirement from `manifest.md`.
The title `Autopilot: build landed` (in older builds `Autopilot: сборка сдана`, a literal kept for grep) is written only by Autopilot — it is how the last build is found.
Issues, milestones and comments on GitHub are in English only.
